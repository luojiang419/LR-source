## 现场根因与最终实现

- 完整 SQLite backup 后，在正式安装 D 盘资料上使用旧代码逐语句复现：资产初始化 **23.203 秒**，其中重复重建 `capture_items` 的 **COMMIT 占 23.157 秒**；缓存初始化 1.422 秒。历史正式日志还有 51.282 秒 HTTP ready，主线程位于相同结构事务。
- 同一正式资料库改用新代码：资产初始化约 **16ms**；缓存首次结构标记迁移 219ms，成熟重开低于该计时器分辨率。这里只能报告本机观察值，不能称缓存耗时绝对为零。
- 旧代码的热副本资产初始化 32ms，正式资料后续完整热启动也出现过 3.17 秒首屏。这说明旧故障随 WAL/磁盘缓存状态波动；不能将所有旧启动固定为 51 秒或宣称每轮固定提速倍数。
- `asset_catalog.py` 仅定义变化时事务替换视图；`fast_path_index.py` 状态存在时只读，缺失时仍 `INSERT OR IGNORE` 保证并发首次初始化幂等。
- `preview_cache.py` 用 `startup_schema_v2` 与 SQLite `schema_version` 判定成熟结构；DDL 变化后重新检查。触发器仅定义变化时替换，继续保留文件读取、哈希和删除保护。
- `cache_storage.py` 将文件核对、旧策略退役与容量恢复移到 `StartupTasks`；每批 16 项，关闭可取消，下次恢复。启动函数不等待维护锁或统计查询。`server.py` 接入后台任务。
- 相关回归覆盖成熟库持写锁启动、旧视图一次迁移、旧缓存分批处理、外部替换文件保留、关闭与恢复、后台维护持锁时启动不等待。

## REA 与 LR 缓存机制结论

- 新增离线缓存索引 REA 证据 `ev_220357b803c5c8841763038b348e888a9114460b97362b9670058436b6190312`，样本是 SQLite backup 后的 `catalog_previews/index.sqlite3`，观察到 `previews`、`pending`、`content_previews`、`cache_totals` 等表；SHA-256 与完整限制保存在证据 JSON。该观察仅证明数据库结构，不冒充运行时解码行为。
- 当前实现已有嵌入 JPEG 复用、2048 预览策略、一次读取两尺寸、持久 LRU、内容别名、邻图预取与前台优先。它保存压缩预览并让浏览器保留有限解码图像，并非全部图片常驻解码内存。
- 与 LR 已核实的共同方向是分层预览及保留嵌入 JPEG。任务 108 的静态资源及任务 109 的 32 张吞吐样本不能证明同批 2000 张冷缓存等价；这轮解决的是启动阻塞并验证本地首屏/翻图，不承诺绝对极限。
