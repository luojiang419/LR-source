## 原因与修改

`server.main` 先启动归档线程，再首次初始化共享评级并逐会话播种；已有活动拍摄流使归档线程先进入长时间持锁的照片路径解析和元数据处理，主启动线程等待归档锁，HTTP 服务迟迟未开始响应。空数据测试不容易复现。

调整为创建归档服务后立即初始化、播种共享评级，完成其余服务及回调配置后再启动归档线程。后台任务继续恢复；不延长桌面超时，不删除数据库或用户照片，不修改正式版本。

## 首屏 15.8 秒的原因分析（仅诊断，未改运行代码）

用户询问 15.8 秒首屏慢的原因。核对 `desktop.js` 与 Rust 指标：15.795 秒表示进程启动到 DOMContentLoaded 后两次 requestAnimationFrame 回调，不代表全部照片图片加载完成。该次引擎 HTTP ready 是 5.234 秒；两者差约 10.561 秒包含 WebView/文档加载、首屏数据和脚本执行，不能未经导航级采样把差值全计给某个函数。

- 当前实际引擎独立 HTTP 测量：`/api/ready` 0.093 秒，HTML `/` 0.078 秒；首屏 `/assets/demo-data.js` 9.813 秒，`/api/state` 9.782 秒。后续串行复测分别为 state 7.641 秒、bootstrap 8.453 秒、ready 0.016 秒。
- `index.html` 的 `/assets/demo-data.js` 是没有 async/defer 的同步脚本，排在 desktop/app/formal 及其他工作台脚本之前。它在后端执行 `browse_state → session_browser.read`；数据未返回时，文档解析和后续界面初始化都被阻挡。
- `session_browser.read` 全程持有 `store.browser_lock`，包括分组、共享评级同步、总数/定位/分页及每行 gap 查询；保存会话和评级/SKU 回调也持有这把锁。启动时已经恢复索引、元数据、监控、模型与缓存工作线程，存在锁排队和磁盘/CPU竞争条件。
- 使用 SQLite backup 复制现有两份业务数据库（约 4 MB 和 10 MB）到隔离快照，以真实分页实现读取 240 条记录：256 次 SQL，总计 0.0565 秒。240 次逐行 gap 查询合计仅 0.001 秒，所以不能把 N+1 形式直接认定为当前几秒延迟的主因。
- 已确认首屏关键路径的数据接口慢、同步脚本将该延迟传递到首屏；隔离测试支持运行时排队/竞争是主要方向。尚未取得运行中各线程堆栈/锁持有耗时，不能声称已经精确分清 browser_lock、SQLite 写锁与后台 I/O 各占多少。
- 后续优化优先级：首屏框架与首批照片数据异步加载；推迟非首屏必需的全库恢复/预热；缩短浏览锁持有范围、复用首屏读取结果。不要先无证据更换 GPU 或清空用户照片/数据库。
- 证据：`build/startup-performance-analysis/summary.json`、`sql-profile.json`，隔离数据库也在该忽略目录。此次没有关闭用户程序、修改业务数据或新增源码改动，没有重复已通过的回归。
