## 根因与实现

- 原 `rename_shooting_row → browse → rename_sku` 在请求内扫描全库、确认资产、逐文件计算哈希，再压缩重写 `source.xlsx`。这些准备发生在业务锁内，慢盘/NAS 和大图片表会拖长请求。前端 `showModal + trackRowWrite` 又一直持有 `busy`，关闭弹窗也不终止等待，正常清单轮询被阻断。
- 改款使用已登记资产、每个路径的持久指纹快速生成版本化写入任务，复用已有原片校验和原子提交 worker；不读取/探测原片，也不进行源 Excel 压缩。多副本使用各自 `path_sha`，不会把一个副本的文件哈希套给另一个。
- 文件 worker 从目录/事件 tick 中独立运行。原来 `sync_stream` 或事件投递一抛异常，后面的 `process_one` 就不再执行，导致队列长期 queued。新 worker 继续处理持久任务；原有 running 在启动时恢复为 queued，关闭时等待在途提交完成。
- 区间投影新增冻结上下文键 `(project,scope)`，与整款编辑及归档重算保持一致；未绑定旧照片不再被下一类型的标签吸收。整款编辑与归档重算的未知二星边界也采用共享评级。SKU 缓存 schema 升级到 v3，重建旧版错误投影，不要求重新 OCR。
- 删除改款模态弹窗及无限等待；“全部”与单工作表均使用原行项目 ID 编辑。页面继续轮询，queued/running 只在拍摄状态内显示“正在写入中”，实际 applied 不输出写入提示；失败显示原因和原批次重试入口。
- 数据库保存新款号，导出在隔离快照中把计划行的新 SKU 写入 Excel，保留用户原始表格及软件源副本。没有进行 NAS 整张原片副本备份。
