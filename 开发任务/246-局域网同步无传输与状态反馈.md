## 已确认的需求（2026-11-20）
1. **同步对象是“当前一套”**：主机当日正在现场监控的文件夹即当前一套。只同步这一套，主机的其它历史拍摄会话一律不读、不散列、不传输。
2. **跨零点自动分套**：监控跨过主机本地零点（Asia/Shanghai）时，零点后入库的照片自动算作新的一套，同步切换到新一套。零点前的那套留在客户端作为历史，不再更新。
3. **没有“手动补同步某一天”的入口**，也不做历史选择界面。
4. **客户端已收到的历史小档保留不动**，不删除、不清理，可以离线浏览。
5. 一台主机可以连接多台客户端，两端实时同步，并且主机和每台客户端都显示真实状态。

## 现象与根因（已查实）
- 办公桌（本机 DESKTOP-G7KA5NK，1.0.5，小档目录 `E:\小档`）联机大屏（192.168.0.231:8467，PC-20240918RSBB，1.0.4）。界面显示“正在接收”，`E:\小档\大屏 [8624ba2a]` 却为空。本机 `/api/lan-sync` 实际为 `phase=reconnecting`、`error="timed out"`、`received_files=0`。
- 用本机保存的密钥直接请求大屏：`/sync/challenge` 用时 0.04 s，`/sync/login` 用时 0.01 s；`/sync/revision` 120 s 内都没有返回。
- **R1 清单过大过慢**：`lan_sync_data.SyncData.snapshot()` 的问题有三处。
  - 在 sku、archive、store 三把业务锁内整表读取所有同步表（大屏约 2 万资产、2.2 万 catalog_links）。
  - 同步范围是全部 15 个拍摄会话，共 24,467 张照片。
  - 首次对每张 JPG 和 XMP 做完整 SHA-256，散列缓存只在内存里。
  - 再加上 `manifest()` 持锁同步生成，而客户端超时只有 10 s，所以一份清单都等不到。
- **R2 状态不真实**：
  - 主机只要客户端登录过就显示“正在发送 · N 台”。
  - 客户端只要处在接收模式就显示“正在接收”，真实错误只拼在底部文字里，而且是英文 `timed out`。
- **R3 自连（未核实）**：PC-20250104PELR（192.168.0.90）截图里，已连接客户端就是它自己（同名、同 IP）。发现列表里还有 `192.168.0.90:53311 · 接收中`，推测同机还有第二个实例在接收。
- **R4 锁争用（待核实）**：大屏 11-20 有 455 条元数据任务长期排队，原因是“归档处理尚未收尾”，即 `asset_archive._metadata_commit_lock` 0.5 s 内拿不到 `archive.lock`。旧 `snapshot()` 在持锁期间整表读取，可能是诱因之一。
- **R5 单点失败**：任一拍摄记录只有 RAW 没有 JPG，或照片被移走时，整份清单直接失败。

## 设计
### “当前一套”的定义（主机端）
- 当前一套由两部分组成：现场监控会话 ID（`WATCH.state().session_id`）和套日期（主机本地日期）。套 ID 为 `set_id = sha256(session_id + ':' + YYYY-MM-DD)` 的前 16 位。
- 照片归属：照片在当前监控会话中，并且入库（到达主机）时间的本地日期等于套日期。入库时间缺失时，用拍摄时间（EXIF）兜底。
- 主机未开启现场监控时，当前一套为空。客户端显示“主机未开启现场监控”，已收到的资料保留。
- 主机换了监控文件夹，或停止后重新开始，就产生新的一套，客户端跟着切换。
- **跨零点**：同一监控会话内，零点后入库的第一张照片产生新的 `set_id`。主机同时发出“分套”变更（含新套日期）。只在同步协议层分套，不拆分、不修改主机本机的会话与业务数据。
- 随套同步的关联数据，只限于本套照片涉及的记录：
  - 照片评级、XMP；
  - SKU 区间、款号与确认状态；
  - OCR；
  - 资产、文件、位置；
  - 当前 SKU 项目，以及套日期对应的自动拍摄文档（`YYYY-MM-DD.xlsx`）。
- 分套后：
  - 旧套在客户端冻结为历史；
  - 零点后才修改的旧套照片（例如补改星）不再推送。这是确认需求 2 的直接结果，验收时要说明。

### 实时增量协议（protocol 2）
- **主机变更表** `lan_sync_changes(seq INTEGER PRIMARY KEY, set_id, kind, ref, created)`，放在 store 库中，序号重启后接着递增。
  - 写入点：照片入库、改星、款号确认或修正、元数据写入完成（XMP 变化）、拍摄文档更新、分套、停止监控。
  - 只保留当前一套和上一套的变更，旧的直接清理。
- **主机文件散列表** `lan_sync_hashes(path PRIMARY KEY, size, mtime_ns, sha256)`：
  - 照片入库时现场监控读文件，顺便计算并写入；
  - 命中大小和 mtime 就直接复用，重启也有效；
  - 同步接口只对本套中缺失或变化的文件补算，绝不散列历史。
- **接口**（沿用现有挑战、登录、令牌鉴权）：
  - `GET /sync/current`：当前一套的完整快照（套信息、行数据、文件摘要和大小），加上当前最新的 `seq`。首次联机、序号断档或分套后调用，数据量只有当前一套。
  - `GET /sync/changes?set=<set_id>&after=<seq>`：长轮询。有变更立即返回受影响的行和文件摘要；没有就最长挂起 25 s 后返回空，同时充当心跳。返回 `set_changed` 时，客户端改调 `/sync/current`。
  - `GET /sync/blob/<sha>`：沿用，按摘要下载。
  - `POST /sync/ack`：客户端上报处理进度，内容为已应用的 `seq`、待下载数、已收文件和字节、当前文件、最近错误、客户端版本。
- **读数据不持业务锁**：快照和变更都在 SQLite 只读事务（WAL 快照）内用 SQL 过滤读取，读完立即释放，不再持有 sku、archive、store 的 Python 锁，避免阻塞现场写入（对应 R4）。
- **客户端应用**：
  - 先持久化待应用批次，再下载文件；
  - 下载时最新照片优先，最多 3 个并行，每个文件校验后原子替换；
  - 文件齐了再投影业务库并记录 `seq`；
  - 崩溃或重启后从已确认的 `seq` 续上，不重复入库。
- **单张容错**：只有 RAW、文件缺失或校验失败的照片标记“跳过：原因”，计入状态，其余照片照常同步（对应 R5）。
- **落盘位置**：`小档根/主机名 [设备前8位]/YYYY-MM-DD/拍摄-<set_id>/原相对路径`。客户端会话命名为“主机名 · 监控文件夹名 · YYYY-MM-DD”，每套一个会话。历史套的文件和会话保留不动。

### 多端状态
- **主机逐台记录**：名称、设备 ID、IP、版本、最后心跳、已确认 `seq`、落后条数、正在传输的文件、速率、最近错误。界面每台一行：

  | 显示 | 条件 |
  |---|---|
  | 同步完成 · 延迟 x 秒 | 已确认 `seq` 等于主机最新 `seq` |
  | 正在传输 a / b · x MB/s | 有待下载文件 |
  | 落后 N 项 | 有心跳，但 `seq` 落后 |
  | 连接中断（x 秒前） | 超过 30 s 没有心跳或长轮询 |
  | 错误：原因 | 最近一次上报错误且未恢复 |
  | 对方版本过旧，请更新 | 客户端只支持 protocol 1 |

  顶部汇总：“当前一套：监控文件夹名 · 日期 · N 张 · M 台已连接 · K 台同步完成”。只有确实在传文件时才出现“正在发送”。
- **客户端阶段**：
  1. 正在联机；
  2. 主机未开启现场监控；
  3. 正在获取当前一套 a / b；
  4. 接收 a / b；
  5. 已同步，显示最新一张的时间和延迟；
  6. 连接中断：中文原因，正在重连；
  7. 已切换到新的一套（YYYY-MM-DD）。

  没有任何数据时不显示“正在接收”。
- **拒绝自连**：登录时客户端设备 ID 等于主机设备 ID，或者来自同机同数据目录，就拒绝并提示“不能连接本机”（对应 R3）。同机确需另一个实例时，显示为“本机另一实例”。

### 兼容
- 旧客户端（protocol 1）仍可调用 `/sync/revision` 和 `/sync/manifest`。但主机返回的旧清单也只包含当前一套，并使用持久散列，避免旧客户端拖垮主机。主机界面标注“对方版本过旧”。
- 实时增量和新状态需要主机、客户端都升级到含 protocol 2 的版本（计划 1.0.6）。

## 本轮实现与验证记录
- 当前套按监控 session + generation + 上海日期生成：补入 generation 是为了满足“停止后重新开始是新套”，正常进程重启持久保留 generation。只有零点后第一张照片入库才切换日期。
- 新入库记录写入 `ingested_at` 并在后到 RAW/JPG 时保留；旧记录先用现有 `shooting_captures.received`，再用 EXIF。SQL 只取当前套关联行；所有同步读取使用只读 WAL 事务，散列在事务外完成。
- 业务表触发器在原事务内增加持久修订；提交后复用 `worker_activity.Condition` 唤醒长轮询。服务将同时发生的变更合并成差异批次，原子写入 `lan_sync_changes` 与当前快照并发布 seq，避免每个细小 SQL 写入重复推送整份资料。日志只保留当前套/上一套。
- 客户端先保存待应用批次，最多 3 路校验下载，再幂等投影和提交持久游标；缺图/RAW/坏文件按张跳过，接收端显示原因，并自动补试可重试文件。切套后的本地会话和项目使用套作用域 ID，历史文件与评级不再被新套覆盖。
- 三端模拟：首次新照片与评级/款号均约 0.55 s，最终回归分别 0.203 s / 0.156 s；单台断网 60 s 后补齐，主机与客户端重启后无重复，持久游标续接已明确断言。
- 大库夹具：24,000 历史 + 30 当前，首轮 0.175 s、后续验证 0.182–0.209 s，历史文件读取 0；清空内存散列后复用磁盘散列 30 个。散列阻塞时元数据提交 0.002–0.003 s。
- 源码验收入口：`python -X utf8 -m unittest test_lan_capture_sync test_lan_capture_sync_v2 test_shooting_progress test_build_workbench test_folder_watch -v`（工作目录 `选片助手`）。测试使用独立临时数据目录与隔离发现端口，断网通过请求出口故障注入，非修改真实网卡。
