## 分析环境与方法
- 本机：i7-14700K（28 线程）、128 GB 内存。磁盘：C 为 NVMe（剩余约 42 GB）、D 为 2 TB SATA 机械盘（ST2000VX008）、G 为 USB SSD、E 为 SATA 机械盘。
- 安装版 `D:\Program Files\Framekeep` 位于 D 盘机械盘，其资料目录 `data\` 内 `asset_catalog.sqlite3` 为 **24 GB**。分析时安装版未运行。
- 实测手段：隔离数据目录（`build/perf-analysis/data*`）启动源码引擎；`py-spy` 采样（安装在 `build/perf-analysis/pylib`，未改动全局环境）；给 `sqlite3.connect` 和 `BEGIN IMMEDIATE` 打点；只读 URI（`mode=ro`、`query_only=1`）读取生产库结构与抽样；读取安装版 `engine.log` 的启动检查点。

## 实测结论（按影响排序）

### 1. 目录库 24 GB，其中约九成来自逐张图片的全量元数据（实测）
- 生产库：页大小 4096，6,140,909 页，`freelist_count=0`（不是空闲页浪费）。`items` 最大 rowid 716,985，63 张表、72 个索引、62 个触发器。`sqlite_stat1` 不存在。
- 抽样平均行长：`items` 约 407 B（全表约 278 MB）；`catalog_metadata` 约 **15,256 B/行，最大 114,382 B**，按 716,985 行估算约 **10.4 GB**。其中 `payload` 约 10,059 B，`search_text` 约 9,130 B。
- `catalog_metadata_fts` 是 `content='catalog_metadata'` 的 FTS5 **trigram** 外部内容索引，对 9 KB 文本建三元组索引，估计再占约 10 GB（该表扫描超时，未取得精确值；`dbstat` 在本机 SQLite 不可用）。
- 根因（读代码确认）：`catalog_metadata.py::_extract` 用 ExifTool `-all:all` 提取全部标签（含 MakerNotes、ICC、XMP 全量）存入 `payload.tags`；`_search_text` 把整份 payload（`capture`、`media`、`description` 与 `tags`，内容相互重复）逐键逐值拼成文本并建 FTS。
- 连带代价：
  - 短词（少于 3 字符）搜索走 `instr(lower(m.search_text),lower(?))`，需读取约 10 GB 大文本，代码注释已承认「逐项随机读取大段 payload/search_text，放大磁盘开销」。
  - 每次指纹变化会触发 `catalog_metadata_change`/`catalog_metadata_retry` 触发器重排队，随后重写这些大字段并同步更新 FTS。
  - 目录库其余表很小：`literal_search_grams` 40.5 万行但首次 `count(*)` 耗时 17.5 s（缓存热后 0.01 s），说明在机械盘上冷读取随机页代价极高，库越大冷读越慢。
- 另见 `items` 表有 14 个二级索引（含 10 列的 `catalog_browse_cover`、`catalog_pair_cover` 等覆盖索引）。索引总占用未测，写放大风险列为推断，见 A3。

### 2. 冷启动在真实数据下可达数分钟（实测）
- 来源：安装版 `engine.log` 共 319 次完整启动。`http ready` 耗时 p50 3.75 s、p90 14.6 s、最大 **291.2 s**；大于 10 s 的 55 次，大于 60 s 的 7 次。对照：隔离空库启动仅约 0.4–1.2 s。
- 慢启动阶段分布（取最慢的几次）：
  - `catalog ready` 42–78 s（源码 `AssetCatalog.__init__` 与 `connect()` 的 WAL/配置步骤；启动堆栈日志多次停在 `asset_catalog.py` 的建库连接）。
  - `ratings ready` 之后 `shared_ratings.seed_session → _seed_large` 数秒至十余秒。
  - `analysis ready` 后段 8–28 s；`preview_cache` 的 `cache_for`/`reconcile`、`cache_storage` 初始化在堆栈中出现。
  - 一次 `reference library ready` 从 1.75 s 跳到 **279.25 s**（卡约 277 s），当次详细堆栈还没分析。
- 判断：以上都与「库在机械盘 + 冷缓存 + 大库」一致，但每个阶段的具体慢点未用 `py-spy` 在真实库上确认（见 A1）。启动期间前台已有 `shell ready`、`capture ready` 提前放行拍摄通道，但其余接口在 `BOOT_GATE` 前返回 503。

### 3. 后台线程空闲轮询：反复新建 SQLite 连接并抢写锁（实测）
- 条件：全新空数据目录、无界面连接、启动后 25 秒起统计 30 秒。
- 结果：`sqlite3.connect` **约 90 次/秒**（2697 次/30 s）；`BEGIN IMMEDIATE` **约 9.2 次/秒**（全部来自 `asset-metadata` 线程）；引擎进程空闲 CPU 约 8%（一个核），约 650–700 次读操作/秒，约 2.2 MB/s 读取，另有约 41–44 个线程。
- 连接次数前几名：`asset-archive` 432、`sku-recognition` 426、`portable-capture` 282、`asset-metadata` 276、`analysis-workflow-discovery` 232，其余约 100–140 各数个线程。`py-spy` 的热点栈顶都是各服务的 `connect()`。
- 代码：`asset_archive._run_metadata` 空闲时每 0.1 s 调 `process_one()`，`process_one` 无条件 `BEGIN IMMEDIATE` 并先执行 `UPDATE metadata_jobs SET status='queued' WHERE status='running'`，即使队列为空；`AssetArchive.connect`、`SkuService.connect`、`AssetAnalysis.connect` 每次都 `sqlite3.connect` 再关闭。各线程等待周期 0.05–0.5 s（`closed.wait(.2)` 一类）。
- 为什么重要：空库的轮询已占 8% CPU；大库时每次连接还要打开 WAL/共享内存、命中 24 GB 库的页缓存；空轮询的写事务与真正的拍摄写入争同一个库锁。历史文档（242、225）记录的「元数据队列饥饿、归档锁争用」属于同一类问题，本项是其结构性根因之一（推断，待 A4 验证）。

### 4. 界面侧的轮询与渲染（实测统计 + 代码确认）
- 前端为 `演示方案/` 下 42 个未压缩、未合并压缩的脚本，打包后约 942 KB；初始 CSS 14 个文件约 264 KB。`/workbench.js` 每次请求都 `stat` 42 个文件并对约 942 KB 重算 SHA-256（`workbench_assets.py`）。
- 19 处 `setInterval` 轮询（周期 1–2 s，`archive-capture.js` 1.5 s 与 1 s、`ocr-feedback.js` 1 s、`multidimensional-workflow.js` 1 s、`automatic-backup.js` 1 s 等），部分按可见页面判断是否执行，部分只判断 `document.hidden`。
- `server.py::reply` 对列表内的 GET 响应调用 `views.remember`：响应变化就序列化并 `atomic_write`（含 `fsync`）写 `views.json`（上限 4 MB），在轮询频率下会产生持续的磁盘同步写；是否实际频繁变化未测（A5）。
- 渲染：选片页网格有虚拟滚动；资产归档网格 `asset-library.js` 用 `replaceChildren` 一次生成全部卡片（任务 225 提到单目录可到 1500–6000 张）；CSS 有 46 处 `backdrop-filter`/`filter:blur`，另有大量 `infinite` 动画（加载轨道、扫描线、写入微光等）。这些对 WebView2 的合成成本未实测（A5）。

### 5. 已量化但优先级低的项
- HTTP 服务使用标准库 `ThreadingHTTPServer`，未设置 `protocol_version`，即 HTTP/1.0 每请求一条连接。本机基准（1500 次小响应）：单连接 HTTP/1.0 p50 0.40 ms、HTTP/1.1 长连接 0.12 ms；6 并发吞吐 3221 与 7780 req/s。绝对差异约 0.3 ms/请求，不是主要瓶颈；改为长连接还会影响依赖 `self.connection` 的检索取消逻辑，风险大于收益，列 P3。
- `direct_previews.preview_bytes` 缩放用 `Image.Resampling.LANCZOS`，其余缩略图路径用默认；缩略图主链路已用嵌入预览直通，影响面小，未实测，列 P3。
- 安装版 `data\maintenance\updates` 留有 `package.zip`（317 MB×2、262 MB）及完整 `stage` 目录，合计约 1.7 GB，属更新残留，不是性能问题，只涉及磁盘占用，清理需用户确认。
- 开发环境：`build/` 约 109 GB、`.runtime/` 约 10 GB、C 盘剩余 42 GB；`EDSDK132011CD(13.20.11)/` 为未跟踪目录。AGENTS 规定的 6 小时清理本次没有执行。

### 已核对、确认较好的部分（不必重做）
- 缩略图链路：优先读取 JPEG/RAW 内嵌缩略图，尺寸合适时只整理 JPEG 头不重编码（`archive_thumbnails.py`、`preview_codec.embedded_jpeg`）。
- 导航任务灯统计（`task_status.py`）使用只读连接并限时 50 ms；`CatalogStatus` 用单后台快照避免 HTTP 轮询重复聚合。
- SQLite 已普遍使用 WAL、`mmap_size`、`wal_autocheckpoint=0` 配合自有回收线程；启动期视图只在定义变化时重建。
- 引擎启动检查点已分阶段输出，拍摄通道在 `capture ready` 提前就绪（任务 135、157、192、224 已做大量工作）。

## 优化方案与阶段计划
每个阶段先写失败/基准测试，再改代码；所有数据库迁移须可恢复、后台分批、不阻塞启动，并按 AGENTS 要求「最小更新包」发布，不改变用户数据路径。

### P0-1 瘦身元数据（预期影响最大）
- 方案：
  1. `payload` 只保留业务使用的字段：`capture`、`media`、`description`、`stamp` 及 SKU/拍摄类型等必要标签；`tags` 改为白名单，MakerNotes、ICC、缩略图二进制等不入库。「详情展开全部已读取标签」需求改为点击时现读文件（或保留压缩 `payload_z` 并仅按需解压），先确认产品取舍。
  2. `search_text` 只包含相机、镜头、日期、ISO/光圈/快门、标题、描述、关键词、SKU、文件名等用户可搜索的内容，不再拼接整份 payload，也不重复 `capture` 与 `tags`。
  3. FTS 随 `search_text` 变小重建；评估去掉对短词的 `instr` 全表兜底，改走 `literal_search_*` 倒排或限制范围。
  4. 迁移：后台分批重写旧行、按 `generation` 断点续作、完成后 `wal_checkpoint`；最后提供「压缩数据库」入口（`VACUUM INTO` 到新文件再切换），不得在启动时自动整库重写。
- 验收：用 5 张真实样片复制 1000 张隔离库对比，每行平均字节与库总大小下降，并给出新旧数字；既有元数据读写、搜索、SKU 回写测试通过；拍摄现场链路延迟不回退。
- 风险：详情页、`catalog_sku_writeback`、`photo_metadata`、搜索命中展示可能依赖 `payload.tags`，改前必须全局检索调用点。

### P0-2 冷启动与库位置
- 方案：
  1. 在真实库（只读副本或程序未运行时）用 `py-spy dump` 周期采样，确定 `catalog ready`、`reference library ready`、`shared_ratings._seed_large`、`preview_cache.reconcile` 各自的实际慢点（A1），再决定下沉到后台还是加索引。
  2. 把非首屏必需的初始化（`ReferenceLibrary` 构造、`seed_session` 大会话、缓存对账）改为 `http ready` 之后后台完成，接口在未就绪时返回「加载中」而不是整体 503。
  3. 对已有库跳过启动期的 DDL/建索引/迁移判断：以 `user_version` 或 schema 摘要一次比较，避免每次启动对 63 张表和 72 个索引执行 `CREATE ... IF NOT EXISTS`。
  4. 设置页「文件索引数据库存储」已提供迁移到高速盘的功能：在引导和诊断中提示库所在介质，机械盘时给出建议；`maintenance/updates` 残留由更新器在成功后清理。
- 验收：真实库冷缓存（重启系统或清空待测文件缓存）启动 `http ready` 与 `catalog ready` 的 p90、最大值；对比修改前 14.6 s / 291 s。

### P1-1 后台线程改为事件驱动
- 方案：
  1. 为各服务提供统一的「有活才醒」机制：入队处 `wake.set()`，空闲等待改为 5–30 s 兜底超时；已有 `wake`/`Condition` 的服务（`sku_service`、`intelligence`、`catalog_metadata`）直接延长空闲超时。
  2. `AssetArchive.process_one` 先用只读 `SELECT 1 FROM metadata_jobs WHERE status IN ('queued','running') LIMIT 1` 判断，有活才 `BEGIN IMMEDIATE`；`running → queued` 的恢复只在启动和异常后执行一次。
  3. 各服务线程持有长期连接（`check_same_thread=False` + 线程内独占），或封装共享连接池，取代每个 tick 的 `connect/close`。注意已有的 `busy_timeout`、WAL anchor 与 `NO_CKPT_ON_CLOSE` 约束。
  4. 空闲退避：连续无工作的 tick 间隔逐级延长，有事件立即恢复。
- 验收：重复本次空闲打点，目标为 `sqlite3.connect` 少于 5 次/秒、空闲 `BEGIN IMMEDIATE` 为 0、空闲 CPU 低于 1%；拍摄入队到写入的延迟不高于现状（用任务 180、243 的现场测试）。
- 风险：这是最容易引入「任务不被唤醒」的改动，每个服务必须保留兜底超时并补「入队后 X 秒内处理」的测试。

### P1-2 统计信息与索引审计
- 方案：对生产形态数据评估 `PRAGMA optimize`/带 `analysis_limit` 的 `ANALYZE`（现在没有 `sqlite_stat1`，而代码里大量 `INDEXED BY`、`CROSS JOIN` 手工约束，说明规划器曾选错计划）；统计 `items` 14 个二级索引的实际占用与命中，合并或删除重复前缀索引（如 `catalog_pair`、`catalog_pair_root`、`catalog_pair_cover`、`catalog_items_browse`、`catalog_root_media_page`）。
- 验收：关键查询（目录浏览分页、搜索、配对）的 `EXPLAIN QUERY PLAN` 与耗时前后对比；写入吞吐（批量入库）不下降。

### P2 界面
- 方案：轮询合并为一个 `/api/poll` 或服务端事件推送（SSE），按当前页面订阅；资产归档网格改虚拟列表或分段渲染；对 `views.remember` 增加写入节流（例如变化后延迟 2–5 s 合并写，且不 `fsync`，丢失可重建）；`/workbench.js` 缓存 SHA-256，按文件版本变化才重算；脚本/CSS 构建期压缩并启用长缓存；静态页面隐藏时暂停 `infinite` 动画，减少同屏 `backdrop-filter` 数量。
- 验收：WebView2 空闲 CPU/GPU 占用、1500 与 6000 张目录的首屏与滚动帧率（Chrome DevTools 性能轨迹）、`views.json` 写入次数。

### P3 低优先
- HTTP/1.1 长连接（需先保证 `CATALOG_SEARCH` 取消逻辑不依赖一连接一请求）；`LANCZOS` 改为 `reducing_gap` 加双线性并做质量对比；清理 `maintenance/updates`；开发目录 `build/`、`.runtime/` 的 6 小时清理策略落地。
