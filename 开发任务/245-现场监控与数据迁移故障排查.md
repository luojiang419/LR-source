## 问题 1：现场拍摄卡在“正在接收 · xxx”，拍完无法标星和 OCR 解析款号

### 现象
`演示方案/receiving-preview.js:57` 的覆盖层 `.receiving-photo-preview` 一直不消失。覆盖层期间以下控件都被设为 inert 或直接返回，所以无法标星，也无法发起 OCR：
- `#stars`、`#reject`、`#clear-rating`、`#undo`、右栏和侧栏底部（`receiving-preview.js:60`）；
- `setRating`、`assignRemoteRating`、`increment/decrementRating`（`app.js:266、468、477、487`）；
- 鼠标遥控被视为暂停（`mouse-remote.js:19`）。

### 根因
1. **【已证实，主因】同一张照片的接收通知 id 和正式照片 id 不一致。**
   - RAW+JPG 配对时，正式 id 取主文件 CR3 相对路径的哈希（`选片助手/media_engine.py:315、321`）。
   - 直连接收通知只针对 JPG，id 用 JPG 路径哈希（`选片助手/direct_jpeg.py:57-58、72`）。
   - 实测：`sha256('xsy_2144.cr3')[:24]=90b98cfe14f1800ac31c5a25`，等于 `/api/watch.last_photo_id`；`sha256('xsy_2144.jpg')[:24]=96cba46b5db68cde92a4ac38`，两者不同。
2. **【已证实代码路径】接收通知取消了正在进行的自动跟随，之后没有重试。**
   1. CR3 先写完，在 JPG 出现前作为“仅 RAW”入库，`/api/watch.last_photo_id` 变为正式 id。
   2. `folder-watch.js:85-93` 调用 `refreshLive(..., 正式id)`，进入 `prepareLivePreview`，等待 RAW 480 缩略图，最长 4 秒（`app.js:52-66`）。在 UNC 共享上这段等待较长。
   3. 等待期间 JPG 到达，直连通道发出 `receiving`（不带 `formal_id`）。`receiving-preview.js:83` 调用 `Framekeep.supersedeLivePreview(photo?.formal_id||photo?.id||...)`，传入的是 JPG 哈希。`app.js:26` 判定 id 不同，取消准备并递增 serial，于是 `follow=false`（`app.js:63`）。字节进度事件每次都会重复取消。
   4. `formal.js:121-122` 把 `followId` 置空，选中项不切换；但 `folder-watch.js:90` 仍记下 `lastPhotoId=state.last_photo_id`。
   5. JPG 配对入库后，`direct_jpeg.py:102-108` 的 `acknowledge` 写入 `latest.formal_id`。这只是更新记录，不是新增，`/api/watch.last_photo_id` 不变；`folder-watch.js:88` 只在 `last_photo_id` 变化时跟随，所以不再重试。
   6. 覆盖层释放条件（`receiving-preview.js:43`）都不成立：`active` 复制自最初的 `receiving`，没有 `formal_id`，`readyFor(active)` 实际是 `mainReady(JPG哈希)`；`mainReady(state.last_photo_id)` 要求主预览已切到正式 id（`:28-31`），但主预览没切过去。每张新照片都会重复这个过程。
3. **【已证实，次要】两个接口的 `last_photo_id` 不一致。** `folder_watch.py:208-211` 首次扫描时只更新 FolderWatch 自己的 `last_photo_id`，不同步到 `DirectJpegFeed`。直连通道没有通知时，`committed()` 的兜底条件变成 `mainReady(null)`，永远为假。
4. **【已证实，设计缺陷】覆盖层没有超时兜底。** 只有主预览命中、关闭跟随、打开对话框、方向键/Esc、点击 `#previous/#next/[data-view]` 才会释放；点击照片区和右栏被 `receiving-preview.js:96-100` 拦截。
5. 已排除：`full=1` 判断对 JPG（`direct_channel.py:91`）和 RAW 配对（`server.py:133-135`）都能成立；UNC 写完判定只造成几秒延迟，现场 `pending=0`、54 对全部入库。

### 修复方法
1. `选片助手/direct_jpeg.py` / `folder_watch.py`：给 `DirectJpegFeed` 增加别名映射。FolderWatch 在 RAW 单独入库时登记“JPG 相对路径哈希 → 正式 id”（`existing` 已按 raw/jpg 路径建索引），`announce()` 发出的 `receiving` 直接带 `formal_id`。
2. `演示方案/receiving-preview.js`：
   - `show()` 只用 `formal_id` 调用 `supersedeLivePreview`；没有 `formal_id` 时不调用。
   - `committed()` 中新通知与 `active.key` 相同时，把 `notice(state).formal_id` 合并进 `active`。
   - 增加兜底：`receiving` 为空且 `latest.formal_id` 已存在时，主预览 1–2 秒内仍未命中，就释放覆盖层；跟随开启时调用 `Framekeep.browsePhoto(formal_id)`。
3. `演示方案/folder-watch.js:85-93` 与 `formal.js:115-125`：`refreshLive` 返回值区分“目录已更新”和“跟随成功”；`preview.follow===false` 时不写 `lastPhotoId`，下次轮询重试。
4. `选片助手/folder_watch.py:211`：首次扫描时同步更新 direct 的 `last_photo_id`（例如 `self.direct.acknowledge([], None, previous['id'])`）。

### 验证
- 现有：`test_jpeg_receiving_preview`、`test_direct_channel`、`test_capture_notification_recovery`、`test_monitor_latency`、`test_folder_watch`、`test_watch_history`、`test_live_arrival_queue`、`test_live_layout_browser`。`test_jpeg_receiving_preview.py` 目前没有 CR3 用例。
- 新增浏览器用例：先写 CR3 并单独入库，用 route 把 RAW 缩略图延迟约 2 秒，期间写入同名 JPG；断言主预览切到 CR3 正式 id、覆盖层 3 秒内释放、`#stars` 不是 inert；再写第二对照片，同样释放。
- 新增单元测试：开始监控时最后一张已在库中，`/api/watch/direct.last_photo_id` 等于 `/api/watch.last_photo_id`。
- 现场：UNC 目录连续拍摄 CR3+JPG，每张拍完都能立即标星并发起 OCR。

## 问题 4：选择文件夹点“开始监控”，按钮变灰无反应，过一会儿又变亮

### 现象
按钮变灰约 20 秒后恢复，对话框不关闭，界面不进入监控布局；底部显示“正在监控 · 本次载入 0 张”，但目录里有 108 个文件。

### 根因
1. **【已证实】`/api/watch/start` 在 HTTP 请求线程中同步做大量 UNC 读写，超过前端 20 秒超时。**
   - 调用链：`server.py:965-968` → `folder_watch.py:154-172 start()` → `catalog_store.py:277-294 ensure_live_session` → `archive_capture_service.py:318-363 prepare_live`。
   - `prepare_live` 持有 `io_lock` 时同步执行：建本地库并写 `registry.json`；`dataset.acquire()`（`:334`）在共享盘建 `.shiying`、用 CreateFile 取得 `write.lock`、写 owner 和 `dataset.json` 并 fsync 回读、再 `refresh()` 读取远端提交（`portable_capture_store.py:102-140、251-269、452-522`）；首次时 `catalog.add_root`（`:340`）会同步执行 `scan(root_id)`（`asset_catalog.py:265-277、352-354`）。若其他任务正持有 `io_lock`，还要先排队。
   - 时间线：`data/portable-capture/registry.json` 12:40:57，共享盘 `.shiying/write.lock`、`dataset.json` 12:40:58，`data/folder-watch.json`（`start()` 最后的 `_persist`）12:41:44，整段约 46 秒。
   - 前端 `api()` 默认超时 20 秒（`formal.js:20、33`），`folder-watch.js:121` 没有单独加长。超时后 `finally`（`:128`）恢复按钮，`dialog.close()`、`refreshLive` 和拍摄计划绑定都没执行。
   - 服务端请求继续跑完，所以 `/api/watch` 显示 `enabled=true`；但前端会话没切换，`workbench-layout.js:156` 要求 `watch.session_id===FRAMEKEEP_SESSION.id` 才进入监控布局。
2. **【已证实】超时提示被轮询覆盖。** 错误写入 `#watch-status`（`folder-watch.js:127`）后，长轮询每次 `show()` 都执行 `$('watch-status').textContent=state.message`（`:66`），后端完成时被替换为“正在监控 · 本次载入 0 张”。
3. **【已证实】“载入 0 张”是统计口径。** `arrivals` 只计本次 generation 新插入的记录，`start()` 清零（`folder_watch.py:169`）。会话 id 是根目录哈希（`catalog_store.py:280`），54 张早已在会话中（`GET /api/state?session_id=9fbde5…` 返回 54 条）。
4. **【已证实】重复点击会更慢。** `start()` 不判断“已在监控同一目录”，每次都重置 generation、清空 arrivals，重新走一遍 `prepare_live`。
5. **【已证实，性能】`.shiying` 元数据目录在被监控目录内。** `folder_watch._run` 收到非图片文件的递归通知时 `named=False`，触发全目录补偿扫描；12:41:58–12:45:27 写了 7 次提交，每次都触发一次。

### 修复方法
1. `folder_watch.start` / `server.py:965`：请求线程只做路径校验和 `ensure_live_session` 的会话登记，状态设为 `initializing` 后立即返回；`prepare_live` 移到 watch 工作线程，失败时通过 `error`/`message` 上报（如“正在准备网络共享目录…”）。
2. `archive_capture_service.py:340`：`catalog.add_root` 改为登记根目录并后台入队扫描，不同步 `scan`。
3. `WATCH.start`：已在监控同一目录（大小写不敏感）且 `recursive` 相同时，直接返回当前状态，不重置 generation 与 arrivals。
4. `folder-watch.js:114-128`：开始请求单独设 60–120 秒超时；超时后 `GET /api/watch` 复核，已开启同一目录就按成功继续 `dialog.close()` 和 `refreshLive`；用错误标志防止 `show()` 覆盖错误提示。
5. 文案改为“正在监控 · 已有 N 张 · 本次新增 M 张”，后端增加 `total` 字段。
6. `folder_watch._run`：忽略 `.shiying/` 和 `.framekeep-` 开头路径的通知。

### 验证
- 现有：`test_folder_watch`（含 `/api/watch/start` 用例 `:251`）、`test_archive_capture_service`、`test_monitor_only`、`test_monitor_source_safety`、`test_live_layout_browser`、`test_watch_plan_browser`、`test_folder_context`。
- 新增：给 `prepare_live` 注入 30 秒延迟，断言 `/api/watch/start` 1 秒内返回 `initializing=true`，浏览器对话框关闭并进入 `FramekeepLayout.isMonitoring()`；重复开始同一目录 generation 与 arrivals 不变；前端超时而后端随后完成时界面仍切换；预置 N 张已入库照片时提示显示已有张数。
- 现场：选择该 UNC 目录，点一次 2 秒内进入监控布局；`.shiying` 提交时 `event_id` 不再因全量扫描跳动。

## 问题 2：局域网同步页面看不到局域网内其他客户端

### 发现机制
- UDP 48781，组播组 `239.255.87.81`（`选片助手/lan_capture_sync.py:22-23`）。
- 只有开启同步（`enabled=true`）才启动监听（`:64-67、120、129-139`）：TCP 同步服务绑定 `0.0.0.0:随机端口`（`:130`）；UDP 绑定 `('',48781)`，`IP_ADD_MEMBERSHIP` 的接口参数为 `0.0.0.0`（`:134-135`）。
- `_listen` 收到 `framekeep.capture.probe` 就单播回复（`:154-157`），只过滤非私网来源，不校验密码、项目或角色；两台都是 host 也能互见。
- `discover(timeout=1)`（`:161-187`）：对 `getaddrinfo(gethostname())` 得到的各接口设 `IP_MULTICAST_IF` 发组播；再用未绑定接口的 socket 发 `255.255.255.255` 和 `127.0.0.1`（`:174-176`）；只等 1 秒、只发一次；不发子网定向广播。
- `connect_peer` 只能连接 `self.peers` 中 120 秒内发现过的设备（`:220-221`），没有手动 IP 入口。
- 前端 `演示方案/lan-capture-sync.js:76-104` 每约 8 秒 POST `/api/lan-sync/discover`，结果为空只显示“未发现客户端”（`:103`）。
- 仓库没有任何防火墙规则代码；本机也没有 `framekeep-engine.exe` 的防火墙规则（本机三个配置文件防火墙均关闭，网络为“专用”）。

### 根因
1. **【已证实，直接原因】192.168.0.181 上没有程序监听 UDP 48781。** 向 `192.168.0.181:48781` 单播探测收到 `WinError 10054`（ICMP 端口不可达）；防火墙拦截通常表现为超时，不会回这个错误。能访问 SMB 只说明 445 端口互通。可能情况（需在对方机器确认）：未开启局域网同步或未设置密码（最可能）、版本过旧、引擎未运行、端口绑定失败（对方页面会显示 `discovery_error`）。本机发现功能正常：本机监听 `0.0.0.0:48781`，组播已加入“以太网”，从 192.168.0.24 发出的探测都收到“办公桌”的回复。
2. **【已证实，代码缺陷】多网卡时 `255.255.255.255` 走错网卡。** `Find-NetRoute 255.255.255.255` 指向 `vnt-tun 192.168.111.9`；未绑定接口发出的广播只走 VNT 虚拟网卡，到不了 192.168.0.0/24（`:174-175`）。这次靠组播兜住，但路由器/AP 过滤组播或开启 IGMP snooping 时会失败。
3. **【高度可能，代码缺陷】组播只加入一块网卡。** `:135` 用 `0.0.0.0`，Windows 只在默认网卡加入组播；对方若有 TUN/虚拟网卡，可能加入到虚拟网卡上，收不到局域网探测。
4. **【待验证】对方防火墙。** 程序与安装器都不添加入站规则，TCP 同步端口每次随机（本次 20468），无法按端口放行；对方网络为“公用”或首次弹窗点过“取消”时，发现成功后联机仍会失败。
5. **【体验缺陷】** 列表为空时没有原因提示，也不能手动输入 IP。

### 修复方法
- `选片助手/lan_capture_sync.py`：
  - 新增 `_interfaces()`：用 `iphlpapi.GetAdaptersAddresses`（ctypes）获取各 IPv4 地址和掩码，过滤规则与 `local_ip` 一致，排除 loopback 与 169.254。
  - `_start`：对每个接口分别 `IP_ADD_MEMBERSHIP(GROUP, iface)`，单个失败跳过；TCP 同步服务改为固定端口（如 48782），被占用时回退 0；`state()` 返回 `sync_port`、已加入组播的接口与各接口错误。
  - `discover`：每个接口建一个绑定 `(addr,0)`、开启 `SO_BROADCAST` 的 socket，分别发子网定向广播（`addr | ~mask`，如 192.168.0.255）、绑定接口后的 255.255.255.255 和组播；用 `selectors` 同时收回复；每 300ms 重发，总时长约 1.5 秒；对已保存的手动地址额外单播。
  - 新增 `probe_address(text)`：解析 `IP[:端口]`，须通过 `local_ip`；先请求 TCP `GET /sync/hello`，失败再 UDP 单播；成功后写入 `self.peers` 并持久化到 `config['manual_peers']`，`connect_peer` 无需改动。
  - `SyncHandler.do_GET`：增加免鉴权 `/sync/hello`，只返回 `device/name/port/receiving`，不含密钥与盐值。
- `选片助手/server.py:700-706`：新增 `POST /api/lan-sync/probe`。
- `演示方案/lan-capture-sync.js`：增加“按 IP 添加”输入框；空列表提示改为“未发现客户端：请确认对方已开启局域网同步并设置密码、处于同一网段；也可输入对方 IP 直接添加”。
- 防火墙：在安装器或首次开启同步的提权环节为 `framekeep-engine.exe` 添加入站允许规则（Private/Domain，`RemoteAddress LocalSubnet`）。当前安装脚本里没有提权挂载点，需先确定位置；引擎不自行提权，只在 `state()` 提示“网络为公用/无防火墙规则”。

### 用户侧临时规避

## 问题 3：自动备份提示无权限，一直卡在“等待写入元数据”

### 现象与现场数据
备份每约 5 秒跑完一轮，状态为 `complete`。只复制了 15 个 `.shiying/*` 文件，108 张照片一张未复制。`issues`、`error`、`reason` 均为空，`attempts=0`；备份模块不写日志，`engine.log` 无相关记录。

### 根因
1. **【已证实】0 星、无款号照片被永久计入 waiting，且永远不会被复制。**
   - `选片助手/automatic_backup.py:394`：只有 `write_state` 为 `verified/sku_verified` 才进入 `verified`；`:420-423` 其余照片、RAW、视频一律 `waiting += 1; continue`。不在记录里的文件也算 waiting。
   - 这些照片到不了 verified：扫描时只带相机星级、无完整元数据的照片标为 `write_state='unknown'`（`archive_capture_service.py:915`）；补写入口 `write_metadata` 对 `sku` 为空的记录只计 `unassigned` 就跳过（`archive_capture_service.py:2202-2203`），不建任务。
   - 现场：`portable-capture/9fbde5ae…sqlite3` 108 条记录全部是 `unknown / rating 0 / sku 空`，`tasks` 为空；`automatic-backup.sqlite3` 中 `folder_jobs` 为 `complete, waiting=108`，`verified_files` 为空。
   - 与问题 1 叠加：覆盖层卡住导致用户无法标星和解析款号，照片也就永远不会进入可备份状态。
   - `test_automatic_backup.py:106-118` 把“未确认照片不复制”当作预期断言。
   - 统计口径不一致：`_dataset`（`:367`）按“有效任务 + 有款号未验证”统计 waiting，随后 `_files`（`:472/:477`）按“所有未 verified 媒体”覆盖。
2. **【已证实】“现场随行元数据尚未就绪”的触发条件**（`:355-358`）：`writer.capture_service` 不存在（服务启动中）；`_source_dataset` 找不到数据集（`:284-292`）；源根目录没有 `.shiying/dataset.json`。`dataset.json` 只在现场监控取得编辑权时由 `Dataset.acquire` 创建（`portable_capture_store.py:251`），所以“开始监控”没真正成功（问题 4）、监控上级目录（根目录本身无 `dataset.json`）、UNC 短暂不可访问时都会触发。当前不在触发状态。
3. **【已证实】前端状态文案掩盖错误。**
   - HEAD 版 `演示方案/automatic-backup.js:35` 的优先级是 已暂停 → 正在同步 → `retrying` → `waiting`。`retrying` 只统计带 `reason` 的队列（`automatic_backup.py:629`），而 `:57、:67、:645` 的错误只写 `self.error`，结果 `retrying=0, waiting=108`，标题仍显示“等待元数据写入”。
   - 安装版是 `3d24fbd` 旧前端：`:32` 的 `if(state.error&&!issues.length)message(state.error)` 没有清除分支，出现过一次错误后提示一直残留，直到输入或重新加载页面。这能解释“issues 为空却总看到权限提示”。HEAD 的 `8c5031b` 已修复，但未发布。
4. **【高度可能】权限类错误的来源**（WinError 5/32/33 都映射为 `PermissionError`，`process_one` 直接用 `str(exc)`，`:590-594`，界面显示 Windows 原文）：
   - 目标标记文件：`:553` 每轮 `atomic_write(marker)` 用 `os.replace` 覆盖 `E:\aaa\2026-11-19\.shiying-backup.json`（`file_safety.py:29-40`），杀毒、索引或资源管理器预览打开时会间歇 WinError 5。
   - 目标写入锁：`:498-499` `WriteOwnership(destination).acquire()` 打开 `.shiying\write.lock`（`portable_capture_store.py:102-123`）；共享冲突提示“此数据集正在由其它客户端编辑”，`check()` 失败提示“数据集写入连接已失效，等待自动重新取得编辑权限”（`:144-153`）。
   - 已证实副作用：每轮取锁都新建 `owner-<session>.json` 且从不删除，`E:\aaa\2026-11-19\.shiying` 已有 105 个。`_run`（`:642`）用 `touch(changed=False)` 把已完成任务重新入队，每个间隔都完整遍历 UNC、取锁、写 owner、替换标记文件，冲突概率随之放大。
5. **【高度可能】“立即同步”会为 0 星照片去抢 UNC 源目录编辑权。** `retry()`（`:609`）设置 `metadata_request`；`_prepare_metadata`（`:306`）要求“所有记录都已 verified”才跳过，108 条 `unknown` 不满足，于是进入 `capture.write_metadata`（`:336`）→ `_acquire_editor` → `dataset.ensure_ownership()`（`archive_capture_service.py:237、261`），在 UNC 上 `FlushFileBuffers` 或重开 `write.lock`。失败时 `metadata_request` 不清除（`:579-583`），后续每轮都先失败，走不到 `_transfer`。
6. **【待验证，可能性低】写入凭证过期。** `formal.js:32` 只取一次 `request_token`，引擎单独重启后所有 POST 返回 403（`server.py:681`）。本次两进程同时启动，可能性低。

### 修复方法
1. `automatic_backup.py _files`（`:391-440`）：改用 `ready(record)`。满足以下任一条件的照片按原样备份：`write_state` 为 `verified/sku_verified`；或 `sku` 与 `decision_id` 均为空、无有效任务、`metadata_relation` 有值、`metadata_import_pending` 为假、无冲突，且记录 `signature` 与当前 `(st_size, st_mtime_ns)` 一致。这类照片计入新的 `unassigned`，不计 waiting。有效任务集合由 `_dataset`（`:362-367`）传入；不在记录里的文件单独显示为“尚未载入”。之后标星或分配款号时，现有受管副本更新逻辑会覆盖旧副本。统一 `_dataset` 与 `_files` 的 waiting 口径。
2. `_prepare_metadata`（`:306`）：跳过条件改为“范围内没有 `sku+decision_id` 且未验证的记录、没有 failed 回执、没有未发布记录”。补写失败不阻断 `_transfer`，已就绪文件照常复制。
3. `process_one`（`:589-595`）：按 `OSError.winerror` 生成中文原因并带阶段和路径（5 →“无写入权限或文件被安全软件锁定”，32/33 →“文件被其它程序占用”）；32/33 及 `os.replace` 上的 5 按 `file_safety.metadata_retry_delay` 短间隔重试；写入 `engine.log`；`:57/:67/:645` 的 `self.error` 同时写入队列 `reason` 或单独返回 `last_error`。
4. 空轮次不写目标盘：`_transfer` 在无新复制、修订号与文件集合不变时不调用 `WriteOwnership.acquire` 和 `atomic_write(marker)`；`WriteOwnership.release`（`portable_capture_store.py:156`）删除本会话 owner 文件（或备份端复用固定 session），并清理历史遗留 owner 文件。
5. `演示方案/automatic-backup.js:35`：`state.error || issues.length` 优先于 waiting，显示“同步失败，等待自动重试”；waiting 文案区分“待写元数据 N 张”和“未标记已备份 N 张”。发布时一并带上 `8c5031b`。
6. `_dataset`（`:357-358`）：异常拆分为“服务未启动”“目录离线”“监控未取得编辑权”；监控上级目录时按子数据集分别处理。

### 用户侧临时规避

- 少点“立即同步／重试”，避免为 0 星照片抢 UNC 编辑权。

- **S4【中，高度可能】安装集成用 PowerShell 获取系统文件夹，30 秒超时会跳过旧启动项迁移。** `更新系统/installation.py:229-238` 每次引擎启动（`update_client.py:49-60`）都启动 PowerShell，`installation-integration-error.json` 记录了 30 秒超时；`register()` 先建快捷方式（`:307`）再迁移 Run 值（`:316-318`）。安装目录仍有 `末帧选片.exe` 1.0.0，Run 值若仍指向它，登录时会启动旧版本，且“不启动”无法删除该值（`desktop_preferences.rs:39-41`）。本机 Run 值已指向新 exe，暂不受影响；错误文件成功后不清除。修复：用 `SHGetKnownFolderPath` 或注册表 `User Shell Folders` 替代 PowerShell；Run 迁移提前；成功后删除错误文件；“不启动”一律删除 `Framekeep` 值。
- **S5【低，高度可能】退出前“仍有任务”确认在引擎繁忙时被跳过。** `/api/health` 需要 `STORE.connect` 计数（`server.py:600`），桌面端读超时 2 秒（`main.rs:253-258`），超时后 `finish_close`（`:552-561`）直接退出。修复：`/api/health` 只读内存状态；Err 时按繁忙处理并照常确认。

### 跨页面：日志中大量 WinError 10053 traceback
`server.py:273 reply()` 只包住 `wfile.write`（`:274-276`），`end_headers/flush_headers` 抛出的 `ConnectionAbortedError` 未捕获，`socketserver` 打印完整栈（日志共 28 次）。修复：重写 `handle_error`，或把整个 `reply` 包进 try，对 `BrokenPipeError/ConnectionResetError/ConnectionAbortedError` 静默处理；同时减少 F2 的无效轮询。

## 联合验收标准
1. 选择 UNC 监控目录，点一次“开始监控”，2 秒内关闭对话框并进入监控布局，提示显示已有张数。
2. 连续拍摄 CR3+JPG，每张拍完覆盖层释放，可立即标星、鼠标遥控标星并发起 OCR。
3. 标星或未标星的照片都能被自动备份；有错误时标题显示失败原因（中文）和重试倒计时；空轮次不新增 owner 文件。
4. 两台开启局域网同步的电脑互相可见；可通过手动 IP 添加。
5. 替换数据库有二次确认并自动生成替换前备份。
6. 参考目录 `monitor_error` 清空，设置页不再持续轮询。
7. 结束引擎进程后仍能在 5 秒内退出桌面程序。
8. 修复发布后，旧版客户端实际发现并下载新版本（最小更新包，`public/latest.json` 已激活）。
