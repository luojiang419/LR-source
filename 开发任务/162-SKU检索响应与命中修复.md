## 已确认原因

- 任务 159 的 RAM 镜像在 `25983e8` 被移除，当前源码为磁盘索引。不能继续引用旧百轮同词缓存测试作为现版性能结论。
- 90ms 预算中断后前端从头再发同一查询，宽词重复执行相同工作可能无法完成。
- 快速结果还同步调用 `cached_preview_hints`，回查主库配对成员及预览缓存，额外等待未计入 query elapsed。
- 主资产页面仅部分数字编号进入快捷索引，输入另有 240ms 防抖。分屏原已复用 quick 路由，但未处理 indexing/pending，准备阶段会显示零结果。

## 验收

- SKU、文件名和路径在不同入口结果一致，保留范围、配对、排序、分页和取消。
- 新词首查、短词、无匹配及连续换词均能结束，不能无限重发预算中断。
- 查询不等待主库缩略图补充，不读原片或调用模型。
- 使用真实索引与真实 HTTP、浏览器验证，分别记录首次输入与同词缓存表现。
- 保留已有任务 036、143、SDK 和错误目录改动。今日同步标记已存在，只作本地提交。

## 实现

- `选片助手/quick_file_index.py` 后台预热独立 SQLite 到 RAM，之后逐批同步素材、OCR 和范围。查询、增量发布和结果代次由同一短锁保护。预热发布核对代次，内存增量失败丢弃镜像并使用已提交的磁盘索引。保留原有持久 dirty 队列及源值复核。
- 当前真实索引 534894 条、687153152 字节，额外 RAM 约 0.7GB。第一次只读备份观察到 25.58 秒；OS 文件缓存热态预热为 0.662 秒。未清空系统文件缓存，不能称物理冷启动基准。预热期间磁盘查询仍可使用。
- 取消 90ms 中断后从头自动循环的机制，极端查询使用 2 秒保护预算并明确结束为可手动重试的错误；正常响应依靠独立 RAM 查询及移除同步主库访问。不是仅靠延长预算获得实测速度。
- 普通 ASCII 款号、字母前缀、文件名输入复用快速检索；自然语言、维度、语义搜索继续原有规则。数字片段可包含匹配 SKU，精确、前缀仍优先，输入两端空格统一去除。
- `选片助手/asset_intelligence.py` 的快速返回不调用 `cached_preview_hints`，缩略图独立加载。`演示方案/asset-retrieval.js` 输入等待统一为 30ms，换词立即取消旧查询及旧卡片、详情图片连接。
- `演示方案/split-capture.js` 换查询取消旧网格图片连接，索引准备期间显示等待并自动续查，避免将准备状态误报为零结果。
