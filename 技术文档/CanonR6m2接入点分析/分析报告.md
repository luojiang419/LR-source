# R6 Mark II 默认相机接入点：分析结论

日期：2026-10-22。机身 **Canon EOS R6m2 / 1.7.0 已通过 USB SDK 和实机 CCAPI 独立读出**。

后续部署更新：REA 已升级到 6.7.0，Codex MCP 已注册并在当前聊天直接调用验证通过，详见[部署记录](../REA部署验证/部署记录.md)。下文关于 MCP 未注册的描述保留为首轮分析时的环境记录；原生反编译引擎仍未配置。

最新私有配置进展：USB 再测已成功取得并离线解码 SET0；它已经是 `MICRO_AP_AUTO` + `PTP_PC/EOS Utility`。不能将保存配置的模式字段直接当作新增设备向导的全局默认值。本文早期“尚无 CCAPI 地址/未激活/内部实现未追踪”等内容为各阶段历史；以本段及“私有 SDK 实机复测与 NIF 解码”节为当前结果。

## 目前能够确定的结论

**实机现象已经确认，默认入口尚未修改，没有可验证的固件补丁。** 用户照片明确显示从 EOS Utility 的“添加要连接的设备”进入后，先尝试连接外部 AP；用户进一步确认已经完整配对并保存相机接入点连接，之后仍优先外部 Wi-Fi。因此，不再将“先完成一次 AP 配对”作为该默认入口问题的修复。

当前官方手册适用于 1.7.0 或更高版本，其新增设备流程描述为先显示相机 SSID/密码、按 INFO 才改用外部接入点；照片已证明不能据此断言用户机身也会如此。尚未知是隐藏设置、持久网络复用规则还是代码中的固定条件决定这一选择。

相机接入点和加入外部路由器都使用 Wi-Fi；本任务要改变的是相机作为 AP 或作为客户端的默认选择。开机自动启动热点又是另一个行为，本次未验证。

## 已完成的机身核对与可用连接路径

1. 入口与 INFO 文字已通过照片核对：相机在新增设备时显示外部 AP 的连接中页面，INFO 标为“切换网络”。这与[官方连接说明](https://cam.start.canon/zh/C012/manual/html/UG-07_Network_0050.html)的示例不同。[手册适用版本](https://cam.start.canon/zh/C012/manual/html/index.html)已核对为 1.7.0 起。
2. 如果实际处在“选择网络”页，可使用“相机接入点模式 → 轻松连接 → 确定”，电脑加入相机网络，再完成配对。见[基本通信设置](https://cam.start.canon/zh/C012/manual/html/UG-07_Network_0090.html)。这是可用连接路径，不代表已经修改默认入口。
3. 官方确认会保存历史记录，见[重新连接](https://cam.start.canon/zh/C012/manual/html/UG-07_Network_0100.html)。但用户已确认保存 AP 配对后，新建设备仍先尝试外部 AP。直接选择保存的设备记录与改变新建设备默认分支是两个验收项，不能混同。

## 已取得固件后的技术缺口

固件来源为[佳能官方 1.7.0 页面](https://asia.canon/en/support/0401144702)导出的下载地址 `https://gdlp01.c-wss.com/gds/7/0400011447/01/eosr62-v170-win.zip`。ZIP 共 79,450,092 字节，FIR 共 76,866,784 字节。FIR SHA-256 为 `764cb4734ef204d8a6578a7351909263f322d0641acd8fe6bb9960b2016fc0d7`，文件在 `.runtime/canon-r6m2-analysis/R6217000.FIR`。

普通本地检查发现偏移 0x10 含版本文本；4 个 64 KiB 样本的熵约 7.997 bit/byte。指定的 EOS Utility/SSID 等 ASCII 字面串未命中。**这些结果不能区分压缩和加密，不能证明菜单功能不存在，也不能确定解码算法。**

REA 的固件区域检查工具当前报告 provider_missing，要求受支持的 Linux/Binwalk/Unblob 环境。现有 Windows 环境完成了 ZIP 目录核验，但尚未恢复 FIR 载荷为可分析代码；因此没有定位到机身菜单状态、网络优先设置或 INFO 处理函数。缺少反编译引擎和缺少固件解码是不同问题，不能把安装 Ghidra 等同于解决固件封装。

目标应保持为：保留外部 AP 的可选能力，同时让 EOS Utility 新建设备先建立相机 AP，只有用户切换网络时才进入外部 AP 流程。仅删除保存网络、重置通信设置或提供电脑自动连接脚本，都不能作为该目标的验收结果。

## FIRv6 深入解析与开发验证（2026-10-22）

已使用[原作者的 FIR 工具](https://github.com/lclevy/d8_oracle)解析该固件，开发了同目录 `inspect_fir_v6.py` 独立检查器。上游 commit、文档和脚本哈希见 `研究来源与版本.json`；实际结果见 `fir-v6-validation.json`。这些是普通离线代码检查结果，不冒充 REA 反编译证据。

已确认模型 ID `0x80000481`；updater 密文起点 `0x120`，主固件密文起点 `0x4db1c0`。区域边界、声明大小和普通校验和一致。基于 DIGIC X 公开验证密钥的两组 ECDSA/secp256r1 + SHA-256 校验均通过，与原作者工具结果一致。头部中存在分别对应两段密文的 IV；结合公开研究，可明确这是 FIRv6 的加密更新结构，而不再仅凭熵猜测压缩或加密。尚未得到该机型解密密钥、解密代码或明文。

已执行五项反例检查，均符合预期：

- 在内存中修改头部的一个字节并修复普通校验和，头部/updater 签名失败，载荷签名仍通过。
- 在内存中修改载荷的一个字节并修复普通校验和，载荷签名失败，头部/updater 签名仍通过。
- 非法区域数量、越界区域和非法签名长度均被拒绝。

反例没有生成修改后的 FIR，原始文件哈希未变。上述结果证明普通校验和不足以维持修改包的有效签名；它们没有模拟机身加载器，也不构成签名绕过。解密成功和修改包能够加载是两个独立验收项。

[原作者演讲](https://pretalx.com/hack-lu-2025/talk/3UEDY8/)和源码表明，公开的 `d8_oracle.py` 需要 EOS R/RP 自有 ROM 来解 DIGIC 8/FIRv5；其中的 `d810_verif.py` 支持 DIGIC 10 签名验证，但不负责解密。不能把 DIGIC 8 解密器直接用于 R6m2，也未找到 R6m2 1.7.0 可验证的 CBasic ROM 导出流程。已有 R5/R6 的脚本和地址不能直接当作 R6m2 的可执行载荷。

### CCAPI 配置路径的进展

已取得 Canon CameraControlAPI Reference Ver.1.1.0 Rev.1.3 的历史副本，并核对第 84、107、114–119 页。它确实定义了 `/functions/wifisetting/set1` 等接口，网络方法有 `cameraap` 与 `infrastructure`，所以不能笼统地说 CCAPI 没有接入点设置能力。

但该旧文档的连接切换仅作用于 CCAPI 启动的设置；功能 MODE 的写入只允许 CCAPI，不能因为 GET 枚举里有 `eos_utility` 就断言可以切换或修改 EOS Utility。旧 Wi-Fi 设置对象没有默认模式、优先级或 INFO 事件字段。参考版本较旧，仍需以用户 1.7.0 机身公布的 API Table 和实际 GET 响应确认最新能力。

已开发 `read_ccapi_network.py`：只向用户明确给定的相机地址发送 GET，读取 API Table 和其中明确公布的相关网络接口；不扫描局域网、不执行 PUT/POST/DELETE，输出会遮盖密码和序列号。`test_ccapi_reader.py` 已使用本地模拟 HTTP 服务验证只读请求边界、拒绝表中的外部 URL/查询路径，以及输出脱敏。**这是工具验证，不是相机功能验证。**

当前尚无相机 CCAPI 地址，EOS 进程也没有可据以识别相机的已建立 TCP 连接，未向任何未知局域网主机探测。已请求用户提供 CCAPI 菜单状态或屏幕地址；在取得真实 API 能力之前，不写入猜测的网络参数。

用户随后确认菜单没有 CCAPI 选项。根据[佳能操作指南](https://downloads.canon.com/sdk/CameraControlAPI_OperationGuide_EN.pdf)第 4–5 页，需先用官方 CCAPI Activation Tool 通过 USB 激活；[官方 CCAPI 标准文件清单](https://www.canon.com.cn/supports/sdk/icp/template/CCAPIStandard.pdf)也将该工具列在 CCAPI 包内。已核对现有 EDSDK 包未包含该工具，没有从不明来源安装或执行激活程序。官方国内申请入口为[SDK 开发包申请](https://www.canon.com.cn/supports/sdk/icp/form.html)，尚未代填或提交申请。

本轮实际再次运行 USB 身份读取工具，EDSDK 返回 `camera_count=0`，记录在 `camera-identity-after-research.json`；这表示当前 SDK 没有可枚举相机，不能把先前的“端口占用”继续当作当前原因。已请求用户重新连接相机并提供 CCAPI 包或激活工具本地路径。下一步需先完成受支持的 CCAPI 激活，再读机身能力；尚不保证启用 CCAPI 就能改变 EOS Utility 的默认入口。

```powershell
python '技术文档\CanonR6m2接入点分析\inspect_fir_v6.py' '.runtime\canon-r6m2-analysis\R6217000.FIR' --output '技术文档\CanonR6m2接入点分析\fir-v6-validation.json' --negative-controls
python '技术文档\CanonR6m2接入点分析\read_ccapi_network.py' 'http://相机地址:端口' --output '.runtime\canon-r6m2-analysis\ccapi-network-readback.json'
```

[Wi-Fi 设置文档](https://cam.start.canon/zh/C012/manual/html/UG-07_Network_0130.html)没有列出“默认接入点模式/交换 INFO”的选项。[1.7.0 更新说明](https://asia.canon/en/support/0401144702)也未明确承诺调换该顺序；机身已是此版本，不能把升级当作已证实修复。

## 实机 CCAPI HTTPS 能力核验（2026-10-22）

用户提供重启后的机身照片，显示“正在等待连接”及 `https://192.168.1.2:443/ccapi`；相机确有 CCAPI 工作界面。电脑 WLAN 已连接相机热点，路由直达相机。首次普通 HTTPS 请求因本地不信任机身签发证书而失败；证书 subject 为该 IP，issuer 为 Canon Digital Camera，SAN 包含 192.168.1.2，有效期 2026-10-22 至 2027-10-22。

读取器新增显式 `--tls-cert` 与 `--tls-cert-sha256` 参数：调用者指定单张相机 PEM，先核验 DER SHA-256，再创建独立 SSLContext，将其作为该次连接的信任锚。证书/IP/有效期校验仍开启，没有更改系统证书库或相机 HTTPS 设置。信任依据为用户照片给出的目标地址和当前直连相机热点，是局部首次信任，不等同于独立的佳能制造商身份认证。证书指纹为 `f6c8cfdd4006c0029f33e01f7b95c3c8216d61a87ad854c8c0f703d4e06b0b4c`，公开元数据见 `ccapi-certificate-metadata.json`；PEM 仅保存在 `.runtime`。

实际 GET 根 API 表及其公布的 5 个白名单接口均成功；`deviceinformation` 返回 Canon EOS R6m2 / 1.7.0。API 表为 ver100 83 项、ver110 28 项、ver120 1 项，总计 112 项。完整脱敏结果见 `ccapi-network-readback.json`，汇总与照片哈希见 `ccapi-live-capability-summary.json`。密码、序列号、GUID、MAC 地址脱敏。

网络相关公布能力只有 `/ccapi/ver110/functions/wifisetting`、三个 `set1..set3` 以及 POST `/ccapi/ver100/functions/wificonnection`。本机没有公布 `networkfunctionmode`、`networksetting/currentconnectionsetting`、连接设置管理、EOS Utility 默认模式或 INFO 映射接口。已取得的 Canon 原始 API Reference v1.1.0 Rev.1.3 第 111 页定义 `wificonnection` 为断开连接并退出 CCAPI，仅有 action=disconnect，不能将它推断成切换到 EOS Utility/AP 的接口。新版 SDK 支持更多机型，并不自动给本机 API 表增加能力；[佳能发布记录](https://asia.canon/en/campaign/developerresources/camera/cap/camera-control-api-release-note)中的通用“Connection settings”新功能也不能代替本机公布能力。

三个 Wi-Fi 槽的 GET 返回 SSID、method、信道、IP 等均为空。此观察不证明相机 GUI 配置的存储结构，也不证明三组槽能影响 EOS Utility 向导；首次连接确认状态等条件尚未排除。因此没有为了尝试而写入这些槽，也没有删除或切换现有网络。当前阶段全部网络请求为 GET。

验证新增了隔离的本地 HTTPS 模拟机：正确指定的证书可读；错误指纹在 HTTP 前被拒绝；未指定信任和主机名不匹配均失败。原有 GET 白名单/凭据脱敏测试保持通过，共 2 项测试。此次实机成功读取是额外的真实集成证据，模拟测试不冒充实机。

结论仅限当前公开接口：CCAPI 激活和相机热点连接已打通，但没有发现能实现用户原始菜单修改的受支持控制项。未实现“默认 AP、INFO 才选外部 Wi-Fi”，不能将启用 CCAPI 当作修复交付。后续固件路线仍受 FIRv6 解密、签名加载与恢复条件限制。

## 私有 SDK 实机复测与 NIF 解码（2026-10-22）

### 再次测试的实际结果

本机佳能 EOS Network Setting Tool 的实际调用方对界面 SET 编号减1，因此 SET1 应传入 `setNumber=0`。此前两次传入1返回 `0x60/INVALID_PARAMETER`，不是整个私有接口不支持。重新按0读取后 `EdsGetWftData` 成功，返回1336字节，SHA256 为 `60224a81eb378750b858d18cbaa2e25b75450f9bd4f95e9c2c1b95b52e2e12d6`。机身身份仍为 Canon EOS R6m2 / 1.7.0，随后 SDK 会话正常关闭、释放。

原始记录仅在 `.runtime/canon-r6m2-analysis/wft-private-zero-based-set1/wft-private.bin`，可能含网络凭据和配对数据，不提交。已提交的 `wft-read-index0.json` 仅保存调用结果、长度及哈希。

实际使用了 `EdsSetPropertyData(camera, 0x01000000, 0x22E1, 4, 0xC53)` 完成本地 SDK 注册。这不是机身网络属性写入：在精确匹配哈希的 SDK 中，静态路径最终到 `0x180007850`，此参数分支仅将本地相机对象的 `+0x388` 标志置1，不发送 PTP；对象销毁后结束。常量和调用也在佳能 NESDK 的 `EOSCamera.connect` 中确认。未调用其他属性写入、WFT Set/Change/Delete、拍摄或固件命令。

注册后0x5B NetInfo（808B）、0x5C ActInfo（408B）可读，0x5A NetworkSetInfo 返回 `0x07/NOT_SUPPORTED`。NetInfo 的 mode2 表示内置无线，不是AP模式；ActInfo 的 mode1 表示EOS Utility角色，二者不能混用。0x01000023/D175是通信功能角色，也不是AP/客户端选择器，未对它写入。

### 解码依据与保存模式

`EdsNIFParse.dll` SHA256 `6d0ab49b647e661ca887e0c41c40ea2b03cc0e8243387d9913c82d65babf4ea0` 的静态汇编确认：`0x180008400` 从 HEAD 取 `ofcn/ofcy`；`0x180008240` 跳过 DATA 的12字节头，对 payload 使用8字节周期 XOR，key 为 `ofcy XOR 0xADB6B4B0CFCDCFCC`，尾部按低位字节处理。未执行该 DLL。原生部分来自固定哈希文件的 Capstone/objdump 静态摘录；托管调用和枚举有 REA 证据，见 `nif-native-xor-evidence.json`、`nif-managed-method-evidence.json` 与 `rea-sdk-network-paths.json`，不将普通静态摘录冒称为 REA 反编译。

外层为 HEAD（payload120B）与 DATA（payload1192B）。解码后是完整 NSET，内嵌一个 NWST 和一个 ACTS。以下偏移均相对整个原始1336B文件：

| 字段 | header / value 偏移 | 实际值及意义 |
| --- | --- | --- |
| NWST/WSET.ctyp | 0x15C / 0x168 | 2 = MICRO_AP_AUTO，相机自动接入点 |
| ACTS.mode | 0x464 / 0x470 | 1 = PTP_PC / EOS Utility |
| NSET.nwnm / acnm | 0xD8 / 0xE8（header） | 各1，分别是内嵌NWST/ACTS数量，不是全局记录编号 |

**这次读到的SET0已经保存相机AP，仍没有证据证明它控制“添加设备”的初始网络选择。** 因而不将ctyp同值写回当作解决方案，也不全局替换 mode2。尚未知该向导是否读取另一份持久状态、复用最近外部网络，或由固件固定分支决定。

`decode_nif_profile_readonly.py` 验证 HEAD/DATA 外层边界、重复/缺失字段，只有输入哈希匹配本次实机样本才解释已核实的偏移，其他样本仅验证外层和变换。已对原始文件执行解码再还原，全部1336B与原文件一致、SHA相同。2项离线测试通过，覆盖8种尾部余数、未混淆格式、越界、截断、重复/缺失字段及报告脱敏。脚本不输出或落盘明文、种子或XOR key。

限制：NWST/IPV4/IPV6 的声明长度与实存边界分别有48/12/36B差异，未完成通用内层序列化兼容。未重算 `chsm`，XOR两次完全一致仅证明变换可逆；它不证明新配置有效、机身可回写或可恢复。佳能托管 SetWftData 入口提交完整byte[]，没有字段级setter；尚未验证机身对完整blob的合并/替换范围，因此未写回。

## 如果确认实机仍需修改固件

以下是定位路线，不是已找到的补丁：

1. **固定复现条件。** 已有入口照片和保存后仍优先外部 Wi-Fi 的用户确认；后续比较时沿用该条件，不删除现有网络设置。
2. **恢复匹配的固件代码。** 官方 FIR 已取得并保留哈希；下一步是识别和解析内部载荷，确认真实代码布局，而非重复下载或把 SDK DLL 当作机身代码。
3. **恢复菜单与事件路径。** 在可分析的代码中以 EOS Utility、SSID/密码页、选择网络页等资源为入口，追踪连接向导的初始状态、INFO 事件处理、历史配置读取和 AP/客户端启动调用。先确认是否只是某个持久设置决定默认分支，再考虑改控制流。
4. **限定修改范围。** 若代码证明有必要，只调整 EOS Utility 新建连接的初始分支及相应 INFO 切换行为，并保持页面提示一致；不要全局替换网络模式常量，以免改变 FTP、手机连接或已保存连接。
5. **验证可加载性和恢复方式。** 必须先弄清该固件的封装、校验/签名、加载条件及恢复路径。不能假设修改文件、重算 CRC 就能被相机接受。当前没有验证这些机制，也没有相机端补丁地址、原始指令或修改字节。
