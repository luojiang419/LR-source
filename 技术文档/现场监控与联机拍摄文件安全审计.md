# 现场监控与联机拍摄文件安全审计

## 结论与事故边界

2026-10-22 用户报告：客户机使用最近一次推送版本，现场监控目录中的小 JPG 彻底消失。本地最近发布记录为 `e94060f / 20261022111607`。尚未拿到客户机目录绝对路径、消失文件的完整名称、删除事件或进程记录，因此不能宣布已定位事故根因、已恢复照片或彻底排除第三方传输/清理。

代码中没有发现现场监控启动、停止、切换或 Canon 接入直接递归清空所选照片目录。末帧的 Canon 接入接收文件路径，照片传输由 EOS Utility 执行，没有下载后删除照片或调用相机删除接口。仅选择目录不写原图；主动标星和 SKU 备案会写元数据。

## 已复现并修复的风险

| 风险 | 触发条件及影响 | 本轮处理 |
| --- | --- | --- |
| 已发布版缓存误认文件 | 缓存目录内存在64位十六进制名称的 JPG；超过容量时可删掉未生成的文件。旧同名 `.tmp` 超过6小时也会被删 | 上轮已取消按名字接管，本轮进一步取消无内容哈希的旧索引接管 |
| 旧索引错误认领外部替换文件 | 旧索引有生成参数但无哈希，启动时给当前文件补哈希，随后淘汰会删除后来放入的文件 | 缺少原始内容凭据时只撤销索引，保留文件；新缓存键 v4 避免升级后被旧文件阻挡 |
| 缓存发布检查后发生同名写入 | 检查目标不存在后，其他程序写入同名文件；原 `replace` 会覆盖它 | 原子禁止覆盖提交，目标出现即报错保留 |
| 缓存删除检查后文件被替换 | 哈希检查通过后，其他进程写入/换入文件，原 `unlink` 仍按路径删除 | Windows 同一句柄内校验和删除；句柄禁止其他写入/替换，拒绝重解析点和多硬链接 |
| 配置固定临时文件冲突 | Canon `.framekeep-tmp`、监控 `folder-watch.tmp` 与已有文件碰撞 | 独占创建随机临时文件，只清理自己创建的临时文件 |
| 照片与内部资料混用 | 用户选择 `.framekeep`、资料目录或其缓存子目录作为照片目录 | 手动启动、旧监控恢复、Canon保存配置与每次监控扫描均检查；递归选择上级目录时跳过资料树 |
| 标星/SKU提交前的外部变化 | 普通 `os.replace` 可能覆盖已变化的文件 | 替换前校验 SHA-256，Windows `ReplaceFileW` 原子提交且备份参数为 `None`；新 XMP 禁止覆盖；不保留整文件恢复副本 |

上述缓存删除必须同时满足目录与命名条件。普通照片名如 `IMG_0001.JPG` 不符合缓存删除规则；“小 JPG”本身不能证明缓存清理就是事故原因。旧版复现将测试缓存上限设为0以确定触发，正式默认上限是10 GiB。复现证据在 `build/released-cache-deletion-repro.json`。

## 逐条排查的路径

- `folder_watch.py` → `media.discover/read_metadata` → `Store.append_live`：读取原图，写数据库；停止与切换不删除照片。历史索引保留，不把文件暂时离线当成删除命令。
- `canon_link.py`：权限探测仅创建独占临时文件；登记/恢复修改 Canon 用户配置及程序偏好。接收通知只校验路径和切换监控，不搬运原图。EOS 同名照片传输策略和客户机的清理工具仍需当地证据，未擅自修改未知 EOS 参数。
- `preview_cache.py`、`media_engine.preview`：唯一常规图片自动淘汰入口；已改为强归属校验和句柄保护。
- `metadata_writer.py`、`asset_archive.py`、`rating_sync.py`：主动标星/SKU 使用独占的同卷临时文件，验证图像和元数据后提交；源目录不创建工作文件夹，不保留整图恢复副本。清理只触及本次登记的临时文件。
- Rust桌面 `deliver_photos`：删除的是程序资料 `canon-link/inbox` 内的通知JSON，不删除JSON中引用的照片路径；导出Excel/评级文件属于用户明确另存。
- `FramekeepBridge.lrplugin`：读取清单并设置Lightroom评级，未发现原文件清理。
- 更新/卸载：只处理安装清单与事务日志中的程序路径，没有把监控目录传给清理函数。构建脚本的 `rmtree` 限于构建前端和旧运行库，不在监控运行链路中。

## 当前空间策略与历史遗留

任务 096 已取消 `.framekeep-recovery-随机编号/`、`original.bin` 和 `recovery.json` 的创建。此前版本的旧目录不会因升级自动消失，看到遗留目录不能据此判断当前版本仍在生成。2026-10-26 用户后续明确要求自动删除这些历史目录，即使原照片缺失或恢复信息无法确认也直接清理。现按旧目录的精确命名在已配置监控/资产归档根目录内执行本次升级的一次性后台清理；完成后保存标记，以后重启不再扫描，也不定时巡检；不进入目录链接目标，不处理普通照片或任意名称的 bin 文件。软件资料/预览缓存排除，清理记录保存在软件资料目录。

当前标星与 SKU 只持久保存小型字段历史。写入期间仍需一个同卷临时编辑文件完成像素验证与原子替换，暂存于软件资料的 `metadata-staging/`，跨卷时使用照片所在卷根目录的 `.framekeep-staging/<资料标识>/metadata-staging/`。照片目录不创建 `.framekeep-write-*` 文件或工作目录。成功及异常退出会清理本次临时文件；进程被强制终止或文件持续被占用可能在软件暂存区留下临时文件。旧 journal 中登记的临时目录继续兼容清理，不创建新目录。网络共享的真实权限、文件系统能力和相机持续传输仍需现场副本验收。

非 Windows 平台未开放本产品的按句柄删除及已有照片安全提交能力，自动缓存清理和已有照片元数据提交会保守失败；验证平台为 Windows。

## 客户机只读取证

修复包附 `Collect-PhotoSafetyEvidence.ps1`。关闭对该目录的进一步测试后，在客户机PowerShell执行（替换实际路径）：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Collect-PhotoSafetyEvidence.ps1 -PhotoFolder "D:\现场小图" -AppFolder "D:\末帧选片" -DataFolder "$env:LOCALAPPDATA\Framekeep\data" -HashPhotos
```

脚本只读目录、文件属性/可选哈希及所指定的版本和监控/联机配置；只在新建报告目录写JSON，不删除、移动、恢复照片，不读取密钥。若资料存放位置不同，应填实际位置。报告包含本地路径，交回前可检查。报告无法回溯此前谁删除了文件；如继续复现，可在照片副本上用进程级文件监视记录删除/重命名事件，结合时间和进程判定。
