## 01 · 先明确我们究竟改了什么

本项目已有两套不同成熟度的成果。后续开发首先选定路径，避免把编译成功、驱动加载、真实输入成功混为一谈。

| 路径 | 组成 | 当前实际状态 | 适合继续开发什么 |
| --- | --- | --- | --- |
| A：现在可用 | 原有签名 Interception 内核 + 重开发 Win32 控制端 + 本地网页 | 已无整机重启运行；用户确认指针不动、点击出现爱心；程序收到47次物理点击 | 点赞、主题控制、答题器、手势、粒子画笔、舞台互动 |
| B：自有内核 | HeartMouse WDM 源码 + 版本化 IOCTL + 专用客户端 | SYS/CAT 已生成，Inf2Cat与策略测试通过；NotSigned，未安装、未加载 | 更清晰的设备协议、内核租约、独立状态查询和专用产品化 |

**这次没有改写鼠标接收器固件，没有修改 Windows 的 `mouclass.sys`，也没有给修改过的二进制冒用原签名。** 当前投入使用的改造发生在设备输入过滤和用户模式控制层。

用户确认的接收器为 `VID_367B&PID_1919`。这个身份来自实际拔插，而非根据“通用 HID 鼠标”这个名称猜测。罗技 G102 和另一个 HID 鼠标没有执行设备重载。

### 建议的学习路线

先跑通当前程序和离线示例，再修改用户模式手势与页面。只有需要内核才能保证的能力，例如程序失联后仍由驱动保证恢复，才进入自有内核开发。绝大多数有意思的交互不要求每加一个功能就重新编译内核。

本文中「已验证」指本项目有实际记录；「示例」指独立演示；「扩展设计」指尚未接入产品的建议。新电脑、不同驱动版本、其他鼠标不自动继承这台电脑的验收结论。

## 02 · 整体原理与源码地图

### 两条输入路径

正常使用时，鼠标数据经 USB/HID、`mouhid` 和 `mouclass` 进入系统，最终移动指针或产生点击。

在本项目专属模式下，目标设备的连接回调把匹配的数据送入过滤队列，程序读取它们并转成应用事件；这些数据不继续交给系统指针。其他鼠标没有被本程序设置过滤。

```text
无线鼠标 → USB 接收器 → HID / mouhid
                              │
                        目标设备过滤回调
                         ┌────┴─────┐
                      普通模式    专属模式
                         │           │
                     mouclass    设备事件队列
                         │           │
                     系统指针    Win32 控制端
                                     │
                            手势/动作 → 本机 SSE
                                     │
                            页面爱心、粒子与计数
```

### 优先阅读的文件

| 文件 | 作用 | 要加功能时看什么 |
| --- | --- | --- |

| `native/mouse_transport.py` | 直接 Win32 驱动通信、白名单、24字节包 | `MousePacket`、`ioctl`、`receive` |
| `native/interception.py` | 开启/释放目标、线程收包、左键状态机 | `start`、`stop`、`_run`、`ClickRouter` |

| 目标 | 本项目所用工具 |

### 两种保护不能混淆

当前 A 路线的页面心跳约每2秒发送一次；控制页面失联超过10秒后，由用户程序释放过滤。全局恢复快捷键是 `Ctrl+Alt+F12`。正常释放、关闭句柄和程序退出路径均有相应实现。

B 路线另外增加 **5秒内核租约**。即使用户程序不再执行看门狗，内核在后续输入/状态检查中也会判断租约到期并恢复透传。它目前尚未部署，不能把这个内核保护描述成当前 A 路线已经具有的能力。

## 04 · 用拔插认准设备

### 为什么设备名不够用

“HID-compliant mouse”不等于某一只物理鼠标。键盘或多媒体接收器也可能带一个鼠标集合。同一个USB接收器还可能同时枚举键盘、鼠标、消费控制等多个接口。

先记录插入状态，再拔出目标接收器，最后插回并对比新增设备。比较完整实例ID以及父子关系，而不只看列表序号。

```powershell
Get-PnpDevice -Class Mouse -PresentOnly |
    Select-Object Status, FriendlyName, InstanceId |
    ConvertTo-Json
```

本次实测记录：

| 阶段 | 观察 |
| --- | --- |
| 原始连接 | `HID\VID_367B&PID_1919\6&328C458&0&0000` |
| 拔下后快照 | 该VID/PID不在当前设备中；另外两个鼠标仍在 |
| 重新插入 | 新鼠标 `HID\VID_367B&PID_1919\7&6A87B6E&0&0000` |
| 新接收器节点 | `USB\VID_367B&PID_1919\6&306893D8&0&3` |
| 重新接入状态 | Present=true、Status=OK、ProblemCode=0 |

**实例尾部和驱动槽号会变化。** 本次曾出现 `driver:14`、`driver:15`、`driver:16`，不得把16写死成鼠标永远的身份。

`VID/PID` 只能限制型号，不能区分两只同型号接收器。遇到同型号多个实例时，应要求用户确认，或补充实例/序列号绑定，不应自动选择第一个。

### 处理硬件修订字段

内核返回的标识可能是 `HID\VID_046D&PID_C092&REV_9000&MI_00`，Raw Input 的路径可能不带 `REV_9000`。本项目先移除 `&REV_XXXX`，再保留VID/PID、MI、COL进行比较。

`MI_XX` 是接口，`COLXX` 是集合，不能为图方便全部抹掉；否则可能把一个复合设备中的不同输入功能混为一谈。

## 05 · 使用 REA 还原真实协议

### 分析顺序

目标是解释实际交付二进制。分析对象应为本机实际安装的驱动及正在使用的控制库，而不是仅依据网上一份头文件猜测。

1. 用 `open_binary` 打开 `C:\Windows\System32\drivers\mouse.sys`。
2. 获取必要的概览及函数列表；本次使用 REA 6.5.0 / Ghidra 12.1.4。
3. 从DriverEntry找到IRP分派，再追踪Device Control分支。
4. 检查各IOCTL的输入长度、输出长度、同步/异步和完成路径。
5. 检查鼠标连接回调和关闭句柄的清理路径。
6. 导出证据，再打开随附DLL，核对getter实际发送的控制码。
7. 对比结论与运行观察，最后关闭分析会话。

示例 REA 调用参数如下；它们是工具参数，不是可以直接贴入PowerShell的命令：

```json
{"path":"C:\\Windows\\System32\\drivers\\mouse.sys"}
```

```json
{"procedure":"0x161c4"}
```

`0x161c4` 只适用于本文所分析的同一二进制；重新编译后地址和函数边界都可能改变。Ghidra的恢复函数名和伪代码不是原作者源码，也不是运行时执行证明。

### 本次关键发现

已安装的 `mouse.sys` SHA-256：

```text
0f12d47d01864ca5e1eb663a52b3d2c060521e57b68ff99d70e7f01506e400f9
```

| IOCTL | 内核中确认的用途 | 当前控制端 |
| --- | --- | --- |
| `0x222004` | 设置优先级 | 不使用 |
| `0x222010` | 设置过滤，输入uint16 | 使用 |
| `0x222040` | 注册/解除通知事件 | 使用 |
| `0x222080` | 把输入写回类驱动 | 不使用 |
| `0x222100` | 读取已拦截输入 | 使用 |
| `0x222200` | 读取硬件ID | 使用 |
| `0x222020` | DLL想调用的GET_FILTER | **该内核未实现，禁止使用** |

旧程序的错误过程是：先设置过滤，再调用DLL的 `interception_get_filter`，读到初始值0，于是主动取消过滤。更严重的是，旧内核未知IOCTL分支未正常完成IRP，因此不能继续用“试一遍看看”的方式探测未知请求。

修复依据保存在：

- `驱动分析/REA-协议与重开发.md`：解释、Evidence ID及协议表。
- `驱动分析/REA-关键证据.json`：8条核心静态证据，随Git保存。
- `artifacts/rea-mouse-driver.json`：本机完整内核分析导出。
- `artifacts/rea-driver-and-client.json`：DLL getter分析导出。

其中调度证据为 `ev_9eef150981363bf69e798652e1f65aff1e702d4a91e161870f6b89d8ea95ba73`，DLL getter证据为 `ev_85c8d1c7fbe47e8dd498464a2b8c5e99cf74a0fbfe797dde19ba6e5ab809e674`。这些证据支持此版本的结论，不自动推广到所有Interception发行版本。

## 06 · 复现当前已验证的无重启路径

### 第一步：确认当前系统状态

下面均为查询命令：

```powershell
sc.exe query mouse
sc.exe query keyboard
Get-AuthenticodeSignature "$env:SystemRoot\System32\drivers\mouse.sys" |
    Select-Object Status, SignerCertificate
Get-FileHash "$env:SystemRoot\System32\drivers\mouse.sys" -Algorithm SHA256
```

服务 `RUNNING` 只说明驱动映像已加载；它不证明目标鼠标的连接回调已接入，不证明应用打开了正确设备，更不证明指针已被隔离。

当前控制端核对已安装内核的SHA-256，不匹配就拒绝发送设备控制请求。更换驱动版本时，应重新分析协议并验证，不能只删掉哈希检查来获得“支持”。

### 第二步：理解本机热加载做了什么

本次官方安装器已放置驱动文件并写入类过滤器，但SCM最初查不到服务。保存两项服务注册表后，才对已有签名驱动进行服务注册和按需启动。

以下是**本机已执行的历史复现命令**，不是新电脑上必须无条件运行的安装脚本。只有确认官方安装已经成功、签名与文件正确、相关服务确实缺失时，才应考虑这条修复路径；已有服务不要重复创建。

```powershell
sc.exe create mouse type= kernel start= demand binPath= System32\drivers\mouse.sys DisplayName= "Mouse Upper Filter Driver"
sc.exe create keyboard type= kernel start= demand binPath= System32\drivers\keyboard.sys DisplayName= "Keyboard Upper Filter Driver"
sc.exe start mouse
sc.exe start keyboard
```

这些名字是本机已安装旧内核使用的服务名，不是给任意驱动通用的名称。当前新控制端只操作鼠标控制节点；上面的keyboard服务来自旧发行版的既有安装配置，不等于程序会过滤键盘。不要因为做鼠标功能而给新工程额外安装键盘过滤器。

需要重新枚举时，先从当前系统读取完整实例ID，再只处理已确认目标。不要复制已经变化的旧ID，更不要重启整个USB控制器、集线器或所有输入设备。

```powershell
# 把此值替换成当前枚举并由用户确认的真实实例ID。
$mouseInstance = 'HID\VID_367B&PID_1919\7&6A87B6E&0&0000'
pnputil.exe /restart-device $mouseInstance
```

不要加 `/reboot`。若系统返回确实需要重启，就报告这台环境的限制，不能通过改安全设置冒充热加载成功。物理拔插也可触发重新枚举，本次最终按插拔确认了目标身份。

### 第三步：运行控制程序

```powershell

```

或双击完整解压目录内的 `HeartRelay.exe`。如果当前服务已经运行，直接打开 `http://127.0.0.1:18765`，不要再启动第二个同端口服务。

在页面选中已确认鼠标，再开启专属点赞。重启过程序就刷新旧页面，使页面拿到新的会话令牌。程序每次启动不自动接管硬件。

修改源码调试可以使用独立端口，但不要同时让两个程序打开同一鼠标控制句柄。页面测试可以使用临时数据；设备独占测试应保证只有一个控制所有者。

## 07 · 读懂控制端，才能稳定扩展

### 原始输入包的24字节布局

直接访问内核时，读取的是WDK `MOUSE_INPUT_DATA`，不是旧DLL导出的20字节 `MouseStroke`。

```python
import ctypes as C

class MousePacket(C.Structure):
    _fields_ = [
        ('unit', C.c_ushort),
        ('flags', C.c_ushort),
        ('state', C.c_ushort),
        ('rolling', C.c_ushort),
        ('raw_buttons', C.c_uint32),
        ('x', C.c_int32),
        ('y', C.c_int32),
        ('information', C.c_uint32),
    ]

assert C.sizeof(MousePacket) == 24
assert MousePacket.state.offset == 4
assert MousePacket.x.offset == 12
```

| 字段/位 | 含义 | 使用注意 |
| --- | --- | --- |
| `state & 0x0001` | 左键按下 | 用边沿/状态机避免重复DOWN连发 |
| `state & 0x0002` | 左键松开 | 与按下成对维护状态 |
| `state & 0x0004 / 0x0008` | 右键按下/松开 | 可映射主题、撤销等 |
| `state & 0x0010 / 0x0020` | 中键按下/松开 | 不是滚轮旋转 |
| `state & 0x0040 / 0x0080` | 第四键按下/松开 | 硬件可能没有侧键 |
| `state & 0x0100 / 0x0200` | 第五键按下/松开 | 不保证每个型号都提供 |
| `state & 0x0400` | 垂直滚轮 | `rolling`需按有符号16位解释 |
| `state & 0x0800` | 水平滚轮 | 不应误当垂直滚轮 |
| `flags & 0x0001` | 绝对坐标标志 | 不能按相对位移直接累加 |
| `x / y` | 相对位移或绝对位置 | 先检查flags，再映射虚拟坐标 |

滚轮向下可能以 `65416` 这类无符号数出现，其有符号解释是 `-120`：

```python
raw = packet.rolling & 0xFFFF
delta = raw - 65536 if raw >= 32768 else raw
```

常见鼠标一格是120，但高分辨率设备可以更细，不能把每个数据包都视为完整一格。需要离散动作时积累余量，需要连续参数时按比例映射。

### 开启与释放的顺序

当前实现大致按下列顺序工作：

```text
枚举 → 用户选择 → 打开单个控制节点 → 再核对硬件ID
     → 创建通知事件 → SET_EVENT → SET_FILTER
     → 等待事件 → READ → 手势处理 → 发应用事件

停止 → SET_FILTER(0) → 解除事件 → 关闭设备句柄 → 关闭事件句柄
```

程序只向白名单IOCTL发送请求。`DeviceIoControl` 返回失败时，读取其Win32错误并进入清理路径。不能对旧内核加一个未实现的“读取状态”来自证设置成功。

所有慢工作放在内核回调之外：页面动画、音效、磁盘、网络、模型推理都由应用层完成。当前输入线程已经把点赞回调放到自身锁之外，扩展时保持这个约束。

## 08 · 把鼠标变成创意控制器

### 功能应该放在哪一层

| 想做的效果 | 首选修改位置 | 是否需要重写内核 |
| --- | --- | --- |
| 不同颜色、爱心、烟花、音效 | `web/app.js`、`style.css` | 否 |
| 左键点赞、右键换主题 | 控制端路由 + 应用事件 + 页面 | 否 |
| 双击爆发、长按蓄力 | 用户模式状态机 + 定时tick | 否 |
| 滚轮控制粒子数量或速度 | 包解释 + 参数限幅 + 页面 | 否 |
| 鼠标移动绘制粒子轨迹 | 相对坐标积分 + 舞台虚拟坐标 | 否 |
| 多人答题器/计分器 | 每设备独立会话与映射，解决同型号身份 | 通常不需要，但当前版本只支持已确认单设备 |
| 音乐控制/MIDI/OSC | 用户模式适配层与明确授权的连接 | 通常不需要，当前未实现 |
| 即使用户进程挂起也由内核到期释放 | 自有内核租约 | 是，A路线没有内核租约 |
| 在新驱动下提供完整移动/按钮流 | 新协议事件队列与READ_EVENTS | 是，目前B路线只提供计数/状态 |

### 随附可运行的离线样例

文件：`教程/示例/创意事件映射.py`。它不打开鼠标、不接管驱动、不发送系统输入，也不连接网络，可以在当前点赞服务保持运行时测试。

```powershell
python '教程/示例/创意事件映射.py'
python '教程/示例/创意事件映射.py' --self-test
```

它把模拟原始包转换为六种动作：

| 操作 | 输出动作 | 样例规则 |
| --- | --- | --- |
| 左键单击 | `like` | 松开后等待250ms排除双击 |
| 左键双击 | `burst` | 第二次按下落在窗口内，释放后输出8颗心动设计事件 |
| 左键长按 | `charge` | 持续650ms触发一次，松开不再补单击 |
| 右键按下 | `theme` | 三套主题循环 |
| 垂直滚轮 | `intensity` | 映射到0—100并限幅 |
| 相对移动 | `brush` | 积分为0—1虚拟舞台坐标 |

例如：

```jsonl
{"time":0.31,"name":"like","payload":{"amount":1}}
{"time":0.7,"name":"burst","payload":{"hearts":8}}
{"time":1.7,"name":"charge","payload":{"level":1}}
```

这是设计示例，不代表当前生产页面已启用这些额外操作。当前页面左键立即响应；如果增加互斥双击，需要接受单击延迟，或设计“第一击立即响应、第二击只补额外效果”。不要同时声称立即单击、完全互斥双击和零等待都能无条件成立。

样例要求时间单调递增。即使没有新输入，也要周期调用 `tick(now)`，否则长按和延迟单击可能永远没有机会确认。退出或拔插时调用 `reset()`，丢弃待判定手势，避免恢复普通鼠标后又补发爱心。

### 如何接到现有程序

接入应按“事件采集—业务动作—页面呈现”三层进行，不把页面知识写进内核。

1. 在 `native/interception.py` 的包循环中，把 `state/rolling/x/y/flags` 传入手势路由；定期调用tick。路由器应归属当前接管会话，开启/关闭/拔插都重置。
2. 在锁外调用业务回调；普通点赞继续走 `HeartApp.like('mouse')`，保留权威计数和SSE路径。
3. 非点赞动作可采用 `HeartApp.emit('action', {'name': ..., 'payload': ...})`。这要求新增动作回调和对应调用方，不能只写这一句就认为接线完成。
4. 在 `web/app.js` 的SSE分派中处理 `type === 'action'`，再按动作名调用主题、粒子或虚拟画笔函数。

示意页面分派：

```javascript
// 接入示意：补充到现有 events.onmessage 的分派中，不覆盖 state/like 处理。
if (data.type === 'action') {
  if (data.name === 'theme') {
    const names = ['rose', 'violet', 'peach'];
    if (Number.isInteger(data.payload.index) && names[data.payload.index]) {
      setTheme(names[data.payload.index]);
    }
  }
  // burst/intensity/brush 需要实现各自的显示函数和边界校验。
}
```

多颗装饰爱心与实际点赞次数应分别设计。一个双击产生8颗视觉爱心，并不必然表示计分加8；如果要加分，明确由服务端修改权威计数。不要让前端粒子数量自动变成业务计数。

### 位移画笔的关键细节

将 `dx/dy` 累加到一个独立虚拟坐标，映射到Canvas或Three.js场景；不需要移动系统指针。归一化到0—1可减少窗口大小变化带来的耦合。设备DPI不同，增益系数应可调；绝对设备、相对设备和高分辨率设备使用不同解释。

持续移动可能产生大量包。输入层保留必要数据，渲染层按 `requestAnimationFrame` 合并到每帧；绘图轨迹保留必要拐点，参数类动作可只保留最新值。点击等离散事件不要被简单节流丢掉。

### 多设备与外部控制的扩展

多只鼠标各自有手势状态、事件序号、控制句柄、设备身份和恢复状态，不能共享一个 `left_down` 变量。当前生产控制端只允许已确认的一个VID/PID，新增型号还要核实协议兼容性；同型号多设备需要实例选择，单改常量不等于支持多人。

如接入本机音乐软件、演示软件、MIDI或OSC，建议在应用层增加适配器、去重和速率限制。外发动作要明确目标和触发条件，先用离线日志模式验证，不把驱动线程变成不透明的自动操作脚本。

## 09 · 自有 HeartMouse 内核开发教程

### 设计职责

新驱动保留Windows的标准功能驱动 `mouhid`，只在目标设备栈增加过滤器。`HeartMouse.inf` 使用设备级 `HKR,,UpperFilters` 追加条目，不写全局Mouse类过滤器。

`HmAddDevice` 再检查硬件ID。即使INF匹配错误，代码也不能随意接管非目标。当前原型只附加第一只匹配设备，第二只同型号不附加；这不等于已经解决唯一物理实例识别。

### 核心执行流程

```text
DriverEntry
  ├─ 初始化全局锁、控制设备与安全DACL
  ├─ 注册 IRP/PnP/Power/内部控制分派
  └─ 注册 AddDevice

HmAddDevice
  ├─ 查询并核实硬件ID
  ├─ 锁内预留唯一目标
  ├─ 初始化移除锁
  └─ IoAttachDeviceToDeviceStackSafe

IOCTL_INTERNAL_MOUSE_CONNECT
  ├─ 保存原ClassService与ClassDeviceObject
  ├─ 替换为HmMouseCallback
  └─ 完成时才标记Connected

HmMouseCallback
  ├─ 检查目标、连接、PnP/电源、所有者、租约
  ├─ 正常：调用上层回调并跟踪已转发按钮
  └─ 独占：消费目标输入，累计左键DOWN
```

回调运行于适合鼠标类服务回调的高IRQL上下文，不应调用网页、文件、网络、用户模式等待或阻塞操作。当前原型把租约决策放在可单独测试的C策略模块。

### 协议必须能独立验证

| 请求 | 数值 | 输入 | 输出 |
| --- | --- | --- | --- |
| GET_STATE | `0x226000` | 无 | `HM_STATE`，40字节 |
| SET_MODE | `0x22A004` | `HM_MODE_REQUEST`，16字节 | 无 |
| HEARTBEAT | `0x22A008` | `HM_HEADER`，8字节 | 无 |

协议版本为1；头部含Version和Size。所有控制请求使用METHOD_BUFFERED。GET_STATE要求读权限，SET_MODE和HEARTBEAT要求写权限。控制设备DACL只授予SYSTEM与Administrators，因此新驱动客户端需要相应权限或经过设计的本地代理；不能假设现有未提升权限页面可以直接打开它。

`HM_STATE` 包含六个uint32字段和两个uint64字段：

```text
Version / Size / Flags / Mode / RemainingLeaseMs / Reserved
LeftButtonDownCount / Sequence
```

`Sequence` 随左键计数增长，不是设备插拔代次。读取点击增量时重新建基线；计数倒退时先检查是否重新加载，不应把无符号下溢解释成海量点击。

### 默认透传与5秒租约

正常流程：CREATE取得控制所有权 → SET_MODE显式开启 → 每隔短于5秒的时间HEARTBEAT → 结束时SET_MODE(0)并关闭。

租约到期后，单独发送心跳不能复活独占，必须重新显式开启。CLEANUP/CLOSE、PnP移除、停止设备、进入非D0状态都会取消接管。租约采用单调时间，不依赖用户修改系统日期。

当前到期判定是后续输入/状态/心跳路径中的检查，不是每秒强制运行的定时器。无人操作时没有输入可吞；到期后的下一次输入应透传。对外说明应准确区分这两种机制。

### 所有IRP都要有完成或转发路径

本次旧驱动问题说明：未知请求不能只返回一个值而不完成IRP。标准完成函数需设置状态、字节数，再调用完成例程，例如：

```c
static NTSTATUS HmComplete(PIRP Irp, NTSTATUS Status, ULONG_PTR Bytes)
{
    Irp->IoStatus.Status = Status;
    Irp->IoStatus.Information = Bytes;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return Status;
}

/* 控制设备的未知 IOCTL */
return HmComplete(Irp, STATUS_INVALID_DEVICE_REQUEST, 0);
```

对需要下层处理的请求则正确复制/转发栈位置，利用完成例程释放移除锁。不能在持有自旋锁期间等待，也不能在尚有完成回调使用设备扩展时删除设备对象。

### 本次审查中修复的并发问题

| 问题 | 修复原则 |
| --- | --- |
| 附加已生效，但Lower指针还没赋值 | 使用 `IoAttachDeviceToDeviceStackSafe` |
| 第二只同型号短暂附加后立即删除，已有IRP可能仍引用扩展 | 附加前锁内预留唯一目标；第二只不临时附加 |
| 失败CONNECT清理覆盖下一次连接的PendingConnect | 连接完成状态与指针在同一锁下更新 |
| 下层CONNECT未完成就宣称已连接 | 仅成功完成后设置Connected |
| 并发透传回调导致按钮DOWN/UP跟踪次序不确定 | 锁存ButtonStateUncertain，保守保持透传，直到新PnP实例 |
| 开启前已有DOWN传给系统，开启后吞掉UP | 检查已转发按钮与在途回调，条件不满足就拒绝开启 |

这些是源码审查和编译测试已处理的事项，不等于Driver Verifier和真实设备测试已经覆盖所有竞争条件。

### 未来完整事件队列怎么设计

目前B路线只有状态和左键计数，不能直接做A路线的完整移动轨迹。要在B路线支持画笔、长按、侧键和滚轮，应设计新版本的 `READ_EVENTS` 协议，而不是从左键累计值推测所有手势。

建议事件包含版本、长度、设备代次、序号、单调时间、按键、滚轮及坐标；使用有界环形队列，定义满队列时的策略，暴露丢包计数，确保事件不会引用可分页内存或失效指针。用事件通知或受控的异步请求唤醒用户态，增加取消、关闭和PnP移除测试。这一队列是扩展设计，目前未实现。

```powershell
python scripts/heartmouse_probe.py --exclusive-seconds 15
```

### 三种“无需重启”不是同一件事

| 操作 | 本项目状态 |
| --- | --- |
| 已加载驱动下切换普通/专属模式 | A路线已实物验证核心独占功能，无需整机重启 |
| 首次加载已签名驱动、重建目标设备栈 | 本机成功；其他环境需观察PnP结果，不能保证所有电脑 |
| 替换已经加载的自有内核代码 | 当前HeartMouse没有DriverUnload，不支持以设备重启完成热升级 |

重新编译 `.sys` 后，仅重启鼠标设备并不会自动替换已经驻留的驱动映像。自有原型保守不提供卸载例程，这是已记录的边界。若未来要真正热升级，需要重新设计控制设备、引用计数、设备解绑及卸载生命周期，并进行专门验证。

## 11 · 验证方法与常见故障

### 每次修改选择对应验证

```powershell
python -m unittest discover -s tests -v
node --check web/app.js
python tests/browser_check.py
python '教程/示例/创意事件映射.py' --self-test
```

当前项目测试覆盖了路由、长按不连发、失败清理、设备身份变化、心跳所有权、接口来源校验、原生协议布局、C租约策略等。`test_driver_protocol.py` 执行真正编译的C测试程序；若构建产物不存在会跳过，因此要看测试报告，不能把SKIP当PASS。

浏览器测试使用临时端口与临时数据目录，本机默认使用Edge。若选择其他浏览器，需要修改/配置测试启动渠道；只装了Playwright Python包不代表已经有对应浏览器运行文件。

### 实物验收清单

| 项目 | 要实际观察的结果 |
| --- | --- |
| 默认状态 | 目标鼠标移动、点击正常 |
| 独占开启 | 目标指针输入不再作用于系统 |
| 点击计数 | 每次独立按下只记一次，长按不自动连发 |
| 其他设备 | 另一只鼠标和键盘仍可操作 |
| 恢复命令 | 按快捷键或页面恢复后正常控制 |
| 页面失联 | 在文档声明的超时范围内恢复 |
| 程序结束 | 句柄清理能释放接管 |
| 插拔 | 重新接入默认普通模式，身份重新核实 |
| 电源与PnP | 新内核在停止、睡眠、移除后不自动恢复独占 |

这次用户反馈确认了核心移动隔离与点击爱心。不要把其余未被反馈覆盖的项填写为全部通过。Driver Verifier等内核测试应安排在适合的测试机器和恢复条件下，本项目尚未执行。

### 故障定位表

| 表现 | 优先检查 | 本项目处理经验 |
| --- | --- | --- |
| 服务RUNNING但看不到目标 | 设备是否插入、栈是否重建、当前实例 | 读取硬件ID和PnP状态，不默认整机重启 |
| 接收器插回却未立刻显示 | 是否换口、是否新实例、枚举时序 | 持续记录插拔事件；旧实例尾部不再有效 |
| 设置后立刻失败/读回0 | getter是否真的存在、是否把错误回读当状态 | REA发现GET_FILTER不支持，改写控制端 |
| 进程清理延迟 | 是否发送未知IOCTL、IRP是否完成 | 禁止未知控制码，不靠机械重试 |
| 数据全乱、位移异常 | 24/20字节结构、对齐、符号 | 对照原始MOUSE_INPUT_DATA和ABI断言 |
| 滚轮向下得到巨大正数 | uint16是否转换为int16 | 先做符号扩展，再做幅度限制 |
| 左键长按反复触发 | 是否把每个包都当一次按下 | 维护DOWN/UP状态；测试重复DOWN |
| 页面点了但未生效 | 会话令牌、SSE连接、原端口、控制所有者 | 程序重启后刷新页面 |
| Ctrl+Alt+F12不可用 | 是否被另一个程序占用 | 注册失败时禁止启用独占 |
| 改了源码EXE还是旧效果 | 是否重新打包、是否仍运行旧进程 | 源码与EXE分别管理，不强行覆盖运行中的EXE |
| PowerShell找不到中文脚本名 | `.ps1`是否被5.1按错误编码解读 | 含中文的脚本存UTF-8 with BOM |
| 浏览器测试被CSP拦住 | 测试是否把字符串当动态表达式 | 使用箭头函数谓词，不放宽产品CSP |
| 新SYS无法加载 | 是否正式签名、包是否匹配、是否旧映像仍驻留 | 保留安全策略，记录签名/生命周期限制 |

## 12 · 后续开发建议与资料

### 推荐的三步扩展

**第一步：增加纯页面效果。** 先实现右键主题、不同形状粒子或用户可选音色。输入层保持原协议，离线样例验证动作语义，再对应用和页面接线。这个阶段不需要编译内核。

**第二步：增加状态型交互。** 实现双击、长按、滚轮参数和虚拟画笔。定义互斥规则、单击延迟、停止取消和数据合并，补上路由与实物测试。保持只对已确认目标接管。

**第三步：按产品需求决定是否部署自有内核。** 如果需要更强的失联恢复保证、清晰可维护的状态协议、事件队列与设备生命周期，再扩展HeartMouse、做签名和专门测试。不要为了一个动画就承担内核维护成本。

### 交接时最少留下什么

记录分支与提交、源码修改点、实际设备身份、协议版本、构建命令、驱动与包哈希、签名状态、已执行测试、用户实物观察、恢复方法和未完成项。继续维护唯一任务文档 `开发任务/001-无线鼠标点赞工具.md`，不要让多个进度文件互相矛盾。

### 许可证与分发

旧Interception库/驱动的上游许可和商业条款仍需遵守。重写控制端不自动消除第三方内核的分发义务；本项目保留原许可，并未把第三方内核重新命名成自有作品。自有源码发布、商用和签名应分别制定许可与发布策略。
