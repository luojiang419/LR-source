# 内置 OCR 预加载与进度锁

开启内置模型后只保存配置，会把 llama.cpp 的启动时间留到第一次标星；若状态查询也取得整段推理使用的锁，加载期间连等待提示都无法更新。

预加载使用后台线程，开关请求立即返回。推理锁继续保护模型进程的生命周期，独立状态锁只维护阶段、起始时间和实际可测进度，查询不能取得推理锁。重复开启共用加载，关闭时标记请求代次取消，加载完成前再次检查代次，避免过期请求重新拉起模型。

组件复制/下载可使用实际 done/total，但需标明“当前文件准备进度”；健康检查只提供就绪信号时，不得把等待时间换算成假百分比。此阶段使用不定进度条与等待时长，真正就绪后再进入 OCR。任务进度同时绑定任务类型、job ID 和 run_token，防止撤星重标后的旧请求串入新任务。

验证包含：人为阻塞组件准备时，开关仍立即返回且快照可读取 42/100；预加载取消及去重；实际本机 GLM-OCR 在标星前加载就绪，标星后正确识别隔离标签，加载起始时间保持，证明没有重复加载。

## LM Studio 已运行但仍等待内置加载

先检查实际安装资料里的 `model-providers.json`，不能只看项目目录中存在 LM Studio 卡片。`builtin_enabled=true` 会覆盖外部选用；二星工作流还可能同时等待选中的 OCR 与多模态模型。任务 138 的安装配置只有内置卡片，历史任务有模型加载超时，而本机 LM Studio 的 glm-ocr 实际已就绪。

按用户明确选用 LM Studio 的要求，备份当前配置、关闭内置开关、选中经过鉴权验证的本机 glm-ocr 卡片；保留其他卡片与凭据，不通过终止用户的模型进程释放显存。不要把匿名 `/v1/models` 的 401 当作服务不可用，应使用用户已有的有效配置，避免打印密钥。

验证必须走真实二星链路：本轮例图直接 OCR 1.223 秒；安装引擎的键盘/按钮二星约 5.822/5.255 秒到确认，正确匹配 P105、P106 未拍摄，四张副本归属一致。原始 OCR 位于 `ocr_documents`；自动确认任务的 result 可能只有 codes/user_sku_choice，不能据此误判模型未执行。程序逻辑无需修改，修复的是本机模型选用。

## 手动 OCR 长时间显示“正在发现图片”

- 表现：设置显示“正在发现图片 58/9289”，容易误以为必须扫描完整个库才开始识别。
- 根因：`workflow_runs.discovered` 仅表示入队扫描结束；`done/total` 实际是已处理数/已入队数，工作线程早已并行消费。旧界面把扫描状态当作整个执行阶段；此外 OCR 复用视觉资产注册，触发不必要的元数据读取、原图哈希和公共归档锁等待，NAS 上尤其慢。
- 解决：OCR 从预览直接识别并保存文本资料，省去资产注册与两次完整 NAS 文件哈希，使用前后 size/mtime、索引文件版本及模型输入摘要校验和去重；完整内容指纹留到视觉阶段生成。分别显示已处理/已入队、继续入队，以及读取、校验、等待模型/解码收尾、识别和保存步骤的真实耗时。
- 验证：覆盖扫描未结束时首图已完成、现场与归档图不注册资产仍保存结果、识别期间原图变化拒收，以及浏览器真实阶段文案。生产任务只读记录从用户反馈的 58/9289 后续到 73/9673，不能把扫描尚未结束等同于完全卡死；已有单项 HTTP 500 也须和扫描问题分别判断。

归档 OCR 结果独立进入全文检索和快捷检索，不能等视觉结果出现后才允许搜索。目录/OCR/视觉证据与文件版本分开保存：全目录 OCR 覆盖后，无有效款号图时采用唯一 LC 目录名；规则长度不符、多个候选或不一致时待核验。新图、文件版本变化和迟到冲突会撤销本功能的自动推断，人工 SKU 保留。批量 OCR 与视觉只写数据库，不调用资产注册或元数据写回队列；完整内容 SHA 与外观向量用于后续核验，不能把配色相近当作同款结论。

## LM Studio 间隔很久才收到一批请求

实机线程栈曾显示四个 OCR 工作线程都在等待共享库写入，参考资源重扫线程在批量写同一数据库。模型批次需要覆盖这些背景写入者的让路规则。参考目录扫描在批次边界等待时必须释放数据库，并支持取消和软件关闭。

目录核验应使用 `(root,online,folder)` 的完整索引前缀。缺少中间的 online 条件时，即使写了 folder 条件，更新仍可能扫描整个归档根目录。清理在线与离线推断可显式写 `online IN (0,1)`。历史 OCR 补录从 OCR 表驱动主键查找，避免优化器从全部在线素材开始扫描。

缓存取图的读租约锁只保护计数。将数据库查询或文件 stat/open 放在这把共享锁内，会使多个取图线程串行等待慢文件。租约先登记，I/O 在锁外执行，再按原摘要校验，失败时沿用缓存失效处理。

取图、模型调用与保存分阶段计时，并为准备和保存留出有界工作线程。模型卡片并发仍通过原有推理槽限制。实际 43 秒处理 39 张，后台请求最大间隔 3 秒。停止时保留队列和当前批次指针，在途结果收尾后计数继续更新，恢复时复用原范围和游标。

## 二星卡在提交或模型准备，但模型自身不到一秒

任务179核验当前魔搭071740与实际本机安装，必须区分客户“仅OCR”配置与本机同时选用Qwen的配置。不能仅发现本机Qwen耗时，就把客户原因归给Qwen。

首次二星建当日文档时同步 `start_stream`，会在HTTP提交路径扫描整目录；入队后调用却丢弃的 `state()` 又增加清单读取。用持久 `shooting_stream_queue` 接续目录、返回轻量入队状态；新标签无历史确认时先只读查空，不等待旧款SKU大锁。并发OCR结果先保存，后台归档事件负责区间接续，避免模型已返回但界面仍等原图哈希。

二星输入复用 `ocr_input`，不进入浏览缓存生成队列。容量4时后台OCR最多使用3个名额，现场二星仍可用4个；调度器还须允许现场worker越过等待中的批量worker，否则只预留推理名额仍会饥饿。真实“等待名额”与“加载本机模型”要分开显示。

自动确认可复用已登记的原片版本哈希，但文件worker仍须在写入前验证真实哈希/修订，外部改图必须拒绝。回归覆盖该拒绝与确认后重启接续。最终实际安装版四款16图两轮3.728/4.382秒全部显示，原生二星约1.526秒入库；文件校验写回继续后台运行，不能把拍摄款数绑定到文件写完才更新。

## 入库已完成但元数据长期写入

任务180在当前安装版复现16图写回36.414秒。4图profile中29次ExifTool启动消耗6.150秒，真正提交仅0.046秒，不能把耗时直接归给磁盘/NAS。复用只读ExifTool会话，并通过同一Perl库在常驻worker内编辑JPG/XMP字节，可把同16图实际写回降到11.077秒。

worker只处理内存；原片提交、哈希/修订/像素/MPF/缩略图/非目标字段验证仍由原流程执行。生成结果不等于写入成功，必须实际回读且页面提示收尾。RAW内嵌路径维持既有实现。

Windows要注意三个边界：`-@`参数文件的中文绝对路径可能打不开，用短命进程cwd和ASCII文件名；常驻子进程不能长期占用用户资料目录作cwd，否则会阻止迁移/清理；读取文本参数要保留原CRLF。管道超时必须同时覆盖stdin发送，不能只给接收队列设超时后仍卡在write。退出时等待文件提交结束，再关闭常驻进程。
