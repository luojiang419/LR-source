# 全库预览进度占锁与重复编码

## 表现

NAS 目录生成预览很慢，清晰图长时间不完成；即使单独解码很快，进入归档后前台预览和缓存状态仍可能等待数十秒。

## 根因

- 420/4096 两阶段共享队列并严格按 edge 排序，全库小图会阻挡清晰图；每阶段重复打开源容器，CPU WebP method4 压缩仍是额外成本，GPU 解码无法消除它。
- 全库进度查询持有缓存全局锁，对十多万份 JSON 任务逐条提取关联键、回查素材，查询时会阻挡前台读取和后台发布。只给素材表加索引仍不足，因为任务表还要回表读取大 JSON。
- 队列恢复在全局锁内逐图打开 SQLite 连接做缺缓存检查，可能长期抢占发布锁。

## 已验证的处理

- 默认嵌入 JPEG，符合尺寸时保留扫描压缩数据，超限才缩到 2048；每张一次读取完成缩略图和清晰图。取消按全库小图阶段排序，保留重试边界与原片只读。
- 进度只读查询使用独立 WAL 快照；任务表保存 pair_key 并建立覆盖索引，素材侧也建立覆盖索引，避免查询统计时解析大 JSON 与随机回表。
- 缺缓存预检移到锁外，批次复用连接；命中条目在事务提交前复核，仍保护淘汰/迁移竞态。只可再生缓存索引使用 synchronous=NORMAL，业务库保持原设置。
- 预览批次已经持有 generation 租约时，内部调用不重复申请租约；否则在线迁移等待读者、读者再次等待迁移会互相阻塞。

## 验证与限制

任务 109 的实际安装库关联进度统计从约 19.8 秒降到 86ms；新增并发回归确认统计和恢复队列不占住前台缓存锁。32 张真实 NAS CR2、28 路无 NAS 限流，在空输出缓存下约 4.30 秒完成 64 份 JPEG；不代表 2000 张冷缓存或不同 NAS 的保证。旧缓存清理只删有登记、生成键和原哈希均匹配的文件，并拒绝链接/硬链接及外部替换文件。
