# 照片元数据写入、中文参数与稳定资产身份

## Windows 中文元数据变乱码

直接通过 Windows 命令行参数传 `-XMP-fk:ShootType=细节图` 时，本机 ExifTool 13.59 读回为乱码。`-charset filename=UTF8` 只解决文件名，不能保证参数值穿过启动器后仍保持 Unicode。

`metadata_writer.py` 使用 UTF-8 编码 stdin 配合 `-@ -` 传递全部数据参数，密钥/文本不经过 shell。拒绝参数内换行，防止拆成额外 ExifTool 参数。中文 SKU、中文拍摄类型在真实 JPEG 写入/读回与浏览器批量操作中已验证。

## 写元数据会改变文件哈希

解码像素相同，整文件 SHA-256 仍改变。不要把路径/mtime 指纹或整文件哈希直接当永久资产主键：资产与文件分别使用 UUID，多位置独立登记，历史文件版本保存前后哈希。XMP 中写带连字符的标准 UUID，避免极少数纯数字 UUID 被 JSON 输出识别成数值丢失前导零。

同文件移动/复制后优先读取 UUID，再用已知哈希匹配；未知内容复用了旧身份时拒绝静默合并。RAW/JPG 是同拍资产的不同组件，后到 RAW 继承已有备案及原批次，撤销原批次时也能恢复后到组件。

## 同内容 JPG 已在其他目录入库时的配对冲突

表现：二星 SKU 任务尚未调用模型就报“配对文件资产冲突”。旧实现逐组件提交，先给 RAW 创建新资产，随后按 JPG 哈希发现另一已有资产，失败后留下没有目录链接的孤立 RAW。

解决：先查齐配对组件身份，再统一选择已有资产并在同一事务提交。旧孤立记录只能在没有业务引用、归属、永久字段、伴随文件和外部改动的情况下恢复；已有独立归属继续要求复核。恢复保留文件身份并记录审计，不直接吞掉冲突。

验证：`test_asset_archive.py` 覆盖跨目录 JPG 复制后配对、旧中断记录恢复、归属及永久身份保护和读取失败回滚；真实 302 张目录在数据库副本中完成准备。手动 OCR 只读当前图，应独立于整目录归档准备，避免首次网络目录哈希阻塞文本读取。

## 临时副本与 Windows 替换

不在原文件上直接跑 ExifTool 写入。写同卷临时副本，读回目标字段，检查原有非目标字段和 JPEG 像素，再保存备份及 SQLite journal，最终替换。Windows 持有原文件读句柄时，本机 `os.replace` 返回 WinError 5；需要结束写前保护句柄，立即再次比较源/目标哈希，再执行同卷替换。

文件替换与数据库提交没有跨系统原子事务。journal 中保存 target 和 after_hash，重启时若文件已经是预期版本，只补记 applied；不能因数据库仍显示 running 而再覆盖用户文件。回退只恢复本工具拥有且尚未被后来改动的备案字段，保留稳定身份、星级和后续不相关编辑。

## 自写元数据不应撤销标签识别

原有监控/识别使用路径、大小和 mtime 指纹，备案写回必然触发变化。写入后明确记录本工具的 before→after 指纹映射，更新目录记录；SKU 验证允许沿已知映射检查，未知的外部变化仍作废输入。不要简单在一段时间内屏蔽整个目录，否则会吞掉真实新照片。

切换工作表前先把已进入目录的照片同步到原拍摄段，再冻结段并创建新段，否则晚到的二星事件找不到原段，容易把 SKU 边界丢掉。

2026-10-22 普通星级也开始自动同步 JPG 内嵌评级，因此不能仅在资产备案写入后维护指纹。`rating_sync.py` 在写入完成后更新同拍文件版本、待执行 SKU 任务的预期哈希及选片索引，并登记 `metadata_versions` 的 before→after 链；不改变会话 revision 或人工覆盖。否则监控会把自己的改星识别成外部照片更新，已完成 OCR 也可能重新排队。`test_rating_xmp_sync_does_not_repeat_completed_ocr` 已验证三张已识别照片改星后仍只有原来三次模型调用。

星级写入与 SKU 队列共用归档锁；旧 SKU 任务执行时使用最新共享评级，避免刚清零又被排队中的一星／两星写回。数据库评级及持久 XMP 任务在同一事务保存，文件写入仍采用临时副本、读回及替换前哈希复核；异常保留数据库评级并等待重试。连续 1→5→0、写入途中更新、重启／离线恢复和“先同步零星再执行旧 SKU 任务”均有隔离测试。

## 已完成验证与限制

2026-10-20 起，新备案和自动 SKU 区间统一为 RAW/JPG 内嵌：界面和公开 API 都不能降级为 RAW sidecar，旧活动/接续段与暂停段迟到识别也要检查策略。历史批次的 mode/journal 不应直接改写，否则撤销会误把原 sidecar 备份当 RAW 文件处理。进度必须按实际 applied 任务及 storage 统计：真实 CR3/JPG 双写已验证，注入 RAW 失败时显示 RAW 0/JPG 1，不能只凭数据库已赋 SKU 宣布两份文件都成功。

## 后拷 RAW 与内部工作文件

- JPG 的星级来自明确人工覆盖或文件真实评级，不从时间规则推荐导出。跨目录配对检查型号/序列号、日期/子秒及图像/文件身份；重复来源保留待确认，不能只按 `IMG_0001` 配对。
- RAW 后拷目录已登记时，再次选择也要重新发现新文件。来源 JPG 的评级/SKU 变化要通知相关 RAW 目录；相同目标和已经存在的内嵌值不重复改写。
- RAW 原始数组和内嵌预览摘要要保持，CR3 还逐块验证所有 mdat 负载；Sony/TIFF 的 StripOffsets、ThumbnailOffset、SR2SubIFDOffset/Length 等结构位置可能随 XMP 插入而合法重定位，不能把指针变化误当拍摄参数变化。
- RAW 副本校验耗时可超过监控稳定窗口。临时文件须放在照片目录之外的同卷软件暂存区；发现器仍忽略 `.framekeep-` 前缀，不能仅依赖“通常写入很快”。当前使用资料目录 `metadata-staging/`，跨卷使用实际挂载卷根目录 `.framekeep-staging/<资料标识>/metadata-staging/`；不可写时失败，不退回照片旁暂存。

## 照片旁的临时 JPG 残留（2026-10-28）

- 表现：资源管理器在拍摄目录显示 `.framekeep-write-随机串.JPG`。移除旧工作文件夹并不等于移除临时编辑文件。
- 根因：旧实现在照片旁 `mkstemp`，文件带真实图像后缀，会被资源管理器等外部读取。现场四份文件对应的任务均记录安全替换错误 32，失败后的删除也未成功；记录不能证明具体占用者。
- 解决：临时编辑移入照片目录之外的同卷软件暂存区，保留哈希、像素和原子替换。旧残留先核验 journal 哈希、原照片及像素，移到软件资料保存并记录位置，不仅按前缀删除。
- 验证：真实 ExifTool 的写星、SKU、中文描述和侧车准备期间检查照片目录没有内部临时项；提交失败保持原图，C/D 跨卷仍同卷提交。冻结引擎重复验证以上关键路径。
