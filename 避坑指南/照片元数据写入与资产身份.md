# 照片元数据写入、中文参数与稳定资产身份

## OCR 确认后的历史补写与 MPF JPG

- OCR 原文已保存、数据库 SKU 已确认、文件元数据已提交是三个独立状态。正向标签与目录一致即可确认；无标签的目录默认款号须等待完整覆盖。文件写入通过持久发件箱接入已有元数据队列，保存请求键，跨库确认中断后可幂等接续。
- 纯元数据提交会改变 size/mtime 指纹。只有原写入器校验通过、文件摘要仍匹配日志且持有只读保护时，才能将 OCR、视觉证据与索引关联到新版本。外部修改仍应使旧证据失效。人工后续修改由资产修订和字段日志保护。
- 真实佳能 JPG 的 `MPImage2:MPImageStart` 会因 XMP 插入合法重定位。不能直接忽略所有 MPF 差异。读取原文件与待提交内存结果中的对应附加图像，要求非空且字节完全相同，记录摘要后才允许偏移改变。MPF 大缩略图可能名为 `MPImage2:PreviewImage`，通用 MPO 对应 `MPImage2:MPImage2`。主图像素与其他元数据继续使用原校验。
- 已知图片主键时，写入后的资料刷新必须按 item 更新。真实 12GB 库上的 `path=? COLLATE NOCASE` 不匹配原路径索引排序规则，导致收尾扫描和数据库锁等待。不能因为函数名叫“路径变化通知”就用于所有写后刷新。
- 验证入口为 `test_catalog_sku_writeback.py`，覆盖真实 JPG/XMP 回读、RAW 字节保留、MPO 附加图像篡改拒绝、冲突恢复、人工保护、重试幂等、导入后暂停及重新建立搜索索引。实际 NAS 证据见任务 163 和 `build/ocr-sku-writeback/`。

## Windows 中文元数据变乱码

直接通过 Windows 命令行参数传 `-XMP-fk:ShootType=细节图` 时，本机 ExifTool 13.59 读回为乱码。`-charset filename=UTF8` 只解决文件名，不能保证参数值穿过启动器后仍保持 Unicode。

`metadata_writer.py` 使用 UTF-8 编码 stdin 配合 `-@ -` 传递全部数据参数，密钥/文本不经过 shell。拒绝参数内换行，防止拆成额外 ExifTool 参数。中文 SKU、中文拍摄类型在真实 JPEG 写入/读回与浏览器批量操作中已验证。

## 写元数据会改变文件哈希

解码像素相同，整文件 SHA-256 仍改变。不要把路径/mtime 指纹或整文件哈希直接当永久资产主键：资产与文件分别使用 UUID，多位置独立登记，历史文件版本保存前后哈希。XMP 中写带连字符的标准 UUID，避免极少数纯数字 UUID 被 JSON 输出识别成数值丢失前导零。

同文件移动/复制后优先读取 UUID，再用已知哈希匹配；未知内容复用了旧身份时拒绝静默合并。RAW/JPG 是同拍资产的不同组件，后到 RAW 继承已有备案及原批次，撤销原批次时也能恢复后到组件。

## 同内容 JPG 已在其他目录入库时的配对冲突

表现：二星 SKU 任务尚未调用模型就报“配对文件资产冲突”。旧实现逐组件提交，先给 RAW 创建新资产，随后按 JPG 哈希发现另一已有资产，失败后留下没有目录链接的孤立 RAW。

解决：先查齐配对组件身份，再统一选择已有资产并在同一事务提交。旧孤立记录只能在没有业务引用、归属、永久字段、伴随文件和外部改动的情况下恢复；已有独立归属继续要求复核。恢复保留文件身份并记录审计，不直接吞掉冲突。

验证：`test_asset_archive.py` 覆盖跨目录 JPG 复制后配对、旧中断记录恢复、归属及永久身份保护和读取失败回滚；真实 302 张目录在数据库副本中完成准备。手动 OCR 只读当前图，应独立于整目录归档准备，避免首次网络目录哈希阻塞文本读取。

## 内存结果与 Windows 直接写回

不对原路径执行 ExifTool 写入，也不生成整图临时副本。ExifTool 通过标准输入/输出在内存中处理，核对目标字段、非目标字段和 JPEG/RAW 图像数据后保存小型 SQLite journal。最终用同一受控读写句柄核对哈希并直接写回，拒绝并发写入与替换；普通异常尝试用内存原内容恢复。强制结束进程或断电不再具备原子替换保障。

文件写回与数据库提交没有跨系统原子事务。journal 中保存 target 和 after_hash，重启时若文件已经是预期版本，只补记 applied；不能因数据库仍显示 running 而再覆盖用户文件。回退只恢复本工具拥有且尚未被后来改动的备案字段，保留稳定身份、星级和后续不相关编辑。

## 自写元数据不应撤销标签识别

原有监控/识别使用路径、大小和 mtime 指纹，备案写回必然触发变化。写入后明确记录本工具的 before→after 指纹映射，更新目录记录；SKU 验证允许沿已知映射检查，未知的外部变化仍作废输入。不要简单在一段时间内屏蔽整个目录，否则会吞掉真实新照片。

切换工作表前先把已进入目录的照片同步到原拍摄段，再冻结段并创建新段，否则晚到的二星事件找不到原段，容易把 SKU 边界丢掉。

2026-10-22 普通星级也开始自动同步 JPG 内嵌评级，因此不能仅在资产备案写入后维护指纹。`rating_sync.py` 在写入完成后更新同拍文件版本、待执行 SKU 任务的预期哈希及选片索引，并登记 `metadata_versions` 的 before→after 链；不改变会话 revision 或人工覆盖。否则监控会把自己的改星识别成外部照片更新，已完成 OCR 也可能重新排队。`test_rating_xmp_sync_does_not_repeat_completed_ocr` 已验证三张已识别照片改星后仍只有原来三次模型调用。

星级写入与 SKU 队列共用归档锁；旧 SKU 任务执行时使用最新共享评级，避免刚清零又被排队中的一星／两星写回。数据库评级及持久 XMP 任务在同一事务保存，文件写入使用内存结果校验、同句柄版本复核及原路径直接写回；异常保留数据库评级并等待重试。连续 1→5→0、写入途中更新、重启／离线恢复和“先同步零星再执行旧 SKU 任务”均有隔离测试。

## 已完成验证与限制

2026-10-20 起，新备案和自动 SKU 区间统一为 RAW/JPG 内嵌：界面和公开 API 都不能降级为 RAW sidecar，旧活动/接续段与暂停段迟到识别也要检查策略。历史批次的 mode/journal 不应直接改写，否则撤销会误把原 sidecar 备份当 RAW 文件处理。进度必须按实际 applied 任务及 storage 统计：真实 CR3/JPG 双写已验证，注入 RAW 失败时显示 RAW 0/JPG 1，不能只凭数据库已赋 SKU 宣布两份文件都成功。

013 阶段 105 项回归通过，含真实 JPEG、中文字段、跨目录恢复、写回撤销、替换后崩溃恢复、SKU outbox、后到组件、分页切换、真实 Chrome 多选/备案和模拟本地视觉两路请求。真实 ARW 副本 XMP 伴随写入/读回成功，RAW 字节保持；该阶段配对时序单测使用模拟 RAW，不能混淆。本地 Qwen/LM Studio 未实际加载，网络适配验证用模拟 HTTP 服务。

014 已进一步开放 CR3/ARW 内嵌：R6 II 公开 CC0 普通 RAW/C-RAW 和 Sony ARW 副本验证通过，回归增至 114 项。详见 [014-JPG现场评级与后拷RAW自动补写](../开发任务/014-JPG现场评级与后拷RAW自动补写.md)。

## 后拷 RAW 与内部工作文件

- JPG 的星级来自明确人工覆盖或文件真实评级，不从时间规则推荐导出。跨目录配对检查型号/序列号、日期/子秒及图像/文件身份；重复来源保留待确认，不能只按 `IMG_0001` 配对。
- RAW 后拷目录已登记时，再次选择也要重新发现新文件。来源 JPG 的评级/SKU 变化要通知相关 RAW 目录；相同目标和已经存在的内嵌值不重复改写。
- RAW 原始数组和内嵌预览摘要要保持，CR3 还逐块验证所有 mdat 负载；Sony/TIFF 的 StripOffsets、ThumbnailOffset、SR2SubIFDOffset/Length 等结构位置可能随 XMP 插入而合法重定位，不能把指针变化误当拍摄参数变化。
- RAW 校验与修改在内存中完成，不创建整图准备文件或任何同卷暂存区。发现器继续忽略旧 `.framekeep-` 内部项，兼容历史文件；不能用更换前缀掩盖仍在创建整图副本的逻辑。

## 照片旁的临时 JPG 残留（2026-10-28）

- 表现：资源管理器在拍摄目录显示 `.framekeep-write-随机串.JPG`。移除旧工作文件夹并不等于移除临时编辑文件。
- 根因：旧实现在照片旁 `mkstemp`，文件带真实图像后缀，会被资源管理器等外部读取。现场四份文件对应的任务均记录安全替换错误 32，失败后的删除也未成功；记录不能证明具体占用者。
- 解决：用户追加要求后，彻底移除整图暂存及替换机制，改为内存生成/校验和直接写回。旧残留核验 journal 哈希、原照片及像素后处理，保留小型字段记录，不仅按前缀删除。
- 验证：真实 ExifTool 的写星、SKU、中文描述及侧车准备期间，照片目录与资料目录均无整图临时项；覆盖同一文件身份、外部版本变化拒绝、部分写入错误后的内存恢复、新 XMP 失败清理及重启补记。
- ExifTool 使用 `-o -` 和标准输入时，输入/输出均走内存；新 XMP 必须提供有效的 XML/RDF 骨架，空输入会默认生成 EXV，不能仅凭返回码为 0 判定已生成标准侧车。中文参数通过软件资料内的小型 UTF-8 参数文件传入，不能与图像同时争用标准输入，也不能依赖 Windows 原生命令行传递中文文件名。

## 现场 JPG 的 Windows 属性与内嵌缩略图（2026-11-04）

- 表现：软件内已入库不能证明磁盘已有 SKU；私有 `XMP-fk:SKU` 也不能保证 Windows 属性展示。现场状态须按当前资产 revision 的文件任务统计，标题/描述任务不能替代 SKU 任务；实际落盘回读之后才能显示成功。当前 RAW 新任务沿用同名 XMP 策略，上文 RAW 内嵌记录属于历史阶段。
- 解决：JPG 除私有 XMP 外同步 `XPSubject` 和 `XPKeywords`，Windows “主题”和“标记”可查看。替换款号时删除旧 SKU 标记，保留其他标记；字段恢复日志保存 XP 原值，旧版当前现场记录补属性时沿用最初撤销基线。
- 易错点：添加 XP 字段会合法移动 `IFD1:ThumbnailOffset`。用户实拍 `XSY_2297.JPG` 的副本复现偏移变化；须对生成前后 `ThumbnailImage` 原始字节逐一核对并记录摘要后才允许变化，不能直接忽略全部 offset 字段。取消最后两个 XP 字段时 ExifTool 可能清理空 IFD，撤销需要显式保留既有分辨率等字段。
- 验证：二星唯一款号自动入库、选择页与拍摄清单改号、旧记录补属性及撤销、缺失任务恢复、失败重试均使用隔离真实文件；Windows Shell `System.Subject` / `System.Keywords` 实读通过。原实拍图只读，在验收副本上保留二星、像素及缩略图字节，注入缩略图篡改会拒绝提交。真实 CR3 后拷匹配及改款同步使用 XMP，RAW 全文件摘要不变。


## 常驻回读、NAS快照复用与历史关键词（2026-11-05）

- 常驻编辑并不等于没有逐图启动进程：旧的内存结果read(bytes)仍走CLI。新增受限JPEG/XML内存读取时，须遵守ExifTool的列表和同名字段优先级；纯JPEG可能从未加载XMP模块，使用FixUTF8前必须显式加载Image::ExifTool::XMP。
- 小于64MB的JPEG可在单次操作中复用已经按expected_sha校验的原图字节，用于元数据、像素、缩略图和内存编辑。该快照只在当前线程/调用内生效；提交前依然读真实哈希，提交及写后回读不以缓存冒充。外部替换后的拒绝覆盖已有专项测试。
- 原文件可能保留旧SKU关键词而私有SKU字段已缺失。只删除“旧私有SKU精确对应的标记”会留下错误的SKU:词条。写入新的主SKU时规范化软件保留的SKU:/ShootType:词条，保留普通关键词，并把旧关键词纳入字段级撤销日志。用户显式编辑关键词和明确撤销不自动接管。
- 当前已完成任务的旧日志可证明残留时，沿原操作和原revision持久补写，保留最初撤销基线；正常日志仅标记策略已检查，不重复写图。本轮217张NAS副本通过这条软件队列自动补齐，随后4217张全量回读残留为0。
- 全量核验要检查最新资产revision和当前文件任务，旧版本applied不能遮住改款后的排队任务。阶段耗时按持久事件重建，手工核对、旧字段升级和开发等待需单列。
- 旧缓存竞态测试不能继续假设一定抛异常：已有独立恢复槽允许安全回退。应同时断言未知原文件字节不变、没有被索引接管、生成预览落入独立槽位；本次未改变缓存实现。
