# 二星 API 并发不能被串行推理与归档锁阻塞

## 表现与根因

API 服务端已开启多并发，新二星仍等待旧图片。仅提升队列优先级不能解决，因为单个 SKU 工作线程同步等待整个识别请求；共享容量满时也会继续等待。增加独立线程后，如果请求前先执行归档 reserve，新图片仍会被归档写图和区间重建锁拖延数秒。

## 已验证的解决方法

- 为 API 二星设置独立调度，原子领取持久任务后启动独立工作线程，网络调用期间不持有 SKU 结果提交锁。普通解析、旧二星与服务端执行顺序独立。
- 独立 API 标签跳过普通本机推理容量等待，local 模型继续受本机资源限制。任务 078 增加每卡并发上限后，OCR、二星和多模态必须共用卡片容量，满时最新二星优先使用下一个空位，不能绕过上限。
- API 请求先执行，归档 reserve 放在响应后的提交阶段。未完成的二星仍保留为空款号边界，防止后款先完成时跨过前款区间。
- 为每次原子领取生成 run_token。撤星重标后即便复用同一个 job id，旧响应也必须因代次不符而丢弃；仅检查 status=running 不够。
- 后台全自动尚未扫描到的新二星，直接为当前照片建任务，不用等待普通扫描循环。
- LM Studio 的 glm-ocr 使用原生 `Text Recognition:`，而不是通用 JSON 指令；不要假造置信度。
- 提高普通 OCR 并发后，识别请求可能与星级 XMP 写回重叠。读图结果校验应在真实文件指纹吻合且已登记的 metadata_versions 链连续时允许元数据变化，真正像素替换仍拒绝提交；测试也要像引擎启动一样先 seed_session，登记路径关联后才能验证这条链。
- 验证文件指纹要沿用 media_engine 的 `json.dumps(...,ensure_ascii=False)` UTF-8 规则；默认 JSON 转义在中文路径下会得到不同哈希，不能因英文路径测试通过就假定可用。

## 验证方式

单元测试用事件保持旧识别未结束，并将普通共享容量限制为 1，确认新请求已进入识别；同时覆盖 4 请求、撤星重标、暂停、去重和乱序区间。

真实验收使用只记录起止时刻的 HTTP 转发器，直接转发本机 LM Studio，不人为延迟响应。旧模型约 1.3 秒即返回，逐项等待 UI 操作会错过重叠窗口；应在同一轮页面事件连续触发多个标星，然后核对请求时间区间、真实 OCR 原文与任务页，不能用人为挂起的响应声称模型真的并发。

任务 077 的安装版实测：旧普通 OCR 加三个新二星共 4 路同时在途，新增请求距同轮事件开始 187／234／281 ms，三个新响应早于旧响应，全部 HTTP 200；四张款号原文正确。82 项相关测试通过，乱序确认时前后款区间仍独立。
