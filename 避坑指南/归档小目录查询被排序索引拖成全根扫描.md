# 归档小目录查询被排序索引拖成全根扫描

## 表现

22 万项归档中，只有 8 项的目录切换也要数秒。实际 `/api/catalog/items` 三次为 8.369、2.468、3.546 秒；并非右侧缩略图解码才开始慢。

## 根因

`capture_items` 包含 JPG/RAW 代表图筛选。将 `root=? AND (folder=? OR folder LIKE ?)` 与 `ORDER BY modified DESC,id` 直接作用于视图，SQLite 选择按根目录的浏览排序索引，先遍历整根目录的大量资料行，再过滤目录。计数查询也可能选择只按根目录定位的索引。

## 解决

- 增加覆盖候选 ID 的 `(root, online, folder COLLATE NOCASE, id)` 索引，支持默认 LIKE 的 ASCII 不区分大小写前缀范围。
- 精确目录与转义后的子目录模式分别查询，UNION 生成候选 ID；CROSS JOIN 强制以候选为外层，通过主键读取原配对视图。
- 保留原外层条件，避免把精确目录匹配意外改成忽略大小写；LIKE 中的 `%`、`_`、反斜杠仍按原语义转义。

## 验证

`test_catalog_folder_latency` 在 1.2 万无关项中查询 8 项目标，使用 SQLite progress handler 约束执行指令预算，防止速度受机器缓存影响而掩盖全根扫描；同时覆盖配对、离线、类型、子目录大小写和分页。完整冻结回归 54 项通过、1 项因公开 RAW 样片缺失跳过。安装后真实目录 HTTP 为 9–181ms，点击到列表更新约 145ms；相邻目录约 104ms，详情见任务 144。

新增索引在大库中只需构建一次；本机安装将它安排在健康检查计时之前。大量历史 WAL 的 checkpoint 可能单独耗时很久，不能将这段磁盘整理时间误判为目录查询回归，也不能仅凭进程存在声称安装完成。


## 2026-11-10：文件名排序索引拖慢后台区间入库

新增 `(online,name DESC,id)` 后，后台 `WHERE path>=? AND path<? AND path>? AND online=1 ORDER BY path LIMIT 2` 也可能误用文件名排序索引。真实 52 万项库的查询计划显示 `catalog_original_order (online=?)` 和 `USE TEMP B-TREE FOR ORDER BY`；1397 张目录只入库 662 张，二星区间迟迟无法闭合。

修正为具名 `(path,online)` 索引 `catalog_capture_paths`，在区间扫描与当前目录可用路径读取处显式指定路径索引。不要只给页面排序加索引而忽略后台扫描的查询计划；小样本的“运行很快”不能证明大库无全表排序。专项验证 `test_capture_scan_uses_path_range_instead_of_global_name_sort` 检查路径范围定位且没有临时排序。

## 2026-11-10：当前目录缩略图准备也需指定目录索引

`ArchiveVisits._visit` 的 `WHERE root=? AND folder=? AND online=1 ORDER BY name DESC` 同样会误用 `catalog_original_order (online=?)`，全库筛选后才进入缩略图循环。24GB真实资料库中，413条目标记录旧查询耗时0.803秒。

显式使用已有 `catalog_folder_candidates`，以 `root、online、folder COLLATE NOCASE` 定位，额外保留 `folder=?` 确保原有大小写语义；同库查询降为0.0012秒。`test_thumbnail_preparation_uses_exact_directory_index` 对实际执行SQL检查查询计划，防止退回全局文件名索引。后台缩略图采用跨目录共用两路池和两项在途窗口，切换后取消未开始的旧任务；不要为每次目录切换创建新池或一次入队全部照片。

另一个独立等待点是HTTP图片返回前调用启动快照写入，其中 `atomic_write` 会 `fsync`；磁盘忙碌时已命中的小图仍需等待。启动副本应通过单线程有界队列后台保存（24项），不将可选持久副本混入图片响应关键路径；`test_http_thumbnail_does_not_wait_for_startup_snapshot_disk_write` 用阻塞写入验证HTTP仍及时返回。
