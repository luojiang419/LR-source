# SQLite 触发器计数与百万队列排序

## 表现

缓存达到百万条后，设置里的实时 COUNT、全量启动核对和待处理任务排序会占用线程；重复绑定可移植别名时，触发器中的 `INSERT OR IGNORE` 还可能意外出现主键冲突。

## 根因与解决

- SQLite 外层 UPSERT 的冲突策略会影响触发器内部插入。可移植覆盖表采用 `INSERT ... SELECT ... WHERE NOT EXISTS`，别名更新时显式维护覆盖，数量触发器与业务写入共用事务，不能只依赖内层 OR IGNORE。
- 待处理队列 `WHERE attempts<3 ORDER BY edge,attempts,requested LIMIT 1` 使用相同顺序的部分索引，并通过 `INDEXED BY pending_active_order` 避免规划器选择含失败记录的全量索引后排序。
- LRU 排序包含文件名作稳定的相同时间次序，索引必须同时覆盖 `(accessed,name)`，否则会创建临时排序。
- 迁移末尾按 `published_seq>? ORDER BY published_seq` 读取增量；不能再按名字排序后过滤发布序号，否则会扫描百万旧记录。
- 启动有限核对并保存游标，运行期按访问校验；数量读维护表，元数据与排队按固定批次释放连接和锁。

## 验证

`test_cache_storage` 覆盖重复别名绑定、计数转换、批次提交、有限启动核对、后台缩容和迁移增量查询计划。`benchmark_preview_scale.py --rows 1000000` 实测百万预览索引与百万生产排队：状态 P95 5.471 ms、领取 P95 26.080 ms、全失败空队列 P95 2.036 ms；队列和 LRU 计划无临时 B-tree。仅 64 张真实 JPEG，不外推为百万原图解码性能。

## 2026-10-23 路径倒排索引与 WAL

增加 FTS 候选后，`root=? ... ORDER BY name COLLATE NOCASE,id` 仍会让 SQLite 选择 `reference_name_page` 并扫描整根目录；50 万文件记录的款号查询仍在数百毫秒。文本查询使用 `+root=?`，让 root 条件继续过滤数据，同时排除它驱动索引选择；候选改走 FTS 虚表与 `catalog_pair`，普通无关键词浏览保留 `root=?`。

`EXPLAIN QUERY PLAN` 必须检查实际完整计数/排序分页，确认有 `VIRTUAL TABLE INDEX`、`catalog_pair` 且没有 `SCAN a` 或名称排序索引整根扫描。`test_fast_path_index` 已纳入真实 `reference_name_page`；50 万记录的 SKU SQL 查询实测从约 217 ms 降至 8.6 ms，完整 HTTP 另行计时。

批次写入的另一成本是反复关闭数据库最后连接触发 WAL checkpoint。为参考目录保留不持有事务的轻量生命周期连接，小批次继续独立提交；同一 1 万张 JPEG 流式验收由约 4.5 秒降至约 2 秒，首批可搜由约 112 ms 降至 48 ms。关闭顺序和完整测量边界见 [任务 084](../开发任务/084-无Everything原生快速索引与搜索.md)。

## 2026-10-28 大量 WAL 导致安装后首次启动超时

表现：引擎启动栈停在 `AssetCatalog.__init__` 的建视图事务中，HTTP 尚未监听，安装器 90 秒健康检查超时。失败桌面退出后，残留的本次引擎仍可能占用可执行文件，导致程序回滚也暂时失败。

现场主库约 3.78 GB、WAL 约 1.75 GB，落盘期间磁盘吞吐受限。不能把初始化等待直接判为数据库损坏，也不能删除非空 WAL、SHM 或数据库来“重建”；尚未 checkpoint 的已提交资料可能只在 WAL 中。

本次处理：确认安装版及本次失败引擎均退出，先用既有 `recover_pending` 恢复一致程序状态，再通过 SQLite 执行 `PRAGMA wal_checkpoint(TRUNCATE)` 并等待返回。现场 155 秒完成、返回 `(0,0,0)`。随后使用既有签名安装协议重试，新引擎约 4.08 秒就绪，826 个程序文件和原业务主键集合核验通过。不要在仍有业务写入时照搬离线维护步骤。

2026-10-29 再次确认同类现场：主库约 4.39 GB、WAL 约 1.27 GB，即使成熟库没有重建视图，最后连接关闭也可能承担已有 WAL 的检查点成本。先恢复 pending 事务、保留五库一致性快照，再离线 checkpoint 与 quick_check；108.625 秒完成，201524 条目录记录数量不变。重试后引擎 3.843 秒就绪，830 文件及原业务主键通过核验。备份后重试应复用本轮已完整生成的快照，不能在应用正在写入时删除 WAL 或复制单独主库。详见任务 116 与 `build/latest-install-20261029/`。

### 2026-10-30：同时消除关闭与提交侧的前台检查点

主库约 7.75 GB、WAL 约 1.02 GB 时，启动再次卡在归档连接关闭。仅设置 `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` 后虽然通过归档初始化，智能检索初始化事务提交仍会触发 `wal_autocheckpoint`，继续阻塞启动。只修改 close 行为或不断延长启动超时都不完整。

归档及共用路径索引连接同时关闭 close-checkpoint 和自动提交检查点；保留事务日志、原同步级别和显式维护。正式服务保留不持有事务的生命周期连接，避免反复初始化 WAL 共享内存。生命周期连接为显式可选，短时工具与原有调用不额外持有文件句柄；引用库沿用原有持有连接的生命周期。

首屏就绪后在独立低资源优先级线程中执行 PASSIVE 检查点，大于 8 MiB 且已合并完成时零等待尝试 TRUNCATE；读者或写者忙碌时稍后重试。4 MiB 是后台触发阈值，8 MiB 是空间回收目标，不能称为长读事务或大写事务期间的绝对上限。禁止通过删除 WAL/SHM 或 `journal_mode=OFF` 消除体积。

验证需要真实异常退出留下 WAL，分别覆盖重启、提交不合并、回滚、显式检查点、后台回收、长读者快照与前台并发。任务 146 最终冻结引擎 62 项、桌面 13 项通过。Windows 普通日志不能用 append-only 文件句柄再 `set_len(0)`，会报拒绝访问；使用唯一后台写入者控制可写句柄位置，并限制当前诊断文件大小。

全速解码的显式选择必须优先于日志压力及常驻监控预算。将 WAL 超过 64 MiB 直接映射为两路并发，会出现“2/2 · 全速”的误导并牺牲用户选择的速度。改为实际首次加载、目录切换请求期间暂停新领取，请求结束后自动恢复；持续的归档预览及状态轮询不进入该保护。回归须验证日志压力加监控时真实四路领取，以及前台结束后队列继续，不能只断言预算字段。

归档列表不得由默认定时器持续重建。进度/ETA 使用独立状态轮询，素材列表在进入、切回页面及用户显式操作时更新，并保留分页、滚动、选中项和已加载图片节点。原每两秒列表刷新会误入目录查询的前台保护，导致静置页面也反复显示“等待前台操作结束”；即使速度样本真实存在也丢失 ETA。短暂让路继续按墙钟完成速度估算，只有手动暂停或样本过期才停止估算。验收应观察跨越两个刷新周期的网络请求与 DOM 变化，而非只看截图；同来源图片重新登记时也不能取消仍有效的请求。

Python 3.12 本地 HTTP 服务默认监听等待队列只有 5；工作台图片和状态突发建连时可能额外等待 TCP 重传。扩大到 128 后，以 accept 循环未开始时 32 个真实连接全部建立验证，而不是只检查常量。

依据：[SQLite 连接关闭行为](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html)、[SQLite 检查点与空间限制](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint)、[Windows 后台资源优先级](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setthreadpriority)。现场结果见任务 146 与 `build/catalog-wal-startup/`、`build/catalog-full-speed/`。

本地增量安装仍须包含校验器规定的主程序、引擎、更新器、更新 worker 和 `update-config.json`，不能仅按字节变化挑选载荷而遗漏必要组件。全过程记录见 [任务 131](../开发任务/131-归档解码数量与剩余时间.md)。

## 2026-10-28 前台浏览与预生成连接开销

真实后台负载下，快缓存仍可能被三类无效工作拖慢：成熟参考目录每三秒在列表 GET 内全层重扫、ready任务无条件重写、缓存maintenance完成误发cache-imported重发尚在加载的缩略图。要同时检查前端HTTP排队和后台索引锁，不能只优化JPEG解码。

修复采用成熟目录只读查询（新子目录仍可补齐）、无变化ready UPSERT不写入、恢复16项分批让路、仅import/migrate重试真正失败图。滚出视口的请求取消后须检查回调身份，旧onload/onerror不能完成新的同元素请求；暂停时也须清理重试标记。

每张预生成原先约17次SQLite开关连接，连接/PRAGMA/close成本远高于SELECT本身。仅在warm_previews单张图片的generation门内暂存线程私有连接，两个尺寸和两类缓存复用；每次connect上下文仍独立提交/回滚，嵌套调用用独立连接。图片退出时先关闭连接再释放generation门，无长期池、无跨线程共享。64次开关取代原544次，事务退出仍544次；迁移、异常、嵌套回滚与并发测试均须覆盖。

容量充足时publish不应强行刷新两库全部访问时间；只有真正选择LRU淘汰对象前才刷新，原有5秒/256次触碰批量写入规则和跨目录最近访问保护继续有效。不能通过取消哈希、归属检查、原子发布或降低业务库同步等级来换速度。最终验收数据见任务135及build/response-performance。

## 2026-10-29 搜索必须先缩小候选，宽词有界回退

新增`intelligence_catalog_order(online,...)`后，SQLite可能先扫描在线items再访问FTS。正式库约20万记录的精确文件名搜索，即使只有7–11项结果，完整items(count+列表)也耗时约1.8秒。只给外层加UNION候选仍可能更慢，必须检查候选子查询自己的EXPLAIN。

路径FTS先CROSS JOIN items；元数据只有在FTS可用时才固定候选优先，短词保留原JOIN。items/tree先探测最多512个唯一pair_key，窄查询由候选驱动capture_items，再按原SKU/路径/元数据/visual条件精确复核，防止非代表RAW的SKU或视觉结果改变匹配。候选与最终count/分页共用读取快照。

宽词先在实际使用的FTS上直接读取至多513行，不JOIN原记录；超过上限立刻回退原查询，不为探测而完整物化大集合。此门允许保守回退，绝不截断业务结果。短词、NUL走原路径。真实库精确查询约60–69ms、整行和总数相等，宽词和单字中文仍保留原有秒级成本，不外推成所有搜索即时。65项冻结相关回归通过；3项LAN UI超时在HEAD基线同样复现，未作为本次SQL优化通过项。

## 2026-10-29 热回滚日志导致只读核验失败

安装前对sku.sqlite3执行只读SELECT时报“attempt to write a readonly database”，文件本身未设置只读属性，旁边有12824字节回滚journal。本次是SQLite需要先恢复未完成事务，并非表已损坏。

确认应用不在写入后，将数据库与journal完整保存，原始备份不打开；在另一份验证副本上用SQLite正常连接执行标准恢复与quick_check。验证成功后才对原库执行同样的SQLite恢复，并核对恢复后的全文件SHA-256和表计数与验证副本一致。不要手工删除journal/WAL来绕过错误。原文件与日志备份保留，具体现场记录见任务135及build/catalog-search/sku-recovery。
