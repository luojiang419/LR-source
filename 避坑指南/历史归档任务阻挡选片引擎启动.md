# 历史归档任务阻挡选片引擎启动

## 表现

桌面提示“选片引擎启动超时”，引擎进程仍存在，端口已绑定但 HTTP 健康检查不响应。空数据库测试正常，带活动拍摄流的现有数据库可以复现；单看 engine.log 未必有异常。

## 根因

`server.main` 在完成共享评级初始化之前启动 `AssetArchive` 后台线程。后台 `sync_stream → ensure` 持有归档锁进行照片路径解析、哈希或元数据读取；主线程首次访问懒加载的 `ARCHIVE.ratings` 也需要同一把锁。主线程停在等待锁阶段，未进入 `serve_forever`，触发桌面的 30 秒超时。

## 解决

创建归档服务后、启动任何使用归档的后台服务前，先初始化共享评级并播种已有会话；配置完其他服务和回调再启动归档线程。既不依赖历史照片处理速度，也无需延长启动超时或清空用户数据库。

## 验证

`test_engine_startup.py` 用真实隔离数据库及 HTTP 健康检查，让归档线程一直持锁，确认引擎仍能就绪且四星评级保留。修复前顺序稳定失败，修复后通过；连同生产和共享评级共 44 项回归通过。本机原有数据发行版首屏 1884 ms，健康检查正常。详见 `开发任务/057-选片引擎启动超时修复.md`。


## 2026-10-26：大库初始化的重复全表扫描

桌面快捷方式与根目录启动器可能使用不同资料库。本机实际安装库约 2 GB，必须按快捷方式目标验证。

`AssetCatalog` 不能每次启动按每个扩展名 UPDATE 全表；使用版本化的一次性迁移，并仅更新不同值。`PreviewWarmer` 实际生成尺寸已固定为 2048 时，不要为重写旧任务 edge 再扫描 13 万项队列；保留原字段作为领取版本条件即可。元数据核对属于后台恢复，不在 start 调用方同步更新全库；放到共享评级初始化之后恢复，避免争抢磁盘。参考库只为未接管目录计算初始统计。

31 项相关回归通过；最终实际冻结版 HTTP ready 5.000/6.859 秒，运行健康响应 31ms。首屏 DOM ready 仍 43–46 秒，需与引擎就绪分开记录，不能用 HTTP 健康时间证明照片首屏速度。日志已有 `[startup]` 分阶段耗时。详见任务 057。


## 冷启动必须使用独立就绪接口

桌面不能用读取业务数据库、等待 Store.lock 的健康查询来判断进程是否启动成功。新增 `/api/ready` 只返回当前服务 PID 与 ready，直到服务全部初始化并开始接收 HTTP 后才可响应；原 `/api/health` 保留业务含义。

固定 30 秒会误判首次升级或冷启动。按本进程真实阶段推进等待，同时保留每阶段 60 秒与总计 180 秒的限制；旧 PID、同阶段重复写入不可续期。启动页通过有权限的 Tauri 命令显示中文进度，须同时注册 build.rs 自定义命令、capabilities 权限以及 IPC CSP。

实际 release 桌面配合隔离测试引擎，延迟 35 秒且业务健康接口不响应，最终 36.657 秒首次进入页面；Python 33 项、Rust 6 项通过。正式安装版 11.985 秒提供服务，页面首载仍慢，不能混用两种指标。慢启动从 data/engine-startup.json 和 engine-startup-stacks.log 看阶段与主线程堆栈；截图本身不能确定故障机的精确阻塞点。

## 2026-10-28：无条件 DDL 让启动承担 WAL 提交成本

同一正式资料库（约 4 GiB、200779 条归档记录），旧 `AssetCatalog` 在每次启动时 `BEGIN IMMEDIATE → DROP VIEW → CREATE VIEW → COMMIT`。逐语句现场测量提交占 23.157 秒，历史启动日志达 51.282 秒。SQLite backup 后的 G 盘副本仅需 32ms，说明热副本不能代替正式磁盘/WAL 状态的验证，也不能把单次最快旧启动当稳定基线。

成熟库启动应读取 `sqlite_master` 比较视图定义，只有定义变化才事务替换；路径索引状态先 SELECT，缺失才 `INSERT OR IGNORE`，既避开日常写锁，也保留并发首次初始化的幂等性。缓存按结构版本标记跳过重复迁移，文件核对/旧策略退役放到首屏后的后台，16 项分批且可取消；实际读取和删除的完整性验证不能省略。后台启动函数不能再调用可能等维护锁的 `state()`。

最终冻结 104 项回归通过；并发幂等补强后受影响 12 项冻结复测通过。正式目录同库资产初始化约 16ms。安装代码在正式资料库上三轮完全撤除启动遮罩 1.94–2.49 秒（为保护原片，后台写回暂停）；原生安装程序在隔离本地照片库启用正常后台时首屏 3.169/1.749 秒。两种测量边界必须分开描述，不能声称已测重启电脑后的冷盘启动或 Lightroom 同条件上限。完整证据见任务 135 和 `build/startup-catalog/`。


## 2026-10-30：大 WAL 冷恢复与维护 I/O 优先级

实际安装版连续启动失败，堆栈停在 `AssetCatalog.__init__` 的首连接 `PRAGMA journal_mode`，残留 WAL 为 5748817312 字节。SQLite 即使禁止关闭检查点，也仍需在首次访问时恢复 WAL 共享索引；不能把首连接恢复误认为后台已在回收。离线复制会预热磁盘缓存，复制后的打开耗时不能当成原始冷启动成绩。

Windows `THREAD_MODE_BACKGROUND_BEGIN (0x10000)` 不只降低 CPU，还降低磁盘和内存优先级；持续全速写库时可能使维护长期饥饿。WAL 维护改为 `THREAD_PRIORITY_BELOW_NORMAL (-1)`，保留普通 I/O 优先级。PASSIVE 仍零等待，超过 64 MiB 后 TRUNCATE 可在维护连接最多等锁 250ms；长读者仍返回 busy 后重试。退出时先停止业务生产者，再关闭 WAL 维护，避免停止回收后继续产生最后一批写入；不修改全速解码预算。

处理现场大 WAL 时先确认软件和引擎均已退出，将主库和 WAL 成对保存到软件目录外的恢复副本，然后执行 SQLite `wal_checkpoint(TRUNCATE)`、`quick_check` 和记录数核对。禁止直接删除 WAL、设置 journal_mode=OFF 或把恢复副本打进安装包。正常写入仍会短暂生成事务 WAL，不能把运行期间文件存在等同于垃圾，也不能承诺在长读事务或强制断电时恒为零。

新增 Windows 真实线程优先级与回收回归；引擎退出顺序用业务生产者关闭时维护尚未关闭的断言覆盖。历史预览全量恢复必须按 keyset 分批，先关闭读连接再入队或等待暂停；一个包住全库的 fetchmany 游标仍会持有数小时旧快照。真实 300 组配对恢复期间并发写入与 TRUNCATE 均可成功。最终源码及冻结各 38 项通过，补强等锁上限后专项各 10 项通过。现场恢复和安装验证详见任务 146 与 `build/wal-recovery-20261030/`。

## 2026-11-19：构造对象不等于可同步全库聚合

安装版一次约277秒停顿的重复堆栈全部落在参考库构造函数的 capture_items 计数。根目录对象登记可同步完成，配对全库统计移到 start 后后台执行，查询设置退出 progress_handler；活动会话 seed_session 也归入既有 historical-ratings 后台。仍需在启动归档线程前构造共享评级对象，不能把对象初始化与历史全量播种混为一步。专项确认构造时不执行配对聚合，后台最终计数正确；未重启系统/清空文件缓存，不能拿小库或复制后数据宣称生产冷启动p90达标。

## 2026-11-19：真实冷缓存复测与右删失样本

同盘复制生产目录库（约24GB）后，每轮先清系统文件缓存工作集再清standby，API成功才计为冷启动；启用的现有进程权限结束后恢复，不需要关闭用户程序或重启系统。原版/优化版各10轮HTTP就绪p90为11.032/9.531秒，最大23.515/12.750秒；中位数约8.766秒不变，catalog阶段尾部略增，不能称所有阶段变快。复制、热读或单纯启动新进程均不能替代清待测文件缓存。

清除隔离参考库的已接管roots后，原版同步capture_items聚合420秒仍未就绪，堆栈确认原位置；记录为>420秒，不捏造完成时间或p90。优化版同场景两次8.750/9.953秒HTTP就绪。构造阶段通过不代表后台全库计数已完成；只报告实际验收边界。工具与证据见任务244及tools/verify_performance_244.py。
