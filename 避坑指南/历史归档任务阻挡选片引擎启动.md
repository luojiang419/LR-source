# 历史归档任务阻挡选片引擎启动

## 表现

桌面提示“选片引擎启动超时”，引擎进程仍存在，端口已绑定但 HTTP 健康检查不响应。空数据库测试正常，带活动拍摄流的现有数据库可以复现；单看 engine.log 未必有异常。

## 根因

`server.main` 在完成共享评级初始化之前启动 `AssetArchive` 后台线程。后台 `sync_stream → ensure` 持有归档锁进行照片路径解析、哈希或元数据读取；主线程首次访问懒加载的 `ARCHIVE.ratings` 也需要同一把锁。主线程停在等待锁阶段，未进入 `serve_forever`，触发桌面的 30 秒超时。

## 解决

创建归档服务后、启动任何使用归档的后台服务前，先初始化共享评级并播种已有会话；配置完其他服务和回调再启动归档线程。既不依赖历史照片处理速度，也无需延长启动超时或清空用户数据库。

## 验证

`test_engine_startup.py` 用真实隔离数据库及 HTTP 健康检查，让归档线程一直持锁，确认引擎仍能就绪且四星评级保留。修复前顺序稳定失败，修复后通过；连同生产和共享评级共 44 项回归通过。本机原有数据发行版首屏 1884 ms，健康检查正常。详见 `开发任务/057-选片引擎启动超时修复.md`。


## 2026-10-26：大库初始化的重复全表扫描

桌面快捷方式与根目录启动器可能使用不同资料库。本机实际安装库约 2 GB，必须按快捷方式目标验证。

`AssetCatalog` 不能每次启动按每个扩展名 UPDATE 全表；使用版本化的一次性迁移，并仅更新不同值。`PreviewWarmer` 实际生成尺寸已固定为 2048 时，不要为重写旧任务 edge 再扫描 13 万项队列；保留原字段作为领取版本条件即可。元数据核对属于后台恢复，不在 start 调用方同步更新全库；放到共享评级初始化之后恢复，避免争抢磁盘。参考库只为未接管目录计算初始统计。

31 项相关回归通过；最终实际冻结版 HTTP ready 5.000/6.859 秒，运行健康响应 31ms。首屏 DOM ready 仍 43–46 秒，需与引擎就绪分开记录，不能用 HTTP 健康时间证明照片首屏速度。日志已有 `[startup]` 分阶段耗时。详见任务 057。


## 冷启动必须使用独立就绪接口

桌面不能用读取业务数据库、等待 Store.lock 的健康查询来判断进程是否启动成功。新增 `/api/ready` 只返回当前服务 PID 与 ready，直到服务全部初始化并开始接收 HTTP 后才可响应；原 `/api/health` 保留业务含义。

固定 30 秒会误判首次升级或冷启动。按本进程真实阶段推进等待，同时保留每阶段 60 秒与总计 180 秒的限制；旧 PID、同阶段重复写入不可续期。启动页通过有权限的 Tauri 命令显示中文进度，须同时注册 build.rs 自定义命令、capabilities 权限以及 IPC CSP。

实际 release 桌面配合隔离测试引擎，延迟 35 秒且业务健康接口不响应，最终 36.657 秒首次进入页面；Python 33 项、Rust 6 项通过。正式安装版 11.985 秒提供服务，页面首载仍慢，不能混用两种指标。慢启动从 data/engine-startup.json 和 engine-startup-stacks.log 看阶段与主线程堆栈；截图本身不能确定故障机的精确阻塞点。
