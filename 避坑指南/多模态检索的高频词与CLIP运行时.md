# 多模态检索的高频词与 CLIP 运行时

## 高频中文词命中越多反而越慢

表现：百万条合成库中 SKU 查询约 6 ms，但“红色”和组合维度超出 2 秒 SQL 预算。

根因：先展开高频全文词的数十万 ID，再排序；媒体视图和跨表版本验证放大成本。短词又无法使用 trigram，提前扫描路径/元数据增加耗时。

解决：添加 `(online,modified DESC,id)` 有序索引，先按顺序取当前页；FTS 同时索引资产 ID 和关键词，每个候选使用罕见的资产 ID 与高频词做交集核验。组合维度沿当前候选做同帧检查；单字中文只检查该资产的索引文本。最终页再批量取完整资料，分面建议按 `(key,normalized)` 跳到下一个不同值，避免整库计数。

验证：最终百万条库中，SKU 5.69 ms、中文词 18.65 ms、组合维度 4.25 ms（中位，五次）；无超时，quick_check=ok。复现脚本为 `选片助手/benchmark_intelligence.py`，详细条件见验证记录，不能将此数值等同包含模型、网络盘和缩略图的端到端耗时。

## 归档短词与全量统计不能沿用只取当前页的优化

表现：归档搜索“蓝”“春夏”返回很少的结果，但完整 items 请求仍耗时约 7 秒；精确文件名搜索很快。这里的归档接口需要准确总数和全部命中目录，与上面的多模态检索分页接口不同。

根因：短词不适用 trigram，优化器从素材排序索引逐项关联大段元数据；COUNT 与当前页又各执行一次相同文本筛选。本次 200779 条历史库中 search_text 总长度约 9.9 亿字符。简单将宽词全部展开为 UNION 候选，反而增加物化、去重与配对成本。

解决：元数据使用 CROSS JOIN 固定先过滤文本、再按主键验证素材版本。宽词/短词一次筛选，仅将 id、modified 放入 MATERIALIZED 集合，供总数和当前页复用，再按页内主键读取完整字段。LEFT JOIN 保留零命中和越界页的总数；所有搜索在索引 ready 检查前开启读取事务。精确词继续有界候选路径，不新增持久索引。

验证：同一只读历史副本前后交替三轮，完整响应与目录树相等；“蓝”中位 6933→2349ms，“春夏”7353→2444ms，`.CR3` 2149→1244ms。源码 68 项通过，覆盖 520 对素材分页、手动代表、旧元数据、无 FTS、空页与并发快照。真实页面还同时请求目录树，短词交互约 4.2–4.4 秒；不能将单 SQL 耗时当成页面耗时。证据与限制见任务 135 及 `build/catalog-search-broad/`。

## 列表 SQL 变快后，页面仍被重复请求拖慢

表现：单次短词查询约 2.4 秒，实际搜索页面仍约 4 秒；每次改词分别请求列表、目录树和全库资料统计，旧 HTTP 中止后数据库查询还可能继续占用资源。

解决：items 可附带 tree，同一事务只筛选一次全局命中集合；目录统计保持全局，列表另加根、目录、SKU 与游标约束。非空输入只刷新这份响应，全库统计仍由正常后台刷新。每个页面独立随机标识和递增序号，迟到请求拒绝，SQLite progress_handler 取消同页旧查询，断线使用不消费数据的 MSG_PEEK 检查；退出时解除回调并关闭读事务。不要让不同页面互相取消。

验证：真实双页面覆盖快速改词、查询中清空、离开、关闭和失败后保留旧结果；历史大库五轮旧查询取消约 0.76–1.98ms。固定 606bdf0 对照中，实际页面“春夏”4246→2958ms、.CR3 2275→1570ms，结果和全局目录统计相同。均为本机样本，不是任何 SQL 的取消硬上限。

测量注意：不要在浏览器已打开后，使用同一个 Playwright 同步线程执行耗时 SQL 来算预期值；这会阻塞事件处理，使周期刷新与下一次输入集中发起。先计算预期值，再打开页面；用实际请求日志区分 SQL、全库统计和测试夹具造成的耗时。首轮“7–9 秒”诊断数据不作为最终页面性能结论。证据位于 `build/catalog-search-shared/`。

## 已安装 CLIP 有文件但初始化卡住

表现：旧 MaterialSearch Python 的 transformers 扫描大量无关模型模块；其他环境加载时又在 GPU `.to()` 处长时间等待。

根因：无关框架初始化、版本差异及共享显存资源争抢，不能仅凭模型文件存在判定可用。

解决：独立常驻进程，优先使用已有可用的开发 Python，模型只从本机读取；设置 `USE_TF=0`、`USE_FLAX=0` 和离线模式。默认 CPU 4 线程，与 Qwen/GLM 及媒体 GPU 队列分离；需要 GPU 时显式设置 `FRAMEKEEP_CLIP_DEVICE=cuda`。加载和推理均有超时与进程回收。

验证：图片与中文文字均实际生成 768 维向量，范数约 1，含启动约 10.52 秒；真实 HTTP 目录解析、以图搜图和语义搜索完成，参考图自相似度为 1。

## transformers 特征返回类型不统一

表现：`get_image_features()` 返回 `BaseModelOutputWithPooling`，直接 `.norm()` 报错。

解决：兼容 Tensor 和 `.pooler_output` 两种返回，之后执行单位化与维数校验。不能用任意维度的占位向量掩盖错误。

## Windows SQLite 备份句柄没有关闭

表现：测试结束清理临时目录时出现 WinError 32。

根因：`with sqlite3.connect(...)` 只管理事务，不关闭连接。

解决：备份目标使用 `contextlib.closing`，读取验证同样显式关闭。已通过在线备份、quick_check 和临时目录清理测试。

## Windows 模型子进程的中文错误中断 JSON 通信

表现：正常 JPG 检索成功，遇到坏图后父进程 reader 出现 `UnicodeDecodeError`，状态轮询超时。

根因：父进程按 UTF-8 读取，Windows 子进程默认代码页输出中文 JSON；普通 ASCII 路径无法暴露该问题。

解决：独立 worker 启动时使用 `-X utf8`，设置 `PYTHONUTF8=1 / PYTHONIOENCODING=utf-8`，stdout 明确 UTF-8；只接收字典型 JSON 行，读取异常也向请求队列返回错误。打包时显式加入脚本目录，兼容原项目内嵌 Python 的 `_pth` 隔离路径。

验证：真实模型复制图片、坏图单独失败、修复重试、持续检索均通过；MaterialSearch 自带 Python 按冻结布局运行通过。见任务 232。

## 独立图库整数 ID 复用导致旧结果指向另一张图

表现：删除最大 ID 的图片再添加新图片后，SQLite 可能重用该整数；仅以 `material:整数` 定位会让旧卡片读到新文件。

根因：原库整数主键只标识当前记录，不能独立承诺旧搜索结果的文件身份。

解决：保留原表结构，在宿主不透明结果标识中加入规范化原路径和 size/mtime 版本摘要；预览、继续搜图及详情定位时重新校验，变化后要求重新搜索，不把 LR 资产 ID 当原图库 ID。

验证：真实原生文件通知完成删图、换名加图和整数复用，旧标识明确被拒绝，原库仍只有四张表。见任务 232 的浏览器生命周期用例。

## 同图排第一不等于整页检索结果相关

表现：原图排第一，但搜索裤子时出现无关 Logo。数据库确有对应特征，不能仅凭这个现象认定未建库或错误解码。

根因：前端默认相似度 50%，请求后端又固定传 0；样本中裤子与 Logo 的余弦约 0.547，因而被放行。CLIP 余弦分数不是同款概率。旧测试只检查同图首位，还错误地把全部候选返回当作正确预期。

解决：按原项目图片默认 85% 统一前后端，文字阈值单独保留；滑块降低时重新请求候选。逐图核对 checksum、向量维数/范数，并使用直接模型 API 从原图复算；同时验证不同视角正例、Logo 负例、Logo 自身正例和空结果，不按文件名屏蔽 Logo。

验证：7 张测试图的 768 维向量复算最大逐元素差为 0；默认裤子返回 6 张相关图、不含 Logo，Logo 查询只返回自己，界面截图返回空。新截图等待图片与动画完全显示后再保存。见任务 232 相关性纠正记录。

## 内容相似不能当成画面一致

表现：无手正面参考图检索到同款带手、侧身照片，CLIP 内容分仍有 0.95–0.98。仅检查同款或提高内容门限不能证明画面细节符合目标。

根因：CLIP 整体内容召回和用户要求的近似画面没有区分，测试把同款不同姿态也当成默认正例。

解决：明确区分“近似画面”和“相似内容”。前者默认在原向量召回后，对实际预览做小幅局部对齐与颜色/结构比较，显示画面分，保留内容分用于说明；后者保持原语义功能。数据库继续原四表，细节特征仅作有界缓存；无法核验不退化成无提示的语义匹配。要做通用手/姿态属性检索，需要另外的模型和评估，不能把结构分数称作分类结果。

验证：真实页面默认只返回三张无手正面；未入库的新正面图同样返回三张；带手、侧身反向查询各找到自身。21 项联合验证通过，原项目自带 Python 也通过。见任务 232 的画面匹配记录。

## 完整冻结环境的模型进程必须使用干净运行目录

表现：源码和手工模拟冻结布局均能检索，真实 PyInstaller EXE 开启建库却报 `cannot import name JSONDecodeError from simplejson (unknown location)`。

根因：外部 Python 把冻结包根 `_internal` 加入 sys.path，该处可能只有包的扩展/数据目录，Python 源码在 PYZ 中；外部解释器把残缺目录视为命名空间包，导致可选依赖被误识别。直接将同一路径插入原 MaterialSearch Python 后导入 Requests，可以复现。

解决：只向外部 Python 暴露单独 `material-search-runtime`（完整 helpers 与 vendor），清理继承的 Python/PATH 路径；在模型子进程内恢复 Windows 默认 DLL 搜索，不在多线程主进程里全局切换。参见 [PyInstaller 官方外部进程说明](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html#launching-external-programs-from-the-frozen-application)。用实际冻结 EXE 测试，不能只验证临时源码目录。

验证：任务232的最终发行与实际安装版，真实内嵌模型 Python、独立测试库和浏览器全部通过。

## 验收执行产生的字节码不能进入签名程序包

表现：冻结验收通过后，签名打包因 worker 目录中的 `__pycache__/...pyc` 被安全路径规则拦截。

根因：外部解释器默认向程序资源目录写缓存，原源码 vendor 的缓存也可能被整目录复制；手工清理一次不能保证后续运行或打包不再出现。

解决：真实启动命令用 `-B`，环境与 worker 同时禁用字节码写入；生成运行目录时只收集规定 helpers、`.py`、LICENSE、SOURCE.json，不删除源目录缓存，也不降低签名包路径检查。新增真实子进程不写缓存及白名单收集测试。

验证：21项运行/画面核心单测通过；冻结版运行、签名安装及安装后浏览器均通过，程序运行目录无新增字节码。正式安装963文件哈希通过，原资料保留。见任务232安装交付记录。
