# GPU 预览同步与 NVENC 驱动兼容

## CPU 像素上传后偶发黑图

- 表现：CUDA 调用返回成功，缩放尺寸正确，但单线程或并发结果偶发全黑；PSNR 约 6 dB。直接 nvJPEG 解码后在同一 CUDA 流缩放正常。
- 根因：可分页主机内存通过同步 HtoD API 提交默认流后，另一个非阻塞 CUDA 流不隐式等待默认流的实际传输完成；主机调用返回不等于所有相关 GPU 流都有顺序依赖。
- 解决：CPU 图片/JPEG 编码上传后显式等待默认流，再在独立流启动内核；输出下载前等待相应计算流。nvJPEG 解码、缩放保持同一流。不要只检查 CUDA 返回码就认定像素已就绪。
- 验证：`test_gpu_media` 覆盖并发线程、十二张输出、CPU 参考像素与八种方向，实际 RTX 4070 Ti SUPER 通过；冻结引擎的 PNG 像素缩放及原片哈希也通过。

## FFmpeg 列出 NVENC 却不能编码

- 表现：FFmpeg `-encoders` 包含 h264_nvenc，但执行报 Required API 13.1 / Found 13.0，提示需要驱动 610.00；本机 580.97 无法使用 FFmpeg 9.0.2 的该编码器。
- 根因：编译时包含编码器不代表当前驱动支持对应 NVENC API。过小测试画面还会额外触发最小尺寸错误，不能据此判断整块显卡不可用。
- 解决：配套固定 SHA-256 的 FFmpeg 8.1.1 兼容组件，并以 256×144 的真实 CUDA 上传/缩放/NVENC 编码探测能力；不擅自更新系统驱动。视频按实际像素格式选 NVDEC，专业编码使用 CPU 解码后上传；准备失败时在发送 MP4 第一段前回退。
- 验证：4070 Ti SUPER / 580.97 实际通过 CUDA 解码、缩放、NVENC、ProRes 上传编码及 GPU 初始化失败后的 CPU 回退。端到端通过冻结引擎和浏览器验证，详见任务 106。

## nvJPEG 混合解码接口与质量

- 只有默认单阶段 nvjpegDecode 时，CPU 熵解码仍可能成为瓶颈。GPU 混合后端使用 Host → TransferToDevice → Device 分阶段接口，并为状态明确连接固定内存与设备缓冲；否则传输可能返回 INVALID_PARAMETER。
- 解码会话与缓冲限定为两路并复用。使用插值色度上采样，严格校验码流；渐进或不支持的 JPEG 回退 nvJPEG 兼容路径，再回退 Pillow。
- 与原 CPU JPEG draft 路径比较时，另取全尺寸 CPU 解码作为质量参考。不能把缩略解码和全尺寸解码的像素差异直接解释为 GPU 质量变差；基准必须同时标明尺寸、缓存、压缩与读盘边界。
