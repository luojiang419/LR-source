# SQLite 短词倒排与首屏统计分离

## 表现与根因

49 万文件、约 9.75 GB 的真实归档库，已有 FTS 和图片缓存，`XSY / 2026 / .CR3 / 蓝 / 春夏` 仍触发搜索预算错误。图片列表出现前等待数秒，易被误认为缩略图缓存无效。

- trigram 无法直接检索一、二字词，普通 `instr(lower(search_text),...)` 会读取整库大段 EXIF 文本。
- 宽泛词的完整候选 UNION、全量排序、COUNT 和目录分组会阻挡首屏，即使只显示 60/120 条。
- `OR length(search_text)<3` 同样会让未命中的点查读取大文本；不要把“只计算长度”当成廉价操作。
- 按字段触发的 UPDATE 也会在新旧值相同的 UPSERT 中触发，必须额外比较真实文本变化。
- 图片 HTTP 与列表查询是两条路径：本例 9 张实际 JPEG 缓存只需约 7–31ms；旧页面列表等待约 4534ms，18 张图在列表出现后约 12ms 已就绪。

## 已验证的处理

1. 后台从现有 trigram 词典建立 `(source,fragment,gram)` 主键映射，另登记小于三字的文档。前台不重复遍历 `fts5vocab`；本例元数据词典即便仅约 3.9 万词，逐次读取仍需约 12 秒。
2. 倒排候选按主键/配对索引驱动记录；密集词尝试沿时间索引点查并取满一页，稀疏词小预算后退回候选查询。SKU 优先级、代表图和游标条件不可省略。
3. 列表首屏与准确全局统计分离，空搜索词也应有界取页。统计复用必须有范围键和过期时间；新词与页面退出取消旧统计，同词刷新不能一直打断同一慢统计。
4. 触发器只登记真实文本变更，队列读取、更新和清理使用同一短事务；搜索同快照覆盖未处理的 dirty 行，避免增量尚未完成时漏掉新内容。短文档候选仍需复核当前文本，不能让旧索引造成假命中。
5. 无视觉服务的目录模式也要安装时间排序索引；不能让测试只在完整多模态服务已经初始化后通过。
6. 快捷文件检索不能在每次按键后回查几千条大库主键。本例 7877 的倒排只需约 12ms，但 7797 个首次主键读取约 1854ms；同批热读约 88ms，容易被假性能结论掩盖。最终将字段、FTS、短词与 scope 全部放在 SSD 独立小库，按键查询不打开主库；只把字段迁走、仍附加大库倒排，也会在繁忙时拖慢首次查询。
7. 持久副本先提交再确认 dirty 行，确认时比较源值防止覆盖期间丢更新；结果缓存按副本代次及根状态失效。复用读取连接必须清除旧取消回调并结束所有附加库读事务，避免缓存性能优化重新造成 WAL 无法回收。
8. 即使后端1ms返回，旧图片请求占满浏览器六条同源连接，新输入的请求也可能发不出去。清空 DOM 不足以保证请求停止；新查询/关闭时显式移除旧 img src，必须用真实 HTTP 保持六条图片连接的回归验证。
9. 短预算中断后从头重试没有累计进度，宽词可能永久等待。2026-11-03 真实 LC 连续三次 pending，9600 首查约 1363ms。独立索引后台预热到 RAM、增量同步并去掉查询后的主库预览地址补充后，77 个不同输入首查 P95 31.08ms，安装 HTTP P95 39.64ms。仍保留取消和终止预算，禁止把无限 pending 当作成功。
10. 性能记录必须对应当前源码与安装载荷。此前已通过的内存镜像被后续提交移除后，旧同词百轮热缓存报告不能证明新版速度。验收应包含不同词首查、无结果、真实 HTTP、输入到卡片，以及单独的真实图片就绪时间；记录 RAM 和重启预热代价。镜像必须同步 OCR/范围并在增量失败时丢弃，不能继续返回旧资料。
