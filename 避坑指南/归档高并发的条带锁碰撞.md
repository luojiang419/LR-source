# 归档高并发的条带锁碰撞

## 表现

提高归档预览线程数后，不同图片仍相互等待。16 个图片任务的重叠验证无法全部进入解码，即使 CPU、预览槽和后台槽都充足。

## 根因

`media_engine._preview` 原来把预览缓存 key 映射到 64 个固定锁。不同预览命中同一条带时，等待者必须等另一张图解码和编码结束；线程数越多，碰撞越明显。用同步屏障验证全部任务同时进入时，还会因这种隐含串行等待而超时。

## 解决

- 按完整预览 key 提供独立锁，同一预览仍然互斥；不要仅增加线程数或用测试替身移除生产锁。
- 用受保护的 `WeakValueDictionary` 保存锁，正在执行和等待的调用持有强引用。最后一个使用者结束后自动回收锁，避免每个历史缓存文件永久占用一个锁对象。
- 后台与前台共用此锁机制，避免同一尺寸重复生成；解码容量继续由全局硬件预算和 semaphore 约束。

## 验证

- 生产归档添加流程实际达到至少 16 张不同图片同时解码，生成全部双尺寸缓存，失败 0。
- 两个同前缀、不同完整 key 同时取得锁；1000 个用完的锁均自动从字典移除。
- 既有前台／后台并发请求同一预览仅生成一次的回归通过。
