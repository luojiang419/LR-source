# EOS 重复激活与新图预览排队

## 2026-10-28：业务 HTTP 连接占满也会拖住原图

- 表现：原图接口单独测只有数毫秒，但实际窗口仍慢；业务请求超时、两个长轮询和图片都使用同一个 HTTP/1.0 来源。浏览器同来源连接达到上限后，图片在请求发出之前排队，仅把 Python 的图像处理移出状态锁不能消除这段等待。
- 证据：六个真实 HTTP 请求保持阻塞，709 字节图像在 1500ms 内仍不能加载；ResourceTiming 的 requestStart 比 fetchStart 晚约 1513ms。应记录网络排队与服务/解码/绘制分别耗时，不能把一次 warm GET 当成快门响应。
- 解决：原图通知和原始字节使用独立 loopback 来源；只允许主工作台准确 Origin、事件凭证和不透明原图 URL，CSP 开放这个确定端口。跨来源 Image 必须先设置 anonymous，服务器精确返回 CORS，直方图的二次 Image 加载也要设置，避免 Canvas 被污染。
- JPG 很快入库时也不能直接丢掉最新图像地址；浏览器在入库后才查询仍需取到可显示主图。保留 latest，正式 ID/RAW 别名完成接续，目录切换和停止清理。
- 验证：六个业务请求仍阻塞时，原始 3600×2400 主图约 319ms 内绘制；跨来源 Canvas 可读取；迟到查询、凭证与路径边界测试通过。它是可控压力测试，不能冒充实拍或 DPP 计时。


## 2026-10-28：清晰主 JPG 直通替代小图首显

- 用户明确拒绝先显示模糊 EXIF 小图；下方内嵌预览是已被替代的历史方案。原始 JPG 显示必须独立于正式入库，不能仅移除固定延时后仍等待元数据、像素校验或资料锁。
- `DirectJpegFeed` 使用独立目录通知、短状态锁及长轮询；HTTP 直接传主 JPG 原始字节，浏览器处理原生 load/error，文件长度增长只作为传输更新信号，不据此判断完整性。不提取内嵌图、不重编码、不等待排他句柄。
- 正式接续、重渲染和手动返回都要使用 `previewFull`，否则清晰直通画面会重新降为 2048。保留 RAW 路径；RAW/JPG 合并后同时登记 JPG 别名，避免迟到通知再次盖住已入库图像。
- 接收态开始和结束都须通知遥控事件时间线；只在下一次 120ms 轮询刷新会丢掉刚接续后的按键。当前接收图还不能关联正式评级时，阻止误给上一张标星。
- 测试必须区分原始 JPG 可见与正式资料就绪：原图可先显示，评级测试需等待其正式接续。浏览器可能容忍截断 JPG，不能把 `naturalWidth` 或 load 成功称为完整性验证。质量测试使用与主图明显不同的红色 160px 内嵌图，断言所有可见帧主图尺寸并核对 HTTP 原始字节。
- REA 确认 DPP 大图使用 WindowFit/ROI、独立队列、即时提交可用 backbuffer；未证明 DPP 全程序无检查。详细 Evidence 与边界见 `技术文档/CanonDPP监控预览机制与优化.md`。

## JPG 传输期间的显示与正式入库

- 仅测文件已写完后的速度会漏掉 1–5 秒的传输/句柄等待。Windows 的目录枚举在写句柄打开时可能仍报告 0 字节，实际已有完整 EXIF 缩略图；零字节文件也要记录并局部重试，不能只等 2 秒补偿扫描。
- 从有界 JPEG APP1/IFD1 中提取完整相机 JPEG，去除元数据、处理方向后临时显示；主文件继续按完整性、写句柄与读取后指纹校验入库。临时画面不能复用上一张的评级对象；旧文件名、星级、参数和直方图应隐藏，接续时不能闪回旧画面。
- 临时预览通知独立于保存和主目录刷新。新图到达应显式结束旧图的等待 Promise，仅把 `img.src` 置空未必能立即解除 `decode()` 等待。相同监控会话中的每张 Canon 通知也不应强制等待上张持久保存。
- 顺序按首次发现记录：旧慢图后完成不能抢回较新的图；更新到新目录/新 generation 时要清理取消跟随状态，即使新旧目录的相对文件名相同。没有内嵌图的新 JPG 完成后，也不能被旧慢图的临时画面盖住。
- 验证：源码 85 项、冻结 73 项，另有视觉/叠化/直方图及目录切换补充测试。2100 历史照片的完整发行引擎中，模拟额外保持写句柄 1/3/5 秒，图像头到首帧中位约 139/156ms；主图未完成前不入库，页面错误 0。仍需真机确认物理快门与 DPP 的实际差距。证据见任务 134、`build/jpeg-arrival-gap/`。

## 2026-10-28：业务回调拖住监控状态

- 表现：即使引擎 ready，监控状态请求仍可能长时间不返回，EOS 与预览线程也停在 `FolderWatch.state`。两次线程快照发现监控持状态锁同步执行归档回调，回调又等待 SKU 长业务锁。
- 解决：已提交的新图通知交给独立有界合并队列，失败重试；SKU 待处理会话使用独立短锁。通知消费者阻塞时，后续新图入库及状态长轮询仍可进行。不能只移动状态通知到回调之前，因为下一张图仍可能被同步回调堵住。
- 文件变化使用有名称的 Windows 异步通知并局部检查，保持独立全量补偿期限；持续连拍不能无限推迟补偿扫描。校验 JPEG 时复用缩小像素，元数据读取后指纹不变才发布缓存，避免再次读取同一原图。
- 修复扫描参数被 `paths` 循环变量覆盖的问题：完整扫描必须能清空 pending/initializing 和移除旧观测；不能把所有扫描误判为局部扫描。
- 验证：源码联机及安全回归 108 项（107 通过、缺样片跳过 1），冻结模块及打包前端 67 项通过；八种 EXIF 方向的校验像素复用与预览缓存/编码 33 项通过。性能只记录本地文件写完到绘制帧，未实拍；模拟 EOS 必须重新启用接入并断言通知 accepted，否则只是普通监控。

## 表现与定位

文件已经写完，目录监控仍比相机配套软件迟；历史缓存正在生成时尤其明显。不能只测无评级、无归档、无预生成的轻量 HTTP 夹具：本次轻量基准约 630ms，但完整服务压力场景约 2 秒。

## 根因与处理

- 每张 Canon 通知和后台跟随都重新激活同一会话，触发整目录评级恢复和 RAW 发现。先核对 active_id；同目录仅做局部评级登记、capture_ids 后续任务和增量页面合并。
- 每轮为全部历史图逐一 stat 不存在的 XMP。复用同次目录枚举属性，可信 EOS 通知优先局部检查同名 JPG/RAW/XMP；保留读取后签名复核。
- 快速预览等待持久缓存写锁及后台清晰图资源。当前快速图使用 CPU 缩小 JPEG 解码和有界内存返回；前台预览期间暂停领取历史任务，监控时历史并发保留两项，停止监控恢复普通并发。
- 完整且写句柄已关闭的 JPG 不再固定等 80ms；RAW/其他格式继续稳定检查。不能移除完整性和读取后签名检查。
- 先准备新快速图，仍保留旧选择与旧画面；准备好后再提交选择并淡入，防止“看到旧图却给新图标星”。清晰图升级保留缩放，手动操作/暂停使过期准备失效。

## 已验证结果

最终冻结完整服务在 600 张有效历史记录、已就绪缓存和相机 JPG 副本下，文件写完到预览就绪为 181–324ms，中位 232ms；同条件修复重复激活前中位 844ms。79 项联机回归通过，覆盖分段写入、RAW/JPG、评级、暂停、目录切换、动画与请求竞态。证据见 `开发任务/128-联机新图显示提速与过渡.md` 和 `build/live-preview-speed/`。这些数据不包含相机曝光或传输，不是 DPP 实测对比。


## 左侧也应使用直接画面接续

独立主图通道解决中心画面后，实际采集仍发现正式侧栏晚 1.8–3.7 秒。应将已加载的原图克隆到虚拟列表外的临时显示区域，等正式当前缩略实际可读后再移除；主图正式接续不等于侧栏已加载。临时画面不创建正式评级对象，用户导航/切目录清理，新图取消未完成克隆，避免旧图或空白重现。最终实拍 XSY_8106 主图和左侧均约 63.37ms 绘制、2400×1600，用户确认立即跟上；压力测试在六条业务请求阻塞时也覆盖左右同步。


## 2026-11-16：即时目录通知失效后的恢复

- 表现：默认链路仍可在文件到达后数百毫秒显示，但即时通知失效时可能退到 2 秒周期的正式监控补偿。另一台电脑反馈快门约 3 秒首显，不能仅因时长接近就断言该电脑也是此原因。
- 根因：DirectJpegFeed 只在通知对象为空或代次变化时重建，句柄为空但对象仍在时永久失效；未知 JPG 仅有修改通知时也被忽略。初始打开失败、运行中断开和仅修改通知三种隔离注入均在修改前复现失败。
- 解决：限频重建无效监听器，未知新 JPG 的修改事件同样接入原图通道；复用正式监控的历史编号及 JPG 别名，防止旧图补写导致自动跳回。保留 generation 隔离与正式补偿，不用缩短全目录扫描间隔掩盖即时通知故障。
- 验证：64 项联合回归通过；Edge 在正式监控锁持有期间仍可显示完整分辨率原图，模拟通知到绘制约 55–201ms。相机曝光及传输未测，重连测试不代表会自动补发丢失期间的全部事件。任务及证据见 `开发任务/243-现场拍摄显示延迟与即时通知恢复.md`。

## 2026-11-20：句柄恢复不等于漏图恢复，三次读取失败也不能永久停止

- 表现：最新版本正常路径很快，漏通知时仍约 2 秒首显；原图临时不可读后，即使已恢复也可能等正式入库才能显示。
- 根因：此前重连验收主动补发修改事件，没有覆盖断开期间丢失且不再补发的通知；浏览器对同一 revision/bytes 三次失败后永久停止。历史修复仍在，但异常恢复没有闭环。
- 解决：名称补偿放到独立线程，目录属性变化/监听恢复/溢出触发，不持业务锁、不解码。250ms 检查属性、空闲复用快照、2 秒名称校核；历史、代次、资料目录与旧图顺序必须隔离，离线不能丢弃已知基线。原图仅对当前有效最新通知限频重试，稳定失败后间隔 500ms，新图及取消跟随撤销旧任务。
- 验证：77 项联合回归及最后 10 项恢复检查通过；完整引擎在 600 张历史、CPU 4 倍降速、禁用 GPU、静默漏通知且正式锁保持时，主图 216–372ms 绘制，接续与标星正常。临时 423 阻断 800ms 后约 1127ms 自动绘制。任务及永久记录见 247；这些是本机文件写入起点的模拟结果，不等于客户机物理快门确诊。
- 验收探针不能把桌面管理头全局附加给跨来源图像请求，否则会人为制造 CORS 预检失败；遵循原生产品的调用范围，不为测试放宽 CORS。
