# 预览方向与 EXIF 镜像处理

JPEG 明确内嵌 Orientation=1 表示像素已经朝正，不能再次套用 RAW/目录方向6。JPEG 没有有效方向标记时，才回退已读取的目录方向；RAW 内嵌图也按此优先级处理，避免重复旋转。变换后的预览不保留方向 EXIF，原片不写入。

Pillow `Image.Transpose.FLIP_LEFT_RIGHT` 的枚举数值是 **0**。使用 `if transform` 判断是否需要变换会漏掉水平镜像，必须判断 `transform is not None`。通过独立四角颜色与尺寸检查验证 EXIF 1–8，不能只测试90度旋转。

方向处理规则或目录方向修正后需要更新预览缓存键，本项目为指纹/尺寸/解码标志/目录方向/v3；不删除已有用户缓存。配对 JPEG 的预览入口必须传入目录方向回退。

验证：`test_live_layout.py` 覆盖8方向、显式朝正/目录回退、缓存隔离；最终引擎通过实际 EXIF=6 的 JPEG 验证600×900竖图、上下颜色位置、原文件哈希不变，缩略图与大图均在 Chrome 查看。证据见开发任务017及 build/layout-acceptance。

归档网格曾出现“同一图片缩略图横向、右侧大图竖向”：原图 EXIF=8，后端两个尺寸都正确，问题是浏览器继续使用早期未旋转的 420px 图。仅更新磁盘缓存键不能淘汰 HTTP 的一年 immutable 缓存；图片 URL 还必须包含文件指纹与处理版本。添加尺寸时使用 URLSearchParams，避免二次拼接 `?` 丢失版本。归档与 SKU 数据库、右栏共用此规则；修改源图后版本地址随指纹变化。

归档里的单独 RAW 不经过选片目录元数据读取，必须自行读取 Orientation 并传给内嵌预览；按源路径、大小、修改时间缓存方向，避免每个尺寸重复启动 ExifTool。新增隔离 RAW 测试验证 EXIF=6 在两种尺寸均为竖图，源文件更新后重新读取；归档浏览器以 EXIF=8 JPEG 验证网格和右侧尺寸及版本 URL。
