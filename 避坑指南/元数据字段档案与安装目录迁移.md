# 元数据字段档案与安装目录迁移

## 表现与根因

- `metadata-backups` 看似只有元数据，实际上 `copy2(target, *.bin)` 复制完整 JPG/RAW，1183 份即可占约 12.16 GiB。
- Windows 原子替换还会在照片旁保存实际旧版本；即使去掉 data 里的整图备份，未收尾的成功恢复副本仍会持续膨胀。
- SQLite 主库不变不代表资料未更新：提交可能只存在 WAL。迁移或重试只看主库会漏掉新评级。
- 同步明确确认的来源评级时，不能让目标文件初始读到的评级覆盖任务字段；只有后来的主动人工修改才具有优先级。

## 解决方法

- RAW 新任务写同名 XMP，JPG 保持原有内嵌兼容；长期保存字段前后值、身份与哈希的 JSON，撤销通过字段写入完成。
- 临时整图仍用于读回、像素/RAW 负载验证及原子替换。确认数据库/字段档案成功后，校验目标新哈希和实际旧版本哈希，再按受保护句柄删除临时副本；外部竞争、失败或校验不一致一律保留实际旧文件。
- 安装资料迁移到 `<安装目录>/data`，用 SQLite backup 包含 WAL，再做 quick_check 和文件校验。非空目标不能合并覆盖；上次复制已成功但安装回滚时，只在源资料状态未变时复用目标。
- 重试收据必须跟踪非空 WAL，忽略可重建 SHM 和空 WAL；不能用忽略所有 WAL 的清单确认资料未变化。原资料在迁移后保留，清理是单独的、已授权且需核验的操作。
- RAW 身份/SKU 读回优先读取侧车；同名侧车有别人的永久文件身份仍拒绝写入。人工覆盖来源评级的优先级只使用 `explicit_only=True` 的最新主动修改。
- 成功安装完成后可以清理压缩包、stage 和 backup；测试须等全部载荷清理完，不能只看到 ZIP 消失就判断清理结束。失败或待回滚事务继续保留。

## 已验证

- 56 项安装/迁移测试包含 WAL、重试期间仅 WAL 更新、损坏数据库、空间不足、非空目录、恢复副本哈希不符及受管卸载保护。
- 61 项相关回归通过，涵盖真实 CR3 全文件 SHA-256 不变、字段撤销、JPG 像素、竞争替换恢复、换机导入及评级冲突显式覆盖。
- 正式资料只迁移不改照片，1183 份整图副本核验转换为约 1.72 MiB 的字段档案；数据表记录数保持一致。
